# Jira 운영 컨벤션

이 문서는 이슈 구조·제목·담당자·작업량·상태·완료 기준의 원본이다. 브랜치·커밋·MR·리뷰·병합 상세 규칙은 Git 컨벤션을 따른다. 프로젝트 키는 `S15P31A307`이다.

## 1. 운영 목적

Jira는 프로젝트의 기능과 실제 수행 업무를 다음 기준으로 관리한다.

```
Notion  → 기능·정책·문서의 원본 관리
Jira    → 기능 구조, 담당자, 스프린트, 진행 상태, 작업량 관리
GitLab  → 브랜치, 커밋, Merge Request, 코드 관리
```

같은 내용을 세 도구에 반복해서 작성하지 않는다.

- Notion에는 상세한 기획, 정책, 화면 설계, 명세를 작성한다.
- Jira에는 업무 수행에 필요한 핵심 설명, 완료 기준, 담당자, 일정, 결과물 링크를 기록한다.
- GitLab에는 실제 구현 코드와 변경 이력을 관리한다.

---

## 2. Jira 업무 구조

프로젝트에서는 다음 구조를 사용한다.

```
에픽
├─ 스토리
├─ 작업
└─ 버그
```

### 핵심 원칙

- 스토리·작업·버그는 모두 에픽 바로 아래에 생성한다.
- 작업을 스토리 아래에 넣지 않는다.
- 스토리와 작업의 관계는 동일한 스토리 코드와 `연결된 업무 항목`으로 표현한다.
- 개인별 구현 업무와 스토리 포인트는 작업 또는 버그에서 관리한다.
- 서브 작업은 평가·작업량 집계에서 누락될 수 있으므로 작업 지시 목적으로 사용하지 않는다. 스프린트 중 추가 업무(2.6)에만 예외로 사용한다.

### 실제 구조 예시

```
에픽: [AUTH] 회원 인증

├─ 스토리: [AUTH-001] 로그인 구현
├─ 스토리: [AUTH-002] 회원가입 구현
├─ 작업:  [AUTH-001 | FE] 로그인 화면 구현
├─ 작업:  [AUTH-002 | BE] 회원가입 API 구현
└─ 버그:   [AUTH-001 | FE] 로그인 실패 시 오류 문구가 표시되지 않음
```

---

### 2.1 에픽

에픽은 기능 도메인 또는 프로젝트 지원 영역을 묶는 최상위 업무 항목이다.

#### 기능 에픽

기능 에픽은 제목 맨 앞에 영문 대문자 에픽 prefix를 포함한다.

```
[AUTH] 회원 인증
[USER] 회원 정보
[DEVICE] 기기 연동
[NOTI] 알림
```

#### 지원 에픽

서비스 기획·인프라처럼 특정 기능 도메인으로 한정되지 않는 공통 업무 영역은 명사형으로 작성한다.

```
서비스 기획
개발 기반 및 인프라 구축
```

#### 에픽 운영 기준

- 에픽은 스토리·작업·버그를 묶는 영역이다.
- 에픽에는 스토리 포인트를 입력하지 않는다.
- 에픽 이슈 자체에서 작업 브랜치를 생성하지 않는다.
- 기능 에픽의 prefix는 관련 코드 작업의 브랜치 prefix로 사용한다.
- 에픽 담당자는 필수가 아니며, 필요할 경우 영역 관리 책임자를 지정한다.

---

### 2.2 스토리

스토리는 사용자에게 제공할 기능 또는 통합 가능한 기능 단위를 나타낸다.

```
[AUTH-001] 로그인 구현
[AUTH-002] 회원가입 구현
[AUTH-003] 통합 검증 및 안정화
[DEVICE-001] 센서 데이터 수집
[NOTI-001] 푸시 알림
[NOTI-002] 알림 내역
```

스토리는 FE·BE·AI·EMB 중 한 파트의 개별 구현 업무가 아니라, 여러 작업이 함께 완성하는 기능 단위다.

#### 스토리 운영 기준

- 스토리 코드는 `{에픽 prefix}-{3자리 일련번호}` 형식으로 작성한다.
- 실제 개인별 구현 업무는 별도의 작업으로 생성한다.
- 관련 작업은 같은 스토리 코드를 제목에 사용한다.
- 관련 스토리와 작업은 `관련됨` 관계로 연결한다.
- 스토리에는 원칙적으로 스토리 포인트를 입력하지 않는다.
- 기능 개발 브랜치는 스토리가 속한 기능 에픽의 prefix를 사용한다.
    - `[AUTH-001] 로그인 구현` 관련 작업 → `feat/AUTH-{작업 내용}`
- 브랜치에는 스토리 코드(`AUTH-001`)나 Jira 키(`S15P31A307-{번호}`)를 넣지 않는다.
- 상세한 명명·분기·병합 규칙은 Git 컨벤션을 따른다.
- 스토리 담당자는 선택 사항이며, 통합 확인 책임자가 필요한 경우에만 지정한다.

---

### 2.3 작업

작업은 담당자가 실제로 수행하고 완료할 수 있는 실행 단위이다.

다음 업무를 모두 작업으로 생성한다.

- FE·BE·AI·EMB 기능 구현
- API 연동
- 화면 구현
- 테스트 및 검증
- 기획 및 UX 설계
- 디자인 및 프로토타입 제작
- 기술 검증
- 문서 작성
- 환경 설정 및 인프라 구축

#### 기능 구현 작업 예시

```
[AUTH-001 | FE] 로그인 화면 구현
[AUTH-001 | BE] 로그인 API 구현
[AUTH-002 | FE] 회원가입 API 연동 및 입력값 검증
[DEVICE-001 | EMB] 센서 데이터 수집 펌웨어 구현
[DEVICE-001 | BE] 기기 데이터 수신 API 구현
[NOTI-001 | AI] 알림 대상 추천 베이스라인 모델 구현
```

#### 지원 업무 작업 예시

```
[PLAN] 핵심 기능 정의
[UX] 정보 구조 및 메뉴 구성 설계
[DOCS] 기술 스택 및 인프라 구성안 확정
[INFRA | FE] 프론트엔드 개발 환경 및 코드 구조 구축
[INFRA | BE] Spring Boot 프로젝트 초기 세팅
[TECH | BE] 프론트엔드 연동을 위한 CORS·에러 응답 표준화
```

#### 작업 운영 기준

- 실제 수행자 한 명을 담당자로 지정한다.
- 스토리 포인트·스프린트·우선순위를 작업에 입력한다.
- 레이블을 반드시 지정한다.
- 기능 구현 작업은 관련 기능 에픽 아래에 생성하고, 제목에 관련 스토리 코드를 사용한다.
- 기능 구현 작업은 관련 스토리와 반드시 `관련됨` 관계로 연결한다. 스토리와 작업은 부모·자식이 아니라 동일 에픽 아래의 독립 이슈이므로 `연결된 업무 항목`으로 연결한다.
- 코드 작업은 관련 에픽 prefix 기반 브랜치에서 진행하고 작업 단위로 MR을 생성한다.
- 관련 기능 에픽이 없는 지원 업무는 공식 업무 분류를 브랜치 prefix로 사용한다.
- Jira 키는 브랜치명이 아니라 커밋과 MR의 관련 이슈에 사용한다.
- 하나의 작업은 한 명이 반나절~하루(2~5점) 안에 완료할 수 있는 크기를 권장한다.
- 완료 여부를 객관적으로 판단할 수 있는 결과물이 있어야 한다.

---

### 2.4 버그

버그는 이미 구현된 기능이 요구사항 또는 의도와 다르게 동작할 때 생성한다.

```
[AUTH-001 | FE] 로그인 실패 시 오류 문구가 표시되지 않음
[AUTH-002 | BE] 동일 이메일로 중복 가입됨
[DEVICE-001 | EMB] 센서 값이 주기적으로 누락됨
```

#### 버그 운영 기준

- 관련 기능 에픽 바로 아래에 생성한다.
- 관련 스토리 또는 작업과 `관련됨` 관계로 연결한다.
- 긴급 선행 수정이 필요하면 `차단함 / 차단됨` 관계를 사용한다.
- 실제 수정 담당자·스토리 포인트·스프린트·우선순위를 입력한다.
- 레이블을 반드시 지정한다.
- 일반 버그는 관련 에픽 prefix 기반 `fix/*`, 운영 긴급 버그는 `hotfix/*` 브랜치에서 처리한다.
- 버그 Jira 키는 커밋과 MR의 관련 이슈에 기록하며 버그 단위로 MR을 생성한다.

---

### 2.5 서브 작업

서브 작업은 원칙적으로 사용하지 않는다. 단, 스프린트 시작 후 추가된 업무는 2.6의 `[Extra] 추가 작업` 아래 서브 작업으로만 생성한다.

#### 사용하지 않는 이유

- 개인별 작업량과 스토리 포인트 집계에서 제외될 수 있다.
- 실제 구현 업무가 스토리 아래에 숨겨져 목록과 스프린트에서 확인하기 어렵다.
- 브랜치·MR·담당자 단위 추적이 불명확해질 수 있다.

작업을 더 나누어야 할 경우 서브 작업 대신 동일 에픽 아래에 별도 작업을 생성한다.

```
비추천
스토리: [AUTH-001] 로그인 구현
└─ 서브 작업: [FE] 로그인 화면 구현

추천
에픽:  [AUTH] 회원 인증
├─ 스토리: [AUTH-001] 로그인 구현
└─ 작업:  [AUTH-001 | FE] 로그인 화면 구현
```

---

### 2.6 Extra 추가 작업

스프린트 시작 후 새로 필요해진 업무는 별도 작업으로 스프린트에 추가하지 않고, 각자의 `[Extra] 추가 작업` 아래 서브 작업으로 생성한다. 스토리 포인트가 있는 이슈를 스프린트 중에 추가하면 번다운 차트에 범위 변경으로 기록되므로, 이를 피하고 계획 대비 진행 흐름을 유지하기 위한 규칙이다.

```
작업: [Extra] 추가 작업                          (담당자: 본인, 스토리 포인트 없음)
├─ 서브 작업: [AUTH-001 | FE] 로그인 실패 횟수 제한 안내 추가   ↔ [AUTH-001] 로그인 구현
└─ 서브 작업: [INFRA | BE] 스테이징 DB 백업 스크립트 작성
```

#### `[Extra] 추가 작업` 운영 기준

- 팀원 각자가 스프린트 시작 시 `[Extra] 추가 작업` 작업을 하나씩 생성해 해당 스프린트에 배정한다.
- 담당자는 본인, 레이블은 본인의 담당 영역 레이블을 지정한다.
- 스토리 포인트는 입력하지 않는다. 상위 에픽과 관련 스토리 연결은 지정하지 않는다.
- 제목은 `[Extra] 추가 작업`으로 고정하며, 3장의 제목 규칙과 브랜치 생성 대상에서 제외한다.

#### 서브 작업 운영 기준

- 제목은 `[스토리 코드 | 담당 영역] 작업명` 형식으로 작성한다. 관련 스토리가 없는 지원 업무는 `[업무 분류 | 담당 영역] 작업명`을 사용한다.
- 관련 스토리와 `관련됨` 관계로 연결한다. 관련 스토리가 없는 지원 업무는 제외한다.
- 담당자·레이블·설명·완료 기준을 입력한다. 스토리 포인트는 입력하지 않는다.
- 브랜치는 관련 스토리가 속한 에픽 prefix(지원 업무는 업무 분류)를 사용하고, 커밋과 MR에는 서브 작업의 Jira 키를 사용한다.
- 완료 기준은 16장의 작업 완료를 따른다.
- 스프린트 종료 시 완료하지 못한 서브 작업은 다음 스프린트의 본인 `[Extra] 추가 작업` 아래로 옮기고, 이번 스프린트의 `[Extra] 추가 작업`은 완료 처리한다.
- 추가 버그는 2.4의 버그 이슈로 생성한다.

## 3. 제목 작성 규칙

### 3.1 에픽 prefix와 스토리 코드

기능 에픽과 스토리는 다음 식별 체계를 사용한다.

```
에픽 prefix: AUTH
스토리 코드:  AUTH-001
Jira 키:     S15P31A307-{번호}
```

#### 스토리 코드 형식

```
{에픽 prefix}-{3자리 일련번호}
```

```
AUTH-001
AUTH-002
DEVICE-001
NOTI-001
```

#### 운영 원칙

- 에픽 prefix는 영문 대문자로 작성한다.
- 스토리 번호는 `001`부터 시작하는 3자리 숫자로 작성한다.
- 같은 스토리를 구현하는 스토리·작업·버그는 같은 스토리 코드를 사용한다.
- 하나의 스토리 코드를 서로 다른 기능에 중복 사용하지 않는다.
- Jira 키 `S15P31A307-숫자`는 Jira가 자동 생성하는 개별 이슈 식별자다.
- 에픽 prefix·스토리 코드·Jira 키는 서로 다른 목적이므로 구분한다.

### 3.4 기능 작업 제목

```
[스토리 코드 | 담당 영역] 구체적인 작업명
```

```
[AUTH-001 | FE] 로그인 화면 구현
[AUTH-001 | BE] 로그인 API 구현
[AUTH-002 | FE] 회원가입 API 연동 및 입력값 검증
[DEVICE-001 | EMB] 센서 데이터 수집 펌웨어 구현
[DEVICE-001 | BE] 기기 데이터 수신 API 구현
[NOTI-001 | AI] 알림 대상 추천 베이스라인 모델 구현
```

#### 담당 영역

```
FE
BE
AI
EMB
```

- 데이터·인프라 작업은 별도 담당 영역과 develop 브랜치를 두지 않는다. 기능 작업이면 해당 파트 영역을, 지원 업무면 `[INFRA | BE]`처럼 업무 분류와 파트 영역을 함께 쓰고 해당 파트 develop-*에 병합한다.
- 대괄호 안의 구분자는 반드시 공백을 포함한 `|`를 사용한다.
- 제목은 파일명이나 클래스명이 아니라 결과 중심으로 작성한다.
- `구현`, `연동`, `검증`, `설계`, `정의`, `작성`처럼 완료 상태를 판단할 수 있는 표현을 사용한다.

---

### 3.5 지원 업무 작업 제목

관련 스토리 코드가 없는 기획·디자인·문서·기술 업무는 다음 형식을 사용한다.

```
[업무 분류] 작업명
[업무 분류 | 담당 영역] 작업명
```

```
[PLAN] 핵심 기능 정의
[UX] 정보 구조 및 메뉴 구성 설계
[DESIGN] 와이어프레임 제작
[TECH | BE] CORS·에러 응답 표준화
[INFRA | BE] Spring Boot 프로젝트 초기 세팅
[DOCS] 기술 스택 및 인프라 구성안 확정
[QA] 핵심 사용자 시나리오 검증
```

#### 공식 업무 분류

| 분류 | 사용 범위 |
| --- | --- |
| `PLAN` | 서비스 목표, 정책, 요구사항, 기능 범위 |
| `UX` | 정보 구조, 사용자 흐름, 메뉴 구조, 사용성 |
| `DESIGN` | 와이어프레임, UI, 프로토타입, 디자인 검수 |
| `TECH` | 기술 조사, PoC, 공통 구조, 성능 검증 |
| `INFRA` | 서버, 배포, CI/CD, 네트워크, 환경 구성 |
| `DOCS` | 명세, README, 발표 자료, 결과 문서 |
| `QA` | 테스트 계획, 통합 테스트, 기능 검증 |
| `PT` | 발표 및 시연 준비 |

---

### 3.6 버그 제목

```
[스토리 코드 | 담당 영역] 오류 조건 또는 증상
```

```
[AUTH-001 | FE] 로그인 실패 시 오류 문구가 표시되지 않음
[AUTH-002 | BE] 동일 이메일로 중복 가입됨
[DEVICE-001 | EMB] 센서 값이 주기적으로 누락됨
```

담당 영역이 아직 확정되지 않았다면 스토리 코드만 사용한다.

```
[AUTH-002] 회원가입 완료 화면으로 이동하지 않음
```

---

### 3.7 사용하지 않는 제목 형식

```
[AUTH-01] 로그인 구현             → 번호 자릿수 불일치
[AUTH-001-FE] 로그인 화면 구현    → 담당 영역 구분자 오류
[FE][AUTH-001] 로그인 화면 구현   → 순서와 구분자 불일치
[AUTH-001/로그인] 구현            → 슬래시 사용
[BE] 로그인 API 구현              → 스토리 코드 누락
로그인 화면                       → 업무 유형과 범위 확인 불가
```

## 4. 스토리와 작업 연결 규칙

스토리와 작업은 부모·자식 관계가 아니라 같은 에픽 아래의 독립 이슈다.

### 4.1 동일 스토리 코드 사용

```
스토리: [AUTH-002] 회원가입 구현
작업:  [AUTH-002 | FE] 회원가입 API 연동 및 입력값 검증
작업:  [AUTH-002 | BE] 회원가입 API 구현
작업:  [AUTH-002 | BE] 이메일 중복 검증 구현
```

### 4.2 연결된 업무 항목 사용

#### 관련됨

같은 기능을 구현하는 스토리와 작업을 연결한다.

```
[AUTH-002] 회원가입 구현
↔ [AUTH-002 | FE] 회원가입 API 연동 및 입력값 검증
↔ [AUTH-002 | BE] 회원가입 API 구현
```

#### 차단함 / 차단됨

선행 업무가 완료되어야 진행할 수 있을 때 사용한다.

```
[AUTH-002 | FE] 회원가입 API 연동 및 입력값 검증
→ [AUTH-002 | BE] 회원가입 API 구현에 의해 차단됨
```

#### 중복 생성 금지

- FE와 BE가 각각 같은 이름의 스토리를 만들지 않는다.
- 구현 담당자별 업무는 스토리가 아니라 작업으로 생성한다.
- 동일한 업무를 스토리와 작업에 중복 등록하지 않는다.

- 기능 완료 목표를 보여 줄 필요가 있을 때만 목표 스프린트를 입력한다.
- 실제 작업량과 번다운 집계는 작업과 버그를 기준으로 한다.
- 스토리에 스토리 포인트를 중복 입력하지 않는다.

## 7. 작업 분리 기준

작업은 담당자와 결과물을 기준으로 분리한다.

### 권장 크기

- 한 명이 담당한다.
- 반나절~하루(2~5점) 안에 완료할 수 있다.
- 하나의 MR 또는 하나의 명확한 문서 결과물로 끝난다.
- 완료 여부를 객관적으로 판단할 수 있다.

### 지나치게 작은 분리

```
비추천
- 로그인 버튼 생성
- 이메일 Input 컴포넌트 생성
- API 함수 파일 생성
- Controller 파일 생성
- DTO 파일 생성
- 버튼 색상 변경
```

### 적절한 분리

```
추천
- [AUTH-001 | FE] 로그인 화면 구현
- [AUTH-002 | FE] 회원가입 API 연동 및 입력값 검증
- [AUTH-002 | BE] 회원가입 API 구현
```

하나의 작업이 하루를 넘기거나 서로 다른 담당자가 함께 수행해야 한다면 작업을 나눈다.

## 8. 스토리 포인트 규칙

스토리 포인트는 실제 수행 업무인 `작업`과 `버그`에만 입력한다.

에픽과 스토리에는 입력하지 않는다. 같은 기능의 스토리와 작업에 포인트를 중복 입력하지 않는다.

### 기준

#### 1점: 30분 ~ 1시간 이내

- 문서 일부 수정, 오탈자 수정
- 리뷰 피드백 반영
- UI 문구·색상·간격 등 단순 스타일 수정
- 설정값·환경 변수 변경
- 테스트 케이스 1~2개 추가

#### 2점: 오전 반나절

- 회의록·짧은 신규 문서 작성
- 정적 화면 또는 단일 컴포넌트 구현
- 단일 엔티티 CRUD API 구현
- 이미 만들어진 API를 화면에 단순 연동
- 센서 하나의 값 읽기 등 단순 기능 단위 테스트(EMB)

#### 3점: 오후 반나절

- 상태·이벤트 처리가 포함된 화면 1개 구현
- 입력값 검증과 오류 처리를 포함한 기능 API 구현
- 외부 API 1종 연동
- 기능 명세서·API 명세 등 분량 있는 문서 작성
- 공개 데이터셋 전처리, 사전학습 모델 추론 테스트(AI)

#### 5점: 하루

- 핵심 사용자 기능 1개를 FE·BE에 걸쳐 완성
- 인증·인가, 파일 업로드 등 여러 단계로 구성된 기능 구현
- 실시간 통신(WebSocket·MQTT 등) 또는 동시성 처리
- 초기 서버·CI/CD 구성
- 기기-서버 통신 연동(EMB)
- 데이터 수집 및 라벨링 1회분, 기존 모델 파인튜닝 1회(AI)

#### 8점: 하루 초과, 완료 가능 여부 불확실

- 결과를 예측하기 어려운 기술 연구·PoC (선례가 없는 기술 검증, 모델 구조 탐색 등)
- 백엔드 대규모 수정 (도메인·DB 스키마 전면 개편, 아키텍처 변경)
- 자체 모델 학습 파이프라인 구축
- 프레임워크 또는 주요 기술 구조 전면 교체

8점 작업은 착수 전에 분리할 수 있는지 먼저 검토한다. 범위를 나눌 수 있으면 5점 이하 작업 여러 개로 쪼개고, 연구처럼 나눌 수 없는 작업만 8점으로 둔다. 8점을 초과할 것으로 예상되는 작업은 반드시 분리한다.

## 9. 스프린트 운영 규칙

### 배정 기준

| 업무 유형 | 스프린트 배정 |
| --- | --- |
| 에픽 | 배정하지 않음 |
| 스토리 | 필요 시 기능 완료 목표 스프린트 지정 |
| 작업 | 반드시 배정 |
| 버그 | 처리할 스프린트에 배정 |
| `[Extra] 추가 작업` | 스프린트 시작 시 팀원별 1개 배정 |
| 서브 작업 | `[Extra] 추가 작업` 아래에만 생성 (부모 스프린트를 따름) |

### 스프린트에 넣기 전 필수 항목

```
상위 에픽
제목 규칙
설명
완료 기준
담당자
우선순위
스토리 포인트
연결된 업무 항목
기한
레이블
관련 Notion 링크(관련 시)
```

스토리의 경우 담당자와 스토리 포인트는 필수가 아니다.

### 백로그 사용 기준

- 수행 시기가 정해지지 않은 업무
- 추가 또는 확장 기능
- 설명과 완료 기준이 준비되지 않은 업무
- 담당자와 우선순위가 정해지지 않은 업무

### 스프린트 중 업무 추가

다음 경우에만 추가한다.

- 스프린트 목표 달성에 반드시 필요한 누락 업무
- 핵심 기능을 차단하는 긴급 버그
- 팀 합의로 기존 업무와 교체하는 업무
- 파트 간 진행 속도 차이로 새로 필요해진 업무

추가 업무는 별도 작업으로 스프린트에 넣지 않고 본인의 `[Extra] 추가 작업` 아래 서브 작업으로 생성한다(2.6). 스토리 포인트가 없으므로 범위 변경으로 기록되지 않는다.

긴급 버그를 버그 이슈로 추가하거나 팀 합의로 기존 업무를 교체한 경우에는 범위 변경으로 기록될 수 있으므로 이유를 댓글에 남긴다.

## 10. 릴리즈(버전) 운영 규칙

Jira의 **릴리즈** 기능(이슈의 `버전`/Fix Version 필드)으로 "어느 이슈가 어느 배포에 들어갔는지"를 관리한다. 배포 절차·태그·브랜치는 Git 컨벤션 7절을 따르고, 여기서는 Jira 쪽 규칙만 정한다.

### 버전 이름

```
v{주차}.{번호}      Git 태그와 같은 문자열

v1.0   1주차 금요일 정기 릴리즈
v1.1   1주차 정기 릴리즈 뒤 추가 릴리즈
v2.0   2주차 금요일 정기 릴리즈
```

- 매주 금요일 정기 릴리즈는 `v{주차}.0`, 그 뒤 다음 금요일 전까지의 추가 릴리즈는 `v{주차}.1`, `v{주차}.2` 순이다.
- 이름은 Git 태그·GitLab Release와 반드시 같게 쓴다. 파트별 버전을 따로 만들지 않는다.

### 버전 생성

- 팀장(PM)이 만든다. 정기 릴리즈 버전은 늦어도 그 주 **월요일 스프린트 계획 때** 만들어 두어, 작업을 만들 때 바로 버전을 고를 수 있게 한다.
- 시작일은 직전 정기 릴리즈 다음 날, 릴리즈일은 해당 금요일로 입력한다. 설명에는 그 주 릴리즈 목표를 한 줄로 적는다.
- 추가 릴리즈 버전은 핫픽스·중간 배포가 결정된 시점에 만든다.

### 버전 입력 대상

| 업무 유형 | 버전 입력 |
| --- | --- |
| 에픽 | 입력하지 않음 |
| 스토리 | 완료 처리할 때, 기능이 사용자에게 나간 릴리즈를 입력 |
| 작업 (코드 변경) | 필수. 그 변경이 `main`에 들어가는 릴리즈 |
| 작업 (기획·디자인·문서) | 선택. 배포물과 무관하면 비워 둔다 |
| 버그 | 필수. 수정이 `main`에 들어가는 릴리즈 |
| `[Extra] 추가 작업`·서브 작업 | 입력하지 않음 |

- 작업을 만들 때는 **목표 릴리즈**를 넣는다. 그 주 금요일에 못 나가면 릴리즈 처리 때 다음 버전으로 옮긴다.
- 한 이슈에 여러 버전을 넣지 않는다. 실제로 나간 버전 하나만 남긴다.
- 핫픽스 버그는 추가 릴리즈 버전(`v{주차}.1` 등)을 넣는다.

### 릴리즈 처리 (매주 금요일)

1. Git 컨벤션 7절에 따라 `main` 병합과 태그가 끝난 뒤 팀장이 처리한다.
2. 릴리즈 화면에서 해당 버전의 미완료 이슈를 확인한다. `main`에 들어가지 않은 이슈는 **다음 버전으로 이동**한다. 이슈를 지우거나 상태를 억지로 `완료`로 바꾸지 않는다.
3. 버전을 `릴리즈됨`으로 바꾼다. 릴리즈일이 실제 날짜와 다르면 고친다.
4. Jira 릴리즈 노트 링크를 GitLab Release 설명과 그 주 회의록에 남긴다.
5. 다음 주 정기 릴리즈 버전이 없으면 이때 만든다.

### 스프린트와의 관계

- 스프린트는 "언제 할 일인가", 버전은 "언제 나갔는가"를 나타낸다. 스프린트 길이가 1주가 아니어도 버전은 항상 주 단위로 둔다.
- 스프린트 종료 시 남은 작업은 스프린트 규칙(9장)대로 옮기고, 버전도 다음 릴리즈로 함께 옮긴다.

## 11. 우선순위 설정 규칙

### Highest

완료되지 않으면 핵심 시연이나 팀 전체 진행이 불가능한 업무

```
배포 서버 장애
파트 간 통합 차단
핵심 기능 전체 동작 불가
데이터 유실 또는 중복 처리
```

### High

현재 스프린트 목표 달성에 반드시 필요한 업무

```
로그인·회원가입
핵심 기능 API
기기-서버 핵심 연동
```

### Medium

핵심 흐름을 보완하지만 일부가 없어도 기본 시연이 가능한 업무

```
프로필 수정
목록 필터
세부 오류 안내
일부 UI 개선
```

### Low

시간이 남을 때 구현하거나 이후 확장할 업무

```
추천 기능
고급 필터
공유 기능
추가 애니메이션
```

우선순위는 개인적인 급함이 아니라 스프린트 목표와 핵심 사용자 흐름에 미치는 영향을 기준으로 지정한다.

## 12. 담당자와 보고자 규칙

### 에픽

- 담당자는 선택 사항이다.
- 영역 책임자를 명확히 표시해야 할 때만 지정한다.

### 스토리

- 담당자는 선택 사항이다.
- 기능 통합 확인 책임자가 필요할 때만 지정한다.
- 실제 FE·BE·AI·EMB 수행자는 관련 작업의 담당자로 지정한다.

### 작업·버그

- 실제 수행자를 반드시 담당자로 지정한다.
- 스프린트가 시작된 작업을 `담당자 없음`으로 두지 않는다.
- 여러 사람이 함께 수행한다면 담당자별 작업으로 분리한다.

### 보고자

- 이슈를 최초 생성하거나 업무를 요청한 사람을 유지한다.
- 담당자와 보고자는 같을 수 있다.

## 13. 상태 운영 규칙

개발 브랜치 표기 `develop-*`는 해당 파트의 `develop-FE`, `develop-BE`, `develop-AI`, `develop-EMB`를 뜻한다.

현재 보드 상태를 다음과 같이 사용한다.

```
해야 할 일 → 진행 중 → 완료
```

### 작업·버그

#### 해야 할 일

- 요구사항과 완료 기준이 정리된 상태
- 담당자와 스프린트가 지정된 상태
- 코드 작업이라면 브랜치를 생성하기 전 상태

#### 진행 중

다음 과정을 모두 포함한다.

```
브랜치 생성
구현 또는 문서 작성
커밋 및 push
Merge Request 생성
리뷰 및 수정
테스트
```

#### 완료

코드 작업은 다음 조건을 모두 만족할 때 완료한다.

```
구현 완료
정상·예외 테스트 완료
Merge Request 리뷰 완료
CI 통과
해당 파트 develop-* 병합 완료 (핫픽스는 main 및 관련 develop-* 반영)
관련 문서 갱신
Jira 완료 기준 확인
```

기획·디자인·문서 작업은 다음 조건을 모두 만족할 때 완료한다.

```
결과물 작성 완료
팀 검토 또는 승인 완료
결과물 링크 등록
수정 사항 반영 완료
```

### 스토리

- 관련 작업 중 하나가 시작되면 `진행 중`으로 변경할 수 있다.
- 필수 작업과 필요한 파트 간 통합 테스트가 끝나고 사용자 흐름이 검증된 뒤 담당자 또는 통합 확인 책임자가 수동으로 `완료` 처리한다. 작업 완료만으로 자동 종료하지 않는다.
- 관련 작업이 남아 있거나 통합 테스트가 끝나지 않았다면 완료 처리하지 않는다.

### 에픽

- 에픽 내 핵심 스토리와 작업이 진행되면 `진행 중`으로 관리한다.
- 필수 스토리·작업 및 핵심 사용자 흐름 검증을 마치고, 제외·연기 범위와 산출물을 정리한 뒤 담당자 또는 영역 관리 책임자가 수동 완료 처리한다. 하위 이슈 완료만으로 자동 종료하지 않는다.

## 14. Notion 웹 링크 규칙

Jira에는 핵심 내용만 작성하고 상세 자료는 Notion 웹 링크로 연결한다.

### 링크 이름

```
[스토리 코드] 기능명
[Jira 키] 작업명
문서명
```

```
[AUTH-001] 로그인 구현
[S15P31A307-{번호}] 로그인 화면 구현
회원 인증 정책
```

### 스토리

다음 링크를 연결한다.

- 기능 정의서
- 관련 정책 문서
- 사용자 흐름 또는 화면 설계

### 작업

해당 작업을 수행하는 데 직접 필요한 자료만 연결한다.

- 작업 페이지
- 디자인 또는 API 명세
- 결과 문서

브랜치·커밋·MR은 Jira-GitLab 연동의 개발 정보로 확인하며 Notion에 중복 등록하지 않는다.

관련 기능 페이지와 동일한 링크를 모든 작업에 반복 등록하지 않는다.

## 15. 레이블 사용 규칙

컴포넌트 대신 담당 영역과 업무 성격을 레이블로 관리한다.

| 레이블 | 사용 대상 |
| --- | --- |
| `feat` | 사용자 기능 스토리 |
| `FE` | 프론트엔드 작업·버그 |
| `BE` | 백엔드 작업·버그 |
| `AI` | AI 모델·AI 서버 작업·버그 |
| `EMB` | 임베디드 작업·버그 |
| `INFRA` | 서버·배포·CI/CD·네트워크 작업 |
| `PLAN` | PLAN·UX·DESIGN 작업 |
| `TECH` | 기술 조사·PoC·구조 검토 |
| `DOCS` | 명세·README·발표 자료 |
| `QA` | 테스트·검증 업무 |
| `PT` | 발표·시연 준비 |

### 적용 기준

- 스토리·작업·버그는 레이블을 반드시 지정한다. 에픽은 레이블을 지정하지 않는다.
- 스토리는 `feat`를 사용한다.
- 작업과 버그는 핵심 담당 영역 레이블 하나를 기본으로 사용한다.
- 담당 영역이 없는 지원 업무는 업무 분류 레이블을 사용한다.
- 업무 분류와 담당 영역이 함께 있는 지원 업무는 담당 영역 레이블을 사용한다. 예: `[INFRA | BE]` → `BE`, `[INFRA]` → `INFRA`
- 제목에 `[AUTH-001 | FE]`가 있으면 레이블은 `FE`를 사용한다.
- 레이블을 불필요하게 여러 개 붙이지 않는다.

## 16. 완료 기준

### 작업 완료

```
담당 범위 구현 또는 결과물 작성 완료
자체 검증 완료
코드 작업은 MR 리뷰·CI·해당 파트 develop-* 병합 완료 (핫픽스는 main 및 관련 develop-* 반영)
관련 문서와 링크 갱신 완료
Jira 완료 기준 확인 완료
```

### 버그 완료

```
원인 파악 완료
수정 완료
재현 테스트와 회귀 테스트 완료
MR 리뷰·CI 통과·해당 파트 develop-* 병합 완료 (핫픽스는 main 및 관련 develop-* 반영)
```

### 스토리 완료

```
동일 스토리 코드의 필수 작업 완료
관련 파트 간 연동 완료
사용자 시나리오 정상 동작
완료 기준 검증 완료
치명적인 버그 없음
관련 Notion 문서 최신화
```

### `[Extra] 추가 작업` 완료

```
하위 서브 작업 모두 완료 또는 다음 스프린트의 [Extra] 추가 작업으로 이동
```

### 에픽 완료

```
필수 스토리와 작업 완료
제외 또는 연기한 기능 정리
핵심 사용자 흐름 검증 완료
관련 문서와 산출물 정리 완료
```

## 17. Jira 이슈 생성 체크리스트

### 에픽

```
- [ ] 기능 도메인 또는 지원 영역이 명확한가?
- [ ] 제목 규칙을 지켰는가?
- [ ] 중복 에픽이 없는가?
```

### 스토리

```
- [ ] 올바른 에픽에 연결했는가?
- [ ] [스토리 코드] 기능명 형식을 지켰는가?
- [ ] 기능 단위로 작성했는가?
- [ ] 사용자 시나리오와 완료 기준을 작성했는가?
- [ ] 기능 정의서 링크를 등록했는가?
- [ ] 레이블(`feat`)을 지정했는가?
- [ ] 관련 작업과 동일한 스토리 코드를 사용하는가?
- [ ] 스토리 포인트를 중복 입력하지 않았는가?
```

### 작업

```
- [ ] 올바른 에픽에 연결했는가?
- [ ] [스토리 코드 | 담당 영역] 형식을 지켰는가?
- [ ] 실제 수행 담당자를 지정했는가?
- [ ] 설명과 완료 기준을 작성했는가?
- [ ] 우선순위와 스토리 포인트를 입력했는가?
- [ ] 올바른 스프린트에 배정했는가?
- [ ] 레이블을 지정했는가?
- [ ] 기능 작업이면 관련 스토리와 `관련됨`으로 연결했는가?
- [ ] 필요한 문서 링크를 등록했는가?
- [ ] 코드 작업이면 Git 컨벤션에 따른 관련 에픽 prefix 또는 공식 업무 분류 기반 브랜치에서 작업하고 MR을 생성했는가?
- [ ] Jira 키는 브랜치명이 아니라 커밋과 MR의 관련 이슈에 사용했는가?
```

### 버그

```
- [ ] 관련 에픽에 연결했는가?
- [ ] 스토리 코드와 오류 증상을 제목에 작성했는가?
- [ ] 재현 절차, 실제 결과, 기대 결과를 작성했는가?
- [ ] 담당자, 우선순위, 스토리 포인트, 스프린트를 입력했는가?
- [ ] 레이블을 지정했는가?
- [ ] 관련 스토리 또는 작업과 연결했는가?
```

### Extra 서브 작업

```
- [ ] 본인의 [Extra] 추가 작업 아래에 생성했는가?
```
