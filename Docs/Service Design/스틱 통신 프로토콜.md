## 0. 요약

- **패킷은 최종 하드웨어(BLE) 기준이다.** 지금의 Web Serial은 같은 패킷을 실어 나르는 임시 운반 수단이고, 시리얼 전용 규칙은 3장 프레이밍뿐이다.
- 패킷 구분 방식은 **FE 구조**를 따른다: Notify 특성 1개, 첫 바이트 = 패킷 타입.
- 타격 패킷 내용은 **EMB의 20바이트 설계**를 따른다: 펌웨어가 패드를 판정해 보내고, 웹이 재판정·보정에 쓰는 근거값(각도, 확신도, 세기, 특징값)을 함께 보낸다.
- FE 현재 코드(14바이트 HIT)에서 바뀌는 부분은 6장에 모았다.

## 1. 전송 경로

| 경로 | 단계 | 패킷 경계 | 비고 |
| --- | --- | --- | --- |
| Web Serial (USB) | 지금 (STM32 + BNO055 프로토타입, 118) | 프레이밍 필요 (3장) | NUCLEO ST-Link 가상 COM. 스틱 1개 |
| Web Bluetooth (BLE GATT) | **최종** (Feather nRF52840) | Notify 1회 = 패킷 1개 | 서비스·특성 UUID는 FE 값 그대로 |
| WebSocket | 개발용 브리지 | 바이너리 프레임 1개 = 패킷 1개 | FE 구현 있음. EMB가 시리얼 ↔ `ws://localhost:8765` 중계 스크립트 제공 (1-1) |

**스틱 2개**: 스틱마다 장치 1개다. Web Serial은 스틱마다 포트 1개, BLE는 스틱마다 GATT 연결 1개. 한 장치가 두 스틱을 묶어 보내지 않는다. 어느 손인지는 flags 비트 0–1(role)로 오지만, FE는 페어링 때 사용자가 고른 손을 우선한다 (FE `BleStickSource` 현재 동작 그대로). STM32 프로토타입은 센서 1개라 스틱 1개만 지원한다.

패킷이 같으므로 **시리얼 경로 지연 − BLE 경로 지연 = 순수 BLE 비용**으로 비교할 수 있다.

### 1-1. WS 브리지 (`EMB/tools/ws_bridge.py`, S15P31A307-118 — 작업 중, 아직 저장소에 없음)

- 실행: `python ws_bridge.py COM5` · 옵션 `--baud 921600` `--port 8765` (둘 다 기본값) → 주소 `ws://localhost:8765`
- 스틱 → 브라우저: 3장 프레이밍을 벗긴 **payload만, 패킷 1개 = 바이너리 프레임 1개**
- 브라우저 → 스틱: **바이너리 프레임만** 받아 프레이밍을 씌워 시리얼로 보낸다. JSON은 받지 않는다 (FE `WebSocketStickSource`의 JSON sync·setMode는 `encodeSync` 등 바이너리로 바꿔야 함)
- CRC 오류는 브리지에서 걸러지므로, 브리지가 **1초마다 통계 프레임**을 따로 보낸다. 스틱이 아니라 브리지가 만드는 패킷이다

`0x7E BRIDGE_STATS (14바이트): [0]0x7E [1]0 [2-5]정상 프레임 u32 [6-9]CRC 오류 u32 [10-13]재동기화(SOF 재탐색) u32` — 누적값

## 2. 공통 규칙

- 바이트 순서: **리틀 엔디언**, 모든 값은 정수 고정소수점
- 모든 패킷 `[0]`은 타입. 스틱 → 브라우저 패킷은 `[1]`이 flags (역할 포함)
- 패킷 크기: **최대 20바이트** (기본 ATT MTU 23에서 쪼개지지 않는 최대 크기). SWING만 예외로 분할
- 시각: **센서 시계 µs, u32**. 약 71.6분마다 랩어라운드하므로 FE는 수신 시각 기준으로 펼친다(unwrap)
- 각도: **도 × 100, i16**. FE 제안의 pitch·yaw 정의와 같다
  - 고도각(elevation) = FE `pitch`: **스틱이 수평이면 0**, 끝이 위(+) / 아래(−). 중력 기준 절대각이라 RESET_POSE와 무관
  - 방위각(azimuth) = FE `yaw`: **RESET_POSE 시점의 방향이 0**, 위에서 봤을 때 시계 방향(오른쪽) +. 지자기를 쓰지 않으므로 시간이 지나면 밀릴 수 있고, SET_YAW_OFFSET으로 보정
  - 센서 축이 아니라 **스틱 길이 방향 벡터**의 방향이라, 스틱을 쥔 방향(롤)과 무관하다
- 길이 확장 규칙: 수신 측은 아는 길이까지만 읽고 뒤 바이트는 무시한다. 필드는 끝에만 추가한다

### flags (스틱 → 브라우저 패킷 `[1]`)

| 비트 | 의미 |
| --- | --- |
| 0–1 | 역할: 0 왼손, 1 오른손, 2 왼발, 3 오른발 (FE `stickId`는 0·1만 사용) |
| 2 | 예약 (0). v0.3까지 "예측 타격" — 116 방식은 모든 HIT가 정지 전에 판정되므로 구분이 필요 없어짐 |
| 3 | 지자기 이상 (방위각 신뢰도 낮음) |
| 4 | 판정 애매 (판정 여유가 임계값 미만) |
| 5–7 | 예약 (0) |

### 패드 번호

패드는 전체 9개: 스틱으로 치는 패드 7개(0~6) + 페달 2개(7~8). `0xFF` = 판정 없음 (어느 영역에도 안 들어감)

| ID | 패드 | 입력 | 비고 |
| --- | --- | --- | --- |
| 0 | CRASH | 스틱 | |
| 1 | HIHAT | 스틱 | |
| 2 | SNARE | 스틱 | |
| 3 | SMALL_TOM | 스틱 | v0.6까지 HI_TOM |
| 4 | MID_TOM | 스틱 | v0.7 추가 |
| 5 | FLOOR_TOM | 스틱 | v0.6까지 4 |
| 6 | RIDE | 스틱 | v0.6까지 5 |
| 7 | KICK | 페달 | v0.6까지 6 |
| 8 | HIHAT_PEDAL | 페달 | v0.7 추가 |

- 스틱 패드는 0~6에 모아 둔다. 펌웨어 패드 테이블(최대 7개)과 1:1로 맞고, `ID ≥ 7`이면 페달로 바로 구분된다
- 스틱 HIT의 `pad`와 SET_PAD_TABLE의 `pad`는 0~6만 쓴다. 페달 입력 경로(장치·패킷)는 별도로 정한다
- **단계적 연결**: 1단계는 HIHAT·SNARE·SMALL_TOM·FLOOR_TOM 4개만 패드 테이블에 넣어 쓰고, 이후 7개로 확장한다. 번호는 처음부터 위 표로 고정해 확장 시 프로토콜을 바꾸지 않는다
- FE `PadId`/`LANE_ORDER`(현재 `HI_TOM` 포함 7개)는 이 표에 맞춰 수정이 필요하다 (SMALL_TOM 이름 변경, MID_TOM·HIHAT_PEDAL 추가)

## 3. Web Serial 프레이밍 (임시 운반 계층)

```
[0] SOF  0xA5
[1] LEN  u8      payload 길이
[2..]    payload (4~5장 패킷 그대로)
[last]   CRC8    payload 기준 (다항식 0x07, 초기값 0x00)
```

- 수신: `0xA5` 찾기 → LEN만큼 수신 → CRC 일치 시 처리. 불일치면 SOF 다음 바이트부터 다시 `0xA5` 탐색
- 프로토콜 모드에서 펌웨어는 printf를 쓰지 않는다. 디버그 문자열은 LOG(0x7F)로 보낸다
- **921600 8N1** (FE 제안과 같음). HIT 프레임 23바이트 전송 약 0.25ms (115200이면 약 2ms이고, 펌웨어 4ms 샘플 주기를 침범해 연타 직후 샘플이 밀림). 디버그용 115200은 펌웨어 설정으로만 전환
- COBS(0x00 구분자) 대신 SOF + LEN + CRC8을 쓴다: FE 제안에서 허용한 대안이며, 패킷이 최대 20바이트로 짧아 인코딩 없이 길이만으로 경계를 잡는 편이 단순하다
- BLE로 넘어가면 이 장은 쓰지 않는다

## 4. 스틱 → 브라우저 패킷

| type | 이름 | 길이 | 전송 시점 |
| --- | --- | --- | --- |
| 0x01 | HIT | 20 | 타격 판정 즉시 (스틱이 멈추기 약 14ms 전(중앙값), 7장) |
| 0x02 | POSE | 13 | SET_MODE 설정 모드일 때 주기 전송 (기본 50Hz) |
| 0x03 | STATUS | 6 | 연결 직후, 이후 5초마다 |
| 0x04 | SYNC_ACK | 10 | SYNC 수신 즉시 |
| 0x05 | SWING | 가변 | 데이터 수집 모드, HIT 직후 (후순위) |
| 0x06 | PARAM_ACK | 5 | SET_PARAM 적용 후, GET_PARAMS 응답 |
| 0x7E | BRIDGE_STATS | 14 | WS 브리지가 1초마다 생성 (스틱은 보내지 않음, 1-1) |
| 0x7F | LOG | 가변 | 디버그 문자열 (개발용) |

### 0x01 HIT (20바이트)

| 바이트 | 필드 | 타입 · 단위 | 웹에서의 용도 |
| --- | --- | --- | --- |
| 0 | type | u8 = 0x01 | |
| 1 | flags | 비트 (2장) | 역할, 지자기 이상, 판정 애매 |
| 2 | seq | u8 | 유실 감지 → 텔레메트리 `packetLoss` |
| 3–6 | timestamp | u32, µs | **타격 시각 = 스틱이 멈추는(하강 속도 0) 시각의 추정값**. 판정 순간보다 미래일 수 있다. 도착 시각이 아니라 이 값으로 판정 (7장) |
| 7 | pad | u8 (0xFF 없음) | **즉시 소리 재생** |
| 8 | margin | u8, 0.1° | 1·2등 패드 거리 차 = 판정 확신도 |
| 9–10 | elevation | i16, 0.01° | 재판정, 드리프트 감지, 화면 표시 |
| 11–12 | azimuth | i16, 0.01° | 재판정, 드리프트 감지, 화면 표시 |
| 13–14 | peakSpeed | u16, °/s | 최대 하강 각속도. 세기 재계산, 코칭 |
| 15 | velocity | u8, 0~127 | 음량 (펌웨어 기본 곡선) |
| 16 | swingMs | u8, ms | 스윙 시작(하강 속도가 swingStart를 넘은 시점)부터 판정까지. 코칭, AI 특징 |
| 17–18 | lateral | i16, 0.1° | 스윙 중 좌우 이동량. AI 패드 분류 특징. 자세 추정(117) 전까지 0 |
| 19 | decel | u8, 0.1 °/s per ms | 감속률 = (최대 하강 속도 − 판정 시 속도) / 걸린 시간. 255에서 포화(25.5). 타격 품질, AI 특징 |

에어드럼은 실제 충격이 없어 가속도 피크가 세기를 잘 나타내지 못하므로, 세기는 **최대 하강 각속도**를 기준으로 한다 (공통 명세서 5장 "세기" 정의 수정 필요).

19번 바이트는 v0.3까지 가속도 감속 스파이크(×10mg)였다. 116 실측에서 타격과 비타격을 가른 값이 **자이로 감속률**(타격 5.5~12.6, 들어 올리기·천천히 내리기 0.3~1.8)이었고, 펌웨어가 판정 중에 이미 계산하며 IMU 종류와 무관하게 나오므로 이 값으로 바꾼다. 가속도 원시값은 SWING 패킷(데이터 수집 모드)에 들어 있다.

**웹이 HIT로 하는 일**

1. **즉시 반응**: `pad` + `velocity`로 바로 재생
2. **재판정**: 웹도 같은 패드 테이블을 갖고 각도로 다시 판정할 수 있다 (FE `padMapper` 그대로 사용)
3. **채보 기반 보정**: `margin`이 작거나 flags 판정 애매면, 그 시점에 채보가 기대하는 패드로 인정 (펌웨어는 채보를 모름)
4. **드리프트 감지**: 패드별 방위각 평균이 중심에서 밀리면 SET_YAW_OFFSET 전송
5. **코칭 · AI 학습**: 세기 편차, 스윙 시간, 특징값을 그대로 사용

### 0x02 POSE (13바이트)

`[0]0x02 [1]flags [2-5]ts u32 µs [6-7]elevation i16 [8-9]azimuth i16 [10-11]roll i16 [12]seq u8`

설정 모드(정면 보정, 패드 학습, 스틱 커서 표시)에서만 보낸다. roll은 FE 미사용.

- `seq`(v0.6 추가): POSE 전용 일련번호, HIT seq와 별개. 타격은 드문드문 와서 유실률을 보기 어렵고, 50Hz로 꾸준히 오는 POSE가 연결 품질(특히 BLE) 측정에 더 적합하다. 끝에 붙였으므로 12바이트만 읽는 옛 파서도 깨지지 않는다

### 0x03 STATUS (6바이트)

`[0]0x03 [1]flags [2]battery u8 % (0xFF 알 수 없음) [3]rssi i8 (시리얼은 0) [4]fwMajor [5]fwMinor`

- STM32 프로토타입: battery = 0xFF, rssi = 0
- **펌웨어 버전**: `fwMajor` = 하드웨어 세대 (0 = NUCLEO-F103RB + BNO055, 1 = Feather nRF52840 Sense), `fwMinor` = develop-EMB에 병합될 때마다 +1. 118 첫 버전이 0.1
- 병합 전 로컬 빌드는 같은 버전 번호를 쓰므로, 부팅 시 LOG로 `BOOT 0.1 a1b2c3d`(git 짧은 해시)를 한 번 보낸다. 실측 기록은 이 줄로 빌드까지 구분한다

### 0x04 SYNC_ACK (10바이트)

`[0]0x04 [1]flags [2-5]t0 u32 [6-9]t1 u32`

- t0: SYNC로 받은 브라우저 값(ms) 그대로
- t1: 펌웨어가 SYNC를 **받은 순간**의 센서 시각 (**µs**)

**시계 동기화 절차 (FE 제안 그대로)**

- 연결 직후 SYNC 5회, 이후 30초마다 2회
- 브라우저: `offset = (t0 + t2)/2 − t1`(단위를 ms로 맞춘 뒤), 왕복이 가장 짧은 샘플 채택
- 펌웨어: SYNC 수신 시각(t1)은 **수신 인터럽트에서 바로** 찍고, SYNC_ACK는 다른 송신보다 먼저 보낸다. 응답 지연 목표 1ms 이하 (118에서 실측)
- 센서 시계: 부팅 기준 µs, 단조 증가 (u32라 약 71.6분마다 랩어라운드, 2장)

### 0x05 SWING (데이터 수집 모드, 후순위)

`[0]0x05 [1]flags [2]hitSeq u8 [3]chunkIdx u8 [4]chunkCount u8 [5..]` 샘플(ax ay az gx gy gz, i16 × 6 = 12바이트) 1개씩

- 타격 직전 약 200ms. 1kHz 원시값 연속 전송은 HIT를 늦추므로 하지 않는다. 책상 데이터 수집은 USB 시리얼 우선

### 0x06 PARAM_ACK (5바이트)

`[0]0x06 [1]flags [2]paramId u8 [3-4]value i16` — 실제로 적용된 값 (범위 밖이면 잘라서 적용한 값)

- **GET_PARAMS 응답**: 파라미터마다 PARAM_ACK 1개, **id 오름차순** (0x01~0x0F, 예약 0x08 제외 14개). 마지막에 **끝 표시** `paramId = 0x00, value = 보낸 개수`. FE는 0x00을 받으면 불러오기 완료, 개수가 다르면 유실로 본다
- **적용 확인** (응답 패킷이 없는 명령용 예약 id)

| paramId | 의미 | value |
| --- | --- | --- |
| 0x00 | GET_PARAMS 끝 | 보낸 PARAM_ACK 개수 |
| 0x20 | SET_PAD_TABLE 적용됨 | 적용 후 패드 개수 (지우기 비트 패킷이면 0부터) |
| 0x21 | SET_YAW_OFFSET 적용됨 | 적용된 오프셋, 0.01° |
| 0x22 | RESET_POSE 적용됨 | 그 순간 고도각, 0.01° |

### 0x7F LOG

`[0]0x7F [1]flags [2..]` ASCII (NUL 없음, 최대 18자). 개발용

| 문자열 | 언제 |
| --- | --- |
| `BOOT 0.1 a1b2c3d` | 부팅 직후 1회 (버전 + git 짧은 해시) |
| `drop weak 342` | 스윙을 타격으로 인정하지 않았을 때. 사유 `weak`(최대 속도 미달) / `slow`(감속 느림) / `long`(스윙 너무 김) + 최대 하강 속도 °/s. **FE 모니터에서 "검출 안 된 스윙"을 보기 위한 것** (형식은 FE 제안) |
| `I2C REC 3` | IMU 버스 복구 (누적 횟수) |
| `CAL HIHAT 1/2` 등 | 보드 단독 패드 보정 진행 (개발용) |

drop은 타격 판정이 끝난 뒤(재무장 단계)에 보내므로 HIT 송신을 늦추지 않는다

## 5. 브라우저 → 스틱 명령

FE 번호(0x10~0x13)를 유지하고 뒤에 추가한다.

| type | 이름 | 형식 | 비고 |
| --- | --- | --- | --- |
| 0x10 | SYNC | `[1-4]t0 u32 ms` | FE 그대로 |
| 0x11 | SET_MODE | `[1]mode u8` | 0 연주 / 1 설정(+POSE) / 2 데이터 수집(+SWING) |
| 0x12 | HAPTIC | `[1]strength u8 [2]duration ×10ms u8` | 테스트용. **타격 진동은 펌웨어가 로컬로 즉시 트리거** (PLAY-006) |
| 0x13 | RESET_POSE | 없음 | 정면 보정: 현재 방향을 방위각 0°로. 고도각은 중력 기준이라 바뀌지 않음 |
| 0x14 | SET_PARAM | `[1]paramId u8 [2-3]value i16` | 신규. 임계값·진동·역할 |
| 0x15 | SET_PAD_TABLE | `[1]ctrl u8` + `(pad u8, elev i16, azim i16, radius u8 0.5°)` × N | 신규. 패드당 6바이트 → 패킷당 최대 3개 (20바이트). 아래 참고 |
| 0x16 | SET_YAW_OFFSET | `[1-2]offset i16 0.01°` | 신규. 웹이 감지한 드리프트 보정 |
| 0x17 | GET_PARAMS | 없음 | 신규. 모든 파라미터를 PARAM_ACK로 회신 |

### SET_PAD_TABLE 전송 규칙

```
[1] ctrl  비트 7   = 1이면 기존 테이블을 모두 지우고 시작 (첫 패킷에만)
          비트 4–6 = 예약 (0)
          비트 0–3 = 이번 패킷의 패드 수 N (1~3)
[2..]     (pad, elev, azim, radius) × N
```

- 항목마다 `pad` 번호가 있으므로 시작 인덱스는 두지 않는다. 펌웨어는 같은 `pad`면 덮어쓰고 없으면 추가한다
- 패드 7개 예: `[1]=0x83`(지우고 3개) → `[1]=0x03`(3개 추가) → `[1]=0x01`(1개 추가)
- 패드 수를 줄일 때(7개 → 4개)도 첫 패킷의 지우기 비트로 남은 항목이 정리된다
- 지우기 패킷 이후로는 순서가 바뀌거나 같은 패킷을 다시 보내도 결과가 같다

### SET_PARAM 파라미터 (초안)

| id | 이름 | 단위 | 기본값 | 용도 |
| --- | --- | --- | --- | --- |
| 0x01 | swingStart | °/s | 150 | 하강 속도가 이보다 크면(2샘플 연속) 스윙 시작 |
| 0x02 | brakeRatio | % | 30 | 속도가 최대치의 이 % 아래로 떨어지면 판정 |
| 0x03 | minPeak | °/s | 400 | 최대 하강 속도가 이보다 작으면 무시 (치는 척) |
| 0x04 | debounceMs | ms | 30 | 타격 사이 최소 간격 |
| 0x05 | hapticEnable | 0/1 | 1 | 로컬 진동 on/off |
| 0x06 | hapticStrength | 0~255 | 200 | |
| 0x07 | role | 0~3 | 0 | 왼손 / 오른손 / 왼발 / 오른발 |
| 0x08 | (예약) | | | v0.3의 predictEnable. 모든 HIT가 정지 전에 판정되므로 삭제 |
| 0x09 | poseRateHz | Hz | 50 | POSE 주기 |
| 0x0A | minDecel | 0.1 °/s per ms | 30 | 감속률이 이보다 낮으면 무시 (천천히 내리다 멈춤) |
| 0x0B | maxSwingMs | ms | 400 | 스윙 시작 후 이 시간 안에 판정 안 되면 포기 |
| 0x0C | rearmUp | °/s | 50 | 스틱이 이만큼 위로 움직이면 다음 타격 준비 |
| 0x0D | rearmIdleMs | ms | 150 | 위로 안 움직여도 판정 후 이 시간 지나면 다음 타격 준비 |
| 0x0E | tsCorrUs | µs | 3000 | 외삽한 정지 시각 보정값 (실측 평균 오차 상쇄) |
| 0x0F | velMax | °/s | 1000 | 이 최대 속도 이상이면 벨로시티 127 (minPeak → 1, 선형) |

- 기본값은 **STM32 + BNO055(250Hz) 실측 기준**이다 (EMB README 9장). 최종 IMU는 샘플링이 달라 다시 맞춘다. 형식과 id는 그대로 간다
- brakeRatio: 50%면 정지보다 약 26ms 먼저 알지만 타임스탬프 표준편차가 약 6ms, 30%면 약 14ms 먼저 · 3.4ms라서 30%를 기본으로 한다 (모두 중앙값·녹화 25회 기준)
- 펌웨어는 필요하면 내부 플래시에 저장하고, 웹은 연결할 때마다 사용자 설정을 다시 내려보낸다

## 7. 지연 · 정확도 메모

- **판정은 도착 시각이 아니라 `timestamp`로 한다.** BLE 지터가 판정 오차에 들어가지 않고, 남는 오차는 샘플링 간격 + 시계 동기화 오차뿐이다
- **`timestamp`는 판정한 샘플의 시각이 아니라 추정 정지 시각이다.** 펌웨어는 하강 속도가 최대치의 30% 아래로 떨어질 때 판정하고, 직전 두 샘플의 기울기로 속도가 0이 되는 시각을 외삽한 뒤 tsCorrUs(+3ms)를 더해 보낸다
  - 판정 시점: 실제 정지보다 중앙값 14ms 먼저 (평균 16ms, 최소 9.5ms, 최대 36ms)
  - 추정 오차: 평균 0.3ms, 표준편차 3.4ms, 최대 10.6ms (녹화 25회 재생, EMB README 9장)
  - 그래서 패킷이 도착했을 때 `timestamp`가 브라우저 시계로 아직 미래일 수 있다. FE는 이를 오류로 보지 않는다
- 소리 지연(체감)은 판정과 별개다: 센서 검출 + 전송 + 브라우저 + 오디오 출력. 정지 전 판정(중앙값 14ms)과 오디오 오프셋 보정(PLAY-004 캘리브레이션)으로 줄인다
- STM32 프로토타입(BNO055) 센서 읽기 실측은 EMB README 8장, 타격 검출 실측은 9장
