# 1. 빌드·배포 매뉴얼

GitLab에서 소스를 클론한 뒤 서비스를 빌드하고 배포하는 절차다. 구성의 기준은 `Infra/docker-compose.yml`이고, 이 문서와 다르면 코드가 맞다.

## 1.1 전체 구성

| 위치 | 하는 일 | 실행 방식 |
| --- | --- | --- |
| EC2 서버 (Ubuntu 24.04) | 웹(FE), API(BE), AI 분석 서버, DB, 스토리지, 모니터링 | Docker Compose (프로젝트 이름 `infra`) |
| GPU 서버 | 음원 분리·채보 생성, LLM 코칭 문구와 리포트 총평 | Python 워커 2개(`run`, `live-run`) + Ollama |
| 사용자 PC 브라우저 | 연주 화면, 판정, 소리 | Chrome·Edge (Web Bluetooth, Web Serial) |
| 센서 스틱·동글 | 타격 검출, 패드 판정 | Arduino 펌웨어 |

- 인터넷에서 닿는 입구는 Nginx 하나다(80, 443). DB·Redis·스토리지는 외부 포트를 열지 않는다.
- GPU 워커는 EC2의 BE에 HTTPS로 접속해 작업을 가져간다. EC2가 GPU 서버로 접속하지 않는다.
- 아키텍처 그림: [Infra/architecture.svg](../Infra/architecture.svg)

## 1.3 EC2 서버 최초 준비

비어 있는 Ubuntu 서버 기준이다. 한 번만 한다.

1. Docker와 복사 도구를 설치한다. Docker 공식 문서의 Ubuntu 설치 절차(`docker-ce`, `docker-compose-plugin`)를 따른 뒤:
   ```bash
   sudo systemctl enable --now docker
   sudo apt-get install -y rsync
   ```
2. 방화벽을 연다. SSH를 먼저 허용해야 접속이 끊기지 않는다. 클라우드 보안 그룹에서도 22, 80, 443을 연다.
   ```bash
   sudo ufw allow 22/tcp
   sudo ufw allow 80/tcp
   sudo ufw allow 443/tcp
   sudo ufw enable
   ```
3. 배포 폴더를 만든다.
   ```bash
   sudo mkdir -p /srv/airdrum/Infra
   sudo chown -R gitlab-runner:gitlab-runner /srv/airdrum
   ```
4. 서버 설정 파일 `/srv/airdrum/Infra/.env`를 만든다. `Infra/.env.example`을 복사해 값을 채우고 권한을 600으로 둔다(1.4절).
5. GitLab 배포 러너(`ec2-deploy`, shell executor, 태그 `deploy`, Protected)를 등록하고 docker 그룹에 넣는다. 절차는 [Infra/deploy/README.md](../Infra/deploy/README.md) "서버 최초 준비".
6. HTTPS 인증서를 먼저 발급한다. 인증서 없이 443 설정을 배포하면 Nginx가 시작하지 못한다. 절차는 [Infra/PORTING.md](../Infra/PORTING.md) 5절.

## 1.5 빌드와 배포

### EC2 (GitLab CI/CD)

1. 코드는 `feat/*` → `develop-*` → 금요일 `[DEPLOY]` MR → `main` 순으로 들어간다.
2. `main` 파이프라인에서 CI가 통과하면 `deploy` 잡을 사람이 직접 실행한다.
3. 러너가 `Infra/deploy/deploy.sh`로 소스를 `/srv/airdrum`에 복사하고 다음을 실행한다.
   ```bash
   docker compose -p infra up -d --build
   ```
   이미지 레지스트리가 없어 서버에서 BE·FE·AI 이미지를 직접 빌드한다(처음 10분 안팎, 이후 3~5분).
4. `api`, `web`, `ai-api`가 `healthy`이고 `/health`가 `ok`가 될 때까지 최대 300초 기다린다. 성공하면 `/srv/airdrum/.deployed`에 커밋을 기록한다.
5. 문제가 있으면 `rollback` 잡으로 이전 커밋을 다시 배포한다.

수동 배포(비상): 서버에서 `Infra/deploy/deploy.sh <커밋> <소스 폴더>`를 러너 사용자로 실행한다.

배포 확인:
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://k15a307.p.ssafy.io/health   # 200
docker compose -p infra ps                                                  # healthy
```

### GPU 서버 (워커)

```bash
cd ~/ssaplash/S15P31A307/AI && git fetch origin main && git checkout --detach origin/main
uv sync --extra models --extra transcribers --extra music-check
uv pip install --reinstall "torch==2.8.0" "torchaudio==2.8.0" --index-url https://download.pytorch.org/whl/cu128
chmod 600 ~/ssaplash/worker.env && set -a && source ~/ssaplash/worker.env && set +a

```

실행 순서: Ollama → 모델 올리기 → 채보·총평 워커(`run`) → 연주 코칭 워커(`live-run`).

```bash
# Ollama (GPU 서버를 여러 팀이 같이 써서 기본 포트 11434가 아닌 11435를 쓴다)
CUDA_VISIBLE_DEVICES=<GPU 번호> OLLAMA_VULKAN=0 OLLAMA_CONTEXT_LENGTH=4096 OLLAMA_KEEP_ALIVE=-1 \
OLLAMA_HOST=127.0.0.1:11435 OLLAMA_MODELS=$HOME/ollama-models OLLAMA_LLM_LIBRARY=cuda_v12 OLLAMA_NO_CLOUD=1 \
setsid nohup ~/ollama/bin/ollama serve >> ~/ssaplash/results/ollama.log 2>&1 < /dev/null &
OLLAMA_HOST=127.0.0.1:11435 ~/ollama/bin/ollama pull gemma3:12b
curl -s http://127.0.0.1:11435/api/generate -d '{"model":"gemma3:12b","keep_alive":-1,"options":{"num_ctx":4096}}' >/dev/null

# 워커
cd ~/ssaplash/S15P31A307/AI && set -a && source ~/ssaplash/worker.env && set +a
setsid nohup taskset -c 0-127 uv run --no-sync ssaplash-worker run >> ~/ssaplash/results/worker.log 2>&1 < /dev/null &
setsid nohup uv run --no-sync ssaplash-worker live-run >> ~/ssaplash/results/live-worker.log 2>&1 < /dev/null &
```

채보 모델 가중치(`strum`)는 저장소에 없다. 학습한 파일을 `AI/data/models/strum_ft/songsterr_egmd/best.pt`에 둔다([AI/README.md](../AI/README.md) "GPU 서버에서 띄우기").

## 1.6 배포 시 특이사항

- **HTTPS 인증서를 먼저 발급한다.** Nginx 443 설정이 인증서 파일을 가리켜서, 인증서가 없으면 Nginx가 시작하지 못하고 서비스 전체가 내려간다.
- **`.env`는 배포가 덮어쓰지 않는다.** 값을 바꾸면 `deploy` 잡을 다시 실행하거나 서버에서 `docker compose -p infra up -d`로 반영한다.
- **`JWT_SECRET`, `POSTGRES_PASSWORD`는 바꾸지 않는다.** 바꾸면 로그인 토큰이 모두 무효가 되거나 기존 DB에 접속하지 못한다.
- **DB 마이그레이션은 롤백되지 않는다.** BE가 시작할 때 Flyway가 `BE/src/main/resources/db/migration/`을 적용한다. 롤백 전에 되돌릴 구간에 새 마이그레이션이 있는지 확인한다.
- **기본 곡과 레슨은 BE가 시작할 때 자동으로 등록한다**(`BuiltinSongSeeder`, `BE/src/main/resources/builtin-songs/`).
- **GPU 워커는 BE의 `/internal/` 경로를 쓴다.** Nginx가 이 경로를 GPU 서버 공인 IP에만 허용하므로(`Infra/nginx/default.conf`의 `allow`), GPU 서버를 옮기면 허용 목록을 고친다.
- **브라우저는 Chrome 또는 Edge를 쓴다.** 스틱 연결에 Web Bluetooth와 Web Serial이 필요하다.
- Grafana(3000)와 MLflow(5000)는 서버의 127.0.0.1에만 열려 있어 SSH 터널로 접속한다([Infra/ACCESS.md](../Infra/ACCESS.md)).
- 서버에서 `docker volume prune`, `docker system prune --volumes`, `docker compose down -v`를 실행하지 않는다. 데이터 볼륨이 지워진다.

## 1.7 계정과 프로퍼티가 정의된 파일 목록

값은 저장소에 없고 서버에만 있다. 저장소에는 이름과 설명만 있는 예시 파일이 있다.

| 파일 | 위치 | 내용 |
| --- | --- | --- |
| `Infra/.env` | EC2 `/srv/airdrum/Infra/.env` (저장소 X, 예시 `Infra/.env.example`) | DB·Redis 비밀번호, JWT 키, 소셜 로그인 키, 스토리지 키, 워커 토큰, 기능 스위치 |
| `Infra/docker-compose.yml` | 저장소 | 서비스 구성, `.env` 값을 각 컨테이너 환경변수로 전달 |
| `BE/src/main/resources/application.yaml` | 저장소 | BE 설정. DB 접속(`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`) 등은 환경변수로 받음 |
| `BE/src/main/resources/db/migration/` | 저장소 | Flyway 마이그레이션(스키마, ERD의 원본) |
| `BE/.env` | 로컬 개발 PC (저장소 X, 예시 `BE/.env.example`) | 로컬 BE 실행용 DB 비밀번호, JWT 키, 소셜 로그인 키 |
| `FE/.env` | 로컬 개발 PC (저장소 X, 예시 `FE/.env.example`) | FE 빌드 변수 |
| `worker.env` | GPU 서버 `~/ssaplash/worker.env` (저장소 X) | 워커 ID·토큰, 모델 설정 |
| `AI/configs/chart/*.yaml` | 저장소 | 분리·채보 모델 설정 |
| `Infra/nginx/` | 저장소 | Nginx 설정(도메인, 내부 경로 허용 IP) |

주요 DB 계정:

| 계정 | 용도 | 권한 |
| --- | --- | --- |
| `POSTGRES_USER` (예시 `app`) | BE 앱 | 앱 DB 전체 |
| `MIDI_WORKER_DB_USERNAME` | MIDI 워커 | 최소 권한 |
| `coach_export` | 약점 기준 보정 배치 | 비식별 뷰 읽기 전용 |
| `recommend_export` | 곡 추천 후보 배치 | 가명 뷰 읽기 전용 |
