# 서버 접속 가이드와 키·시크릿 보관 규칙

배포 서버(EC2)에 접속하는 방법과, 키·비밀값을 다루는 규칙이다. 점검 기록은 `Infra/SECURITY.md`에 있다.

> 초안이다. 3절의 "사람마다 키를 따로 등록" 방식은 제안이며 아직 적용하지 않았다.

## 1. 서버에 접속해야 하는 경우

| 하는 일 | 서버 접속 필요 |
| --- | --- |
| 코드 배포 | 필요 없음. GitLab에서 `main` 파이프라인의 `deploy` 잡을 수동 실행한다 |
| API 확인 | 필요 없음. 브라우저나 `curl`로 도메인을 호출한다 |
| 로그·지표 확인(Grafana) | SSH 터널이 필요하다(2절) |
| MLflow 확인 | SSH 터널이 필요하다(2절) |
| 서버 상태 점검, `.env` 변경, 장애 대응 | 인프라 담당만 직접 접속한다 |

서버에 직접 접속하는 일은 최소로 한다. 접속하지 않아도 되는 일은 GitLab 배포나 터널로 처리한다.

## 2. 접속 방법

- 서버 주소: `k15a307.p.ssafy.io`, 계정: `ubuntu`
- 인증: **키 파일만 허용**한다. 비밀번호 로그인은 꺼져 있다. root 로그인은 쓰지 않는다.

```bash
ssh -i <키 파일 경로> ubuntu@k15a307.p.ssafy.io
```

**Grafana·MLflow는 서버에 직접 공개하지 않는다.** 내 PC의 포트를 서버의 `127.0.0.1`에 연결하는 SSH 터널로 본다.

```bash
# Grafana(3000), MLflow(5000)를 내 PC의 같은 포트로 연결한다. 이 창을 열어 둔 동안만 접속된다.
ssh -i <키 파일 경로> -L 3000:localhost:3000 -L 5000:localhost:5000 ubuntu@k15a307.p.ssafy.io
```

터널을 연 상태에서 브라우저로 `http://localhost:3000`(Grafana), `http://localhost:5000`(MLflow)을 연다.

### 키 파일 권한(Windows)
키 파일은 소유자만 읽을 수 있어야 한다. 다른 사용자가 읽을 수 있으면 SSH가 접속을 거부한다.

```
icacls "<키 파일 경로>" /inheritance:r
icacls "<키 파일 경로>" /grant:r "%USERNAME%:R"
```

## 3. 키 발급과 관리

### 현재 방식
서버를 만들 때 받은 키 한 쌍을 담당자가 보관한다. 키 한 쌍을 여럿이 나눠 쓰면 서버 로그에서 **누가 접속했는지 구분할 수 없다.** 한 명이 키를 잃어버리면 모두의 키를 바꿔야 한다.

### 제안: 사람마다 키를 따로 등록
서버 접속이 필요한 팀원은 자기 PC에서 키를 만들고, **공개 키(`.pub`)만** 인프라 담당에게 전달한다. 개인 키(확장자 없는 파일)는 PC 밖으로 보내지 않는다.

팀원(자기 PC):
```bash
ssh-keygen -t ed25519 -C "<이름>"
```
- 키 두 개가 만들어진다. `id_ed25519`(개인 키, 보관)와 `id_ed25519.pub`(공개 키, 전달).
- 암호(passphrase)를 지정하면 PC를 잃어버려도 키를 바로 쓰지 못한다.

인프라 담당(서버에서):
```bash
# 받은 공개 키 한 줄을 접속 허용 목록에 추가한다. 줄 끝에 이름이 들어 있어 나중에 구분된다.
echo "<받은 공개 키 한 줄>" >> ~/.ssh/authorized_keys
```
- 추가한 키로 접속이 되는지 새 창에서 확인한다.

접속이 필요 없어진 팀원은 `~/.ssh/authorized_keys`에서 그 사람의 줄을 지운다. 이 방식이면 한 사람을 빼도 다른 사람의 키를 바꿀 필요가 없다.

### 서버 안에서 자동으로 도는 작업용 키 (MLflow 터널 전용)

GPU 서버의 평가 스크립트처럼 **사람이 없이 MLflow(`localhost:5000`)에 기록해야 하는** 작업은 그 서버에서 터널 전용 키를 따로 만든다. 사람 키와 섞지 않는다.

서버(GPU 서버)에서 키를 만든다. 자동으로 쓰므로 암호는 비우고 대신 아래 제한으로 막는다.
```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/mlflow_tunnel -C "<용도>-mlflow-tunnel"
chmod 600 ~/.ssh/mlflow_tunnel
```
배포 서버(EC2)의 `~/.ssh/authorized_keys`에는 공개 키 앞에 **네 가지 옵션을 모두** 붙여 추가한다.
```text
command="/usr/sbin/nologin",restrict,port-forwarding,permitopen="localhost:5000" ssh-ed25519 AAAA… <용도>-mlflow-tunnel
```
| 옵션 | 하는 일 |
| --- | --- |
| `command="/usr/sbin/nologin"` | 어떤 명령을 요청해도 로그인 거부만 실행된다. **명령 실행을 막는 것은 이 옵션 하나다** |
| `restrict` | 터미널 할당·에이전트 전달·X11 등을 끈다 |
| `port-forwarding` | 포워딩을 다시 허용한다(`restrict`가 끈 것) |
| `permitopen="localhost:5000"` | 그 포트로 가는 포워딩만 허용한다 |

- **`restrict`와 `permitopen`만으로는 명령 실행이 막히지 않는다.** `command=`가 빠지면 이 키로 EC2에서 `ubuntu`로 명령을 실행할 수 있다. 2026-11-04에 이 옵션을 빼고 등록했다가 시험에서 발견해 고쳤다.
- **등록한 뒤 반드시 시험한다.** 키를 가진 서버에서 아래를 실행해 아무것도 실행되지 않아야 한다(`This account is currently not available.`가 나오면 정상).
```bash
ssh -i ~/.ssh/mlflow_tunnel -o BatchMode=yes ubuntu@<배포 서버 주소> "echo 실행됨"
```
- 터널은 명령 없이 연다: `ssh -i ~/.ssh/mlflow_tunnel -N -L 127.0.0.1:<빈 포트>:localhost:5000 -o ExitOnForwardFailure=yes ubuntu@<배포 서버 주소>`
- **공용 서버에서는 로컬 포트가 다른 사람과 겹칠 수 있다.** 5000, 15001처럼 이미 쓰는 포트에 연결하면 엉뚱한 서비스에 닿는다. 터널을 열기 전에 `ss -ltn | grep ':<포트> '`로 비어 있는지 보고, 열고 나서 `curl http://127.0.0.1:<포트>/health`가 `200`인지 확인한 뒤 기록한다.
- 개인 키 파일은 서버 밖으로 옮기거나 붙여 넣지 않는다. 필요 없어지면 EC2의 줄과 서버의 파일을 함께 지운다.
- 기록 방법: `uv run python scripts/eval_narrative.py … --mlflow --tracking-uri http://127.0.0.1:<포트>`

### 키를 잃어버렸거나 노출됐을 때
1. 서버의 `~/.ssh/authorized_keys`에서 해당 키의 줄을 **즉시 삭제**한다.
2. 새 키를 만들어 등록한다.
3. 서버 접속 기록(`last`, `journalctl -u ssh`)에서 의심스러운 접속이 있는지 본다.

## 4. 키·비밀값 보관 규칙

**하지 않는다**
- 저장소, 이슈, MR, 채팅, 메일에 키 파일(`.pem`, 개인 키)이나 비밀번호·토큰을 올리지 않는다. 이미 올렸다면 **값을 교체**한다(삭제만으로는 부족하다).
- 서버 터미널 출력(`gitlab-runner list` 등)에 토큰이 섞여 있을 수 있다. 출력 내용을 붙여넣기 전에 비밀값이 있는지 본다.
- 서버에서 `docker volume prune`, `docker system prune --volumes`를 실행하지 않는다(데이터·인증서 볼륨이 삭제된다).

**한다**
- 서버의 비밀값은 `/srv/airdrum/Infra/.env`에만 둔다(권한 600). 값은 서버에서 직접 만든다(`openssl rand -hex`). 만든 값을 화면이나 채팅에 출력하지 않는다.
- 값이 들어 있는지는 값이 아니라 **변수 이름이나 개수**로 확인한다.
- 키 파일은 본인 PC의 전용 폴더에 두고 권한을 제한한다. 클라우드 동기화 폴더나 공유 폴더에 두지 않는다.
- 비밀값이 노출됐다면 사고 범위를 따지기 전에 **먼저 교체**한다.

## 5. 서버를 바꾸는 작업의 안전 규칙
- SSH나 방화벽(`ufw`) 설정을 바꿀 때는 **SSH 창을 하나 더 열어 두고** 한다. 설정이 틀리면 열어 둔 창으로 되돌린다.
- SSH 설정은 적용 전에 `sudo sshd -t`로 문법을 검사하고, 적용 후 새 창으로 접속해 확인한 뒤에 기존 창을 닫는다.
- 재부팅이 필요한 보안 패치가 있는지 주 1회 `ls /var/run/reboot-required`로 확인한다. 재부팅은 CI·배포가 없을 때 한다(컨테이너는 자동으로 다시 올라온다).
