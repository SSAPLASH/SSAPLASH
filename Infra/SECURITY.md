# 인프라 보안 점검 기록

서버·컨테이너·CI에서 **보안 관점으로 확인하고 결정한 것**을 모은다. 새로 점검하거나 결정할 때마다 항목을 추가한다. 문제를 겪은 사례는 `Infra/TROUBLESHOOTING.md`에, 여기에는 점검 기준과 결과를 둔다.

- 상태 표기: **확인함**(직접 시험·검증), **설계 반영**(코드·설정에 반영, 서버 시험은 별도), **원리 정리**(원리는 이해했고 서버에서 직접 확인은 전), **미확인**(아직 점검 전)
- 비밀값(토큰, 키, 비밀번호)은 적지 않는다.

## 2. 네트워크

### 2.1 외부에 닿는 포트는 최소로
- **원칙:** 인터넷에서 직접 닿는 입구는 Nginx(80, 곧 443) 하나로 하고, 나머지는 열지 않는다.
- **적용:** DB·Redis·SeaweedFS·Prometheus·Loki는 `ports:`로 공개하지 않고 내부 네트워크(`internal: true`)에만 둔다. Grafana(3000)와 MLflow(5000)는 `127.0.0.1`로만 공개하고 팀원은 SSH 터널로 접속한다.
- **확인 방법:** `docker compose config`의 `ports` 항목(공개된 포트 목록)을 본다. 서버 밖에서 실제로 닿는 포트는 별도로 스캔한다(미확인, 2.3).
- **이유:** 서비스가 하나 늘 때마다 공격 면이 늘어난다. 입구를 하나로 두면 점검·로그·인증서 관리가 한곳에 모인다.

### 2.2 방화벽은 두 겹이다
```
인터넷 → [① AWS 보안 그룹] → [② 서버 안 ufw] → Docker / Nginx
```
| 계층 | 누가 바꾸나 | 확인 방법 |
| --- | --- | --- |
| ① AWS 보안 그룹(클라우드 쪽) | AWS 콘솔 권한이 있어야 함(우리는 없음) | **바깥에서 포트 연결 시험** |
| ② ufw(서버 안) | 서버에서 `sudo ufw ...` | `sudo ufw status` |

- **확인함:** 443번이 바깥에서 닿는지를 콘솔 없이 시험했다. 서버에서 `ufw allow 443/tcp` 후 **빈 폴더에서** 임시 서버(`python3 -m http.server 443`)를 띄우고, 내 PC에서 `Test-NetConnection 서버 -Port 443`을 실행해 `TcpTestSucceeded : True`를 확인했다. → 보안 그룹이 443을 허용한다. 시험 후 서버를 종료하고 폴더를 삭제했다.
- **교훈:** 권한이 없어 설정을 못 봐도, **결과(실제로 닿는가)** 를 시험하면 상태를 알 수 있다.

### 2.3 Docker가 공개한 포트는 ufw를 우회한다
- **원리 정리:** Docker가 `ports:`로 포트를 공개하면 PREROUTING에서 목적지를 컨테이너 IP로 바꾼다(DNAT). 그러면 패킷이 "서버 자신"이 아니라 "다른 곳"으로 판정되어 INPUT이 아니라 **FORWARD 체인**을 지난다. ufw의 허용·차단은 주로 INPUT 체인에 걸려 있어서, 컨테이너로 가는 패킷에는 적용되지 않는다. FORWARD에는 Docker가 공개 포트를 허용하는 규칙을 먼저 넣어 둔다.
- **결과:** ufw에서 막아도 `ports:`로 공개한 컨테이너 포트는 열린다. 예를 들어 DB를 실수로 `ports: "5432:5432"`로 공개하면 ufw가 있어도 인터넷에 노출된다. 반대로 ufw에서 80을 허용하지 않아도 Docker로 공개한 Nginx 80은 열린다(정확한 확인은 시험이 필요함).
- **대응:** (1) DB·Redis·스토리지는 `ports:`를 쓰지 않는다. (2) 서버 안에서만 쓸 포트는 `127.0.0.1:포트:포트`로 공개한다. (3) 필요하면 `DOCKER-USER` 체인에 차단 규칙을 둔다.
- **서버에서 확인한 결과(2026-10-25, 읽기 전용 명령):**
  - `sudo ufw status verbose`: active, 기본 `deny (incoming)`·`deny (routed)`, 허용은 22, 80/tcp, 443/tcp(IPv4·IPv6).
  - `sudo iptables -t nat -L DOCKER -n`: DNAT 규칙이 `tcp dpt:80 → 172.19.0.2:80` 하나뿐이다. Docker가 공개한 포트는 80뿐이다.
  - `sudo iptables -L FORWARD -n --line-numbers`: 정책 DROP, 순서가 `DOCKER-USER`(1) → `DOCKER-FORWARD`(2) → `ufw-*`(3 이하)다. Docker 체인이 ufw보다 앞에 있다.
  - `sudo iptables -L DOCKER-USER -n`: **비어 있다.** 누가 실수로 `ports:`를 추가해도 막아 줄 규칙이 없다.
  - `docker ps`: 컨테이너 5개(api, nginx, seaweedfs, postgres, redis). 호스트에 공개된 것(`->` 표시)은 nginx의 80뿐이다. 나머지는 컨테이너 내부 포트만 열려 있다.
  - 모니터링·MLflow 컨테이너는 없다(서버에 아직 배포되지 않음).
- **바깥(내 PC)에서 접속 시험(2026-10-25, 공개 IP, 13개 포트, 4초 대기):** 22·80 열림. 443은 연결 거부(보안 그룹·ufw는 통과, 듣는 프로그램이 없어서 정상). 3000, 3100, 5000, 5432, 6379, 8080, 8333, 8888, 9090, 9333은 응답 없음(차단). 서버 안의 `ss`·`iptables` 결과와 일치한다. 한계: 흔한 포트만 본 것이고 전체 포트 스캔이 아니며, 응답 없음만으로는 보안 그룹과 ufw 중 어느 쪽이 막았는지 구분하지 못한다.
- **아직 안 한 것:** ufw 규칙을 지워도 Docker가 연 80이 계속 열리는지 직접 시험(우회 동작 확인), `DOCKER-USER`에 보호 규칙 추가 검토.
- **외부 전체 포트 검사(2026-10-26, 내 PC → 공개 IP, 1~65535번 전체):** **22(ssh) 열림, 80(http) 열림, 443 닫힘(연결 거부: 서버까지 닿았고 듣는 프로그램이 없음), 나머지 65532개는 응답 없음(차단).** 서버 안의 `ss`·`iptables` 결과와 일치한다. 예상 밖의 열린 포트는 없다.
  - 방법: `nmap`을 먼저 시도했으나 이 PC에서 Windows 네트워크 오류(`10014`)가 계속 나서 전체 결과를 쓸 수 없었다(`Infra/TROUBLESHOOTING.md` H6). 대신 PowerShell(.NET 소켓 접속 시험)로 250개씩 끊어 접속하고, 오류가 난 포트(구간마다 약 300개)는 20개씩 다시 검사해 끝내 오류가 남은 포트가 0개임을 확인했다. 구간 합계가 65535개와 맞는다.
  - 한계: 접속(TCP connect) 시험이라 UDP는 보지 않았고, "응답 없음"은 방화벽 차단과 서버가 응답을 버리는 경우를 구분하지 못한다. `nmap`으로 같은 확인을 다른 PC·네트워크에서 다시 하는 것은 선택 과제다.
- **점검 기준:** ufw 규칙이 아니라 **바깥에서 실제로 닿는 포트**로 점검한다(외부 스캔, `ss -tlnp`, 위 DNAT 규칙).

### 2.4 임시 포트 시험 때의 위험
- `python3 -m http.server`는 **현재 폴더의 모든 파일을 공개**한다. 홈 폴더에서 실행하면 `.ssh` 같은 중요한 파일이 노출될 수 있다. 반드시 빈 임시 폴더에서 실행하고 끝나면 종료한다.
- 시험용으로 연 포트·프로세스는 끝나면 닫는다(방화벽 규칙은 필요한 것만 남긴다).

## 3. 시크릿(비밀값) 관리

### 3.1 저장 위치와 누락 시 동작
- 비밀번호·키·토큰은 **서버의 `Infra/.env`에만** 둔다(권한 `600`, Git 무시). 저장소에는 값이 빈 `.env.example`만 둔다.
- 필수 값은 Compose에서 `${변수:?메시지}`로 지정해, **비어 있으면 실행 자체를 중단**한다(빈 비밀번호로 서비스가 뜨는 일을 막음). 단점: `docker compose down`도 변수가 없으면 중단된다.
- 서버 배포가 `.env`를 덮어쓰거나 지우지 않는다(`rsync --exclude .env`).

### 3.2 비밀값을 보지 않고 만들기
- 서버에서 `openssl rand -hex`로 만든 값을 `sed`/`tee`로 **`.env`에 직접 쓴다.** 값이 화면과 채팅에 출력되지 않는다. 확인은 값이 아니라 **개수**(`grep -c`)로 한다.
- 비밀번호에 `$`, `#`, `%`, `@`, `/`, `:` 같은 문자가 있으면 설정 파일·접속 주소가 깨질 수 있어 영문·숫자(hex)를 쓴다.

### 3.3 토큰 노출 사고
- `gitlab-runner list`가 러너 인증 토큰을 그대로 출력하는 것을 모르고 결과를 공유했다.
- 대응: 러너를 삭제하고 새로 만들어 토큰을 교체했다. 이후 상태 확인은 `systemctl status`로 한다.
- **원칙:** 도구가 비밀값을 출력하는지 모르면 출력 전에 확인한다. 노출됐다면 값을 **폐기(교체)** 한다. 노출 범위가 작아 보여도 교체가 가장 빠르다.

### 3.4 명령줄 인자로 넘긴 비밀번호는 `docker top`에 그대로 보인다 (2026-10-27)
- **발견:** MLflow의 재시작 반복 원인을 `docker top infra-mlflow-1`로 보다가, 출력에 DB 접속 주소의 **비밀번호가 평문으로** 나왔다. `mlflow server --backend-store-uri postgresql://사용자:비밀번호@…`처럼 비밀번호가 포함된 주소를 **명령줄 인자**로 넘겼기 때문이다. 명령줄은 `docker top`, `ps`로 서버에 들어온 사람이 읽을 수 있다.
- **2차 노출:** 이 출력을 진단 도구 결과로 채팅에 붙여 넣어 비밀번호가 **대화 기록에도 남았다.** 3.3의 러너 토큰 사고와 같은 모양이다("도구가 비밀값을 출력하는지 모르고 결과를 공유").
- **위험 평가:** PostgreSQL은 내부 네트워크에만 열려 있고 호스트 포트가 없어서, 비밀번호만으로 바깥에서 접속할 수는 없다. 그래서 즉시 악용 가능성은 낮다고 판단했다. 다만 서버 안에서 프로세스를 볼 수 있는 사람(docker 그룹, 4.4)에게는 열린 값이다.
- **조치(설계 반영):** DB 주소를 명령줄에서 빼고 `MLFLOW_BACKEND_STORE_URI` 환경변수로 넘기게 `Infra/docker-compose.yml`을 고쳤다. `mlflow server --help`에는 환경변수 표기가 없어서 지원 여부를 알 수 없었고, MLflow 소스(`cli/__init__.py`의 `envvar="MLFLOW_BACKEND_STORE_URI"`)로 이 옵션이 환경변수를 읽는 것을 확인했다.
- **서버 확인(2026-10-27):** 서버에 적용하고 `healthy`, 재시작 0회를 확인했다. `docker top infra-mlflow-1 -eo pid,args`에서 `postgresql://`이 든 명령줄이 0개다. 컨테이너 환경변수는 `postgresql`로 시작하고(비밀번호는 출력하지 않고 앞부분만 확인), `mlflow` DB에 MLflow 테이블이 있어 파일 저장소로 떨어지지 않았다.
- **시험 실수(기록):** 처음 `docker top -eo args`는 `Couldn't find PID field` 오류를 냈는데, 오류를 `grep -c`가 빈 입력으로 받아 `0`이 나왔다. 오류 때문에 나온 `0`이어서 유효한 시험이 아니었고, `-eo pid,args`로 다시 해서 확인했다. **명령이 실패했는지 먼저 본 뒤 결과를 믿는다.**
- **한계(솔직하게):** 환경변수로 옮겨도 `docker inspect`(컨테이너 환경)에서는 값이 보인다. 줄어드는 것은 `docker top`/`ps`처럼 흔히 쓰고 공유하기 쉬운 출력에서의 노출이다. docker 그룹은 이미 사실상 root라서(4.4) 그 사용자에게서 값을 완전히 숨길 수는 없다. 근본 대책은 비밀 관리 도구 또는 파일 기반 비밀(Docker secrets) 도입이며 후속 과제로 둔다.
- **같은 문제가 있던 곳(Redis, 조치함):** Redis는 `redis-server --requirepass ${REDIS_PASSWORD}`로 비밀번호를 넘겼다. Compose가 변수를 치환해 컨테이너 설정(`Cmd`)에 비밀번호가 글자 그대로 들어가고, 헬스체크의 `redis-cli -a 비밀번호`도 실행되는 동안 명령줄에 남는다. 조치: 비밀번호를 설정 파일(`/tmp/redis.conf`, 권한 600, 소유자 `redis`)에 쓰고 명령줄에는 파일 경로만 넘긴다. 헬스체크는 `-a` 대신 환경변수 `REDISCLI_AUTH`를 쓴다. 이미지의 시작 스크립트(`docker-entrypoint.sh`)를 거쳐야 root에서 `redis` 사용자로 내려가므로 `exec docker-entrypoint.sh`로 호출한다.
  - **서버 시험(2026-10-27, 가짜 비밀번호의 임시 컨테이너, 운영 Redis는 건드리지 않음):** 환경변수 인증 `PONG`, 인증 없이는 `NOAUTH`, 설정 파일 `-rw-------`·소유자 `redis`, 프로세스 사용자는 root가 아님(호스트에서 uid 999로 표시). 운영 반영은 다음 배포에서 하고 반영 뒤 BE 연결 복구를 확인한다.
  - **정정(내가 먼저 짚은 가설이 시험으로 틀린 부분):** 처음에는 예전 방식이 `docker top`에 비밀번호를 보였을 것이라 생각했지만, Redis가 시작 뒤 자기 프로세스 이름을 `redis-server *:6379`로 바꿔서 `docker top`에는 인자가 나오지 않는다. 실제 노출 경로는 `docker inspect`·`docker compose config`의 `Cmd`와 헬스체크 실행 중의 명령줄이었다. 환경변수로 넘기는 값은 `docker inspect`의 환경 항목에서 여전히 보인다(한계, 위와 같음).
- **비밀번호 교체 여부:** 노출된 값이라 교체가 가장 안전하다. 같은 DB를 쓰는 BE 등의 설정과 배포 순서를 함께 맞춰야 해서 담당자가 일정을 정해 결정한다. 교체하면 이 항목에 날짜를 적는다.
- **원칙:** (1) 비밀번호가 포함된 주소·옵션을 명령줄에 두지 않는다. (2) 진단 출력(`docker top`, `docker inspect`, `ps`, `env`)은 비밀값이 섞일 수 있으니 **붙여 넣기 전에 훑는다.** (3) 노출됐으면 범위를 따지기 전에 교체를 먼저 검토한다.

### 3.5 키 파일
- SSH 키(`.pem`)는 소유자만 읽도록 권한을 제한한다(Windows는 `icacls`). 다른 사용자가 읽을 수 있으면 접속이 거부된다.
- 저장소·채팅·문서에 키를 올리지 않는다. 팀원 접속 키는 메신저로 주고받지 않는다.

## 4. 권한(최소 권한)

### 4.1 읽기 전용 마운트
- 인증서·모델 볼륨은 Nginx에 `:ro`로 연결한다. 호스트 파일 시스템을 읽는 `node-exporter`·`cadvisor`·`alloy`도 읽기 전용으로 마운트한다. 쓰기는 필요한 한 곳에만 둔다(인증서는 certbot만, 모델은 게시 도구만).
- **이유:** 서비스가 뚫려도 개인 키나 호스트 파일을 바꾸지 못하게 한다.

### 4.2 스토리지 키 분리
- 읽기용(reader)은 악보·반주 버킷 읽기만, 쓰기용(writer)은 서버 내부 적재·플레이 원본·임시 음원에 쓴다.
- **확인함:** 읽기 키로 악보·반주는 읽히고, 쓰기와 다른 버킷 접근은 거부된다(`Infra/README.md` 서버 시험 표). 읽기 키로 서명한 PUT URL의 동작은 기록이 없어 **미확인**이다.
- **이유:** 서명 URL은 서명한 키의 권한을 따른다. 사용자에게 나가는 URL을 만드는 키는 가장 작은 권한이어야 한다.

### 4.3 Docker 소켓은 서버 전체 권한이다
- 로그를 서비스 이름으로 구분하려고 `alloy`에 Docker 소켓을 마운트했다. 소켓은 **읽기 전용(`:ro`)으로 마운트해도 Docker API 호출은 막히지 않는다.** 소켓에 접근하는 프로세스는 컨테이너를 만들어 호스트를 장악할 수 있다.
- 완화: 포트를 열지 않고 내부 네트워크에만 둔다, 이미지 버전을 고정한다, 다른 서비스에는 소켓을 마운트하지 않는다, 위험을 README에 기록한다.
- **교훈:** 편의 기능(서비스 이름 라벨)과 위험(서버 전체 권한)을 비교해, 위험을 인정하고 완화책과 함께 선택했다. 더 안전한 대안(로그 파일 직접 읽기)은 완료 기준을 못 채워 택하지 않았다.

### 4.4 `docker` 그룹은 사실상 root
- 배포 러너(`gitlab-runner` 사용자)를 `docker` 그룹에 넣으면 그 사용자는 서버 root와 같은 일을 할 수 있다. 그래서 배포 러너는 **보호된(protected) 러너**로 두고 `main`의 잡만 받게 한다.

## 5. CI·배포

- **배포는 수동 승인**: `main` 파이프라인의 `deploy` 잡을 사람이 직접 실행해야 서버가 바뀐다. 병합이 곧 배포가 되지 않는다.
- **일반 CI와 배포를 분리**: 테스트·빌드는 격리된 Docker 컨테이너에서(`ec2-docker`), 서버를 바꾸는 배포는 별도 보호 러너(`ec2-deploy`)에서 한다.
- **서버 접속 키를 CI에 두지 않음**: 러너와 서버가 같은 머신이라 SSH 키 없이 서버 안에서 실행한다. CI 변수에 올리는 비밀이 없다.
- **저장소 접근은 읽기 전용 배포 토큰**: 서버가 코드를 받을 때 개인 토큰이 아니라 `read_repository` 권한만 가진 토큰을 쓴다. 서버에서 GitLab SSH(22번)가 막혀 있어 HTTPS 방식을 썼다.
- **MR 대상 브랜치 확인**: CD MR이 `develop-BE`가 아니라 `main`으로 병합된 사고가 있었다. 병합 통제(대상 브랜치, 리뷰)는 의도하지 않은 배포를 막는 수단이다. MR 설명 맨 위에 대상 브랜치를 적는다.
- **서버에서 검증된 뒤 병합**: 시험 전에 병합되는 일이 반복돼 Draft MR로 연다.
- **롤백과 DB 마이그레이션**: 마이그레이션은 앞으로만 진행한다. 새 마이그레이션이 적용된 뒤 옛 앱으로 롤백하면 시작하지 못할 수 있어 롤백 전에 확인한다.

## 6. 데이터

### 6.1 서명 URL
- **확인함:** 변조된 서명, 만료된 URL, 서명 없는 접근이 모두 403으로 거부된다. 브라우저 사전 요청(CORS)은 공개 주소로 허용 출처를 좁혔다.
- 서명에는 호스트와 경로가 포함되므로 프록시가 경로를 자르거나 `Host`를 바꾸면 서명이 틀어진다. 경로·`Host`를 그대로 전달하고 스토리지에 공개 주소를 알려 준다.

### 6.2 비공개 버킷
- 플레이 원본 버킷은 Nginx가 전달하지 않아 외부에서 접근되지 않는다(**확인함**). 앱만 내부 주소로 접근한다.
- 앱이 쓰는 비공개 버킷 조건: 외부 접근 차단, 버전 관리 꺼짐(버전 관리 여부는 **미확인**, 서버에서 확인 후 기록).

### 6.3 개인정보·저작권
- 기획이 "사용자 음원 원본은 처리 후 즉시 폐기"를 확정했다. 임시 음원 버킷에 보관 기간(1일, 보험)을 걸었고, 즉시 폐기는 처리 끝에 BE·AI가 삭제하는 것으로 합의했다.
- S3 수명주기 API는 규칙만 저장되고 객체에 만료가 붙지 않아 **경로 TTL**을 썼다(실제 삭제를 시험으로 확인). 보안·개인정보 기능은 "설정됨"이 아니라 **실제 동작**을 시험해야 한다.

## 7. 로그

- 로그에는 토큰·비밀번호·이메일이 섞일 수 있다. 로그 수집기(Alloy)에서 Loki로 보내기 전에 가린다(Bearer 토큰, JWT 형태, `password`·`secret`·`token`·`authorization` 값, 이메일).
- **확인함(결함 발견):** 샘플 로그로 시험하니 `Authorization: Bearer 토큰`에서 "Bearer"만 가려지고 토큰이 그대로 남았다. 규칙 순서 때문이었다(key=값 규칙이 먼저 "Bearer"를 잡음). Bearer 규칙을 앞에 두어 해결했다.
- **교훈:** 가림 규칙은 **실제 모양의 샘플로 시험**하고, 가려진 결과에 원문이 남았는지를 검사한다. 구체적인 규칙을 먼저, 일반 규칙을 나중에 둔다. 시험은 Python이었고 실제 엔진(Alloy의 Go 정규식)에서는 서버 확인이 남았다.
- 가림은 마지막 안전장치다. 앱이 비밀을 로그에 남기지 않는 것이 먼저다.
- 로그 보관은 Loki 7일, 컨테이너 로그 파일은 크기 한도(10MB×3)로 디스크를 보호한다(가용성).

## 8. 공급망·재현성

- 이미지는 `latest`를 쓰지 않고 **버전을 고정**한다(prometheus, grafana, loki, alloy, certbot, seaweedfs, MLflow 등). 어느 날 갑자기 동작이 바뀌거나 변조된 새 이미지를 받는 일을 줄인다.
- CI의 JDK는 `eclipse-temurin:21-jdk` 이미지를 쓴다. 해시(다이제스트)로 고정하거나 검증하지는 않는다. 태그는 같은 이름으로 내용이 바뀔 수 있어 **한계**로 기록한다. `redis:7-alpine`, `nginx:1.27-alpine`도 마이너 태그까지만 고정되어 있다.
- 모델 파일은 게시할 때 `sha256`을 계산해 매니페스트에 적는다(변조·손상 확인용).
- 서버에서 처음 받는 이미지는 출처 레지스트리(Docker Hub, gcr.io 등)를 확인한다. 큰 이미지는 미리 받아 둔다.
- 후속(미확인): 이미지 취약점 스캔(Trivy), 저장소 비밀 스캔, SAST. Jira 48번의 후속 작업에 있다.

## 9. 가용성·데이터 보호

- **`docker volume prune`, `docker system prune --volumes`를 서버에서 실행하지 않는다.** 사용하지 않는 볼륨을 지우기 때문에 멈춰 있는 서비스의 데이터와 인증서 볼륨이 삭제된다. 스토리지 볼륨이 사라진 사례가 있었다(원인은 확정하지 못함).
- PostgreSQL 비밀번호는 DB를 처음 만들 때 고정된다. 운영 데이터가 있으면 볼륨을 지우지 않고 DB 안에서 바꾼다.
- 메모리·디스크 한도(컨테이너별 `mem_limit`, 로그 크기 한도)를 두어 한 서비스가 서버 전체를 먹지 않게 한다.
- 알림 규칙: 디스크 85% 초과, 사용 가능 메모리 10% 미만, 핵심 컨테이너 중단(Grafana에 표시, 외부 전송은 후속).

## 10. TLS(HTTPS) — 진행 중

- **인증서 발급 원리(HTTP-01):** certbot이 토큰 파일을 만들고, Let's Encrypt가 80번으로 `/.well-known/acme-challenge/토큰`을 요청해 같은 값이 돌아오면 "도메인을 통제한다"고 인정한다. 그래서 80번과 챌린지 경로가 열려 있어야 하고, 80→443 리다이렉트에서도 이 경로는 예외로 둔다.
- **발급 횟수 제한:** 진짜 Let's Encrypt는 같은 도메인에 일주일에 발급할 수 있는 횟수가 제한되어 있다. **스테이징(시험용)으로 먼저 연습**한다.
- **개인 키 보호:** 인증서·키는 `letsencrypt` 볼륨에만 두고 Nginx에는 읽기 전용으로 연결한다. 저장소·채팅에 올리지 않는다. 볼륨을 `prune`으로 잃지 않게 한다.
- **갱신:** 인증서는 90일이다. 갱신이 끊기면 서비스가 멈춘다. 자동 갱신과 갱신 시험(`--dry-run`)이 완료 기준이다.
- **남은 점검(미확인):** 허용 TLS 버전(1.2 이상), 약한 암호 제외, HSTS 적용 시점, 외부 검증(SSL Labs), 폰·다른 브라우저 접속.

## 11. 접근 제어(48번) — **아직 점검 전**

| 점검 | 확인 방법(서버, 읽기 전용) | 기준 |
| --- | --- | --- |
| SSH 비밀번호 로그인 | `sudo sshd -T \| grep -i passwordauthentication` | `no` |
| root 로그인 | `sudo sshd -T \| grep -i permitrootlogin` | `no` 또는 `prohibit-password` |
| 열린 포트 | `sudo ss -tlnp`, 외부에서 스캔 | 필요한 포트만(22, 80, 443) |
| Docker가 공개한 포트 | `sudo iptables -t nat -L DOCKER -n` | Nginx 외에 없음(루프백 제외) |
| 자동 보안 업데이트 | `systemctl status unattended-upgrades` | 켜져 있음 |
| 서버 접속 기록 | `last`, `sudo journalctl -u ssh` | 낯선 접속 없음 |
| 컨테이너 실행 사용자 | 각 이미지의 사용자 확인 | root가 아닌 서비스 확인(예외 기록) |

**점검 결과(2026-10-25, `sudo sshd -T`):** 비밀번호 로그인 `no`(기준 충족), 키 로그인 `yes`, 포트 22. root 로그인은 `without-password`(= `prohibit-password`, 키로만 허용)이고, root의 `authorized_keys`에는 AWS 기본 제한 키(`no-port-forwarding` 등 옵션과 안내 `command`)만 있어 쉘을 받을 수 없다. 키보드 대화형 인증 `no`, `AllowUsers` 제한 없음, `MaxAuthTries 6`, `LoginGraceTime 120`(기본값).
- **SSH 보강 적용(2026-10-26):** `/etc/ssh/sshd_config.d/10-hardening.conf`로 `PermitRootLogin no`, `MaxAuthTries 3`, `LoginGraceTime 30`을 적용했다. **자동 보안 업데이트 점검 결과(2026-10-25):**

**접속 기록 점검 결과(2026-10-25, `last`, `journalctl -u ssh`, 최근 3일):**

- **참고:** 서버 키(`.pem`)는 서버 지급 때 받은 한 쌍이라 사무국이 같은 키를 보관하는지는 확인하지 못했다. 필요하면 사무국에 문의한다.
- 키 한 쌍을 공유하면 접속자를 개인별로 구분할 수 없다. 팀 접속 가이드에서 사람마다 키를 따로 등록하는 방안을 다룬다.
- 선택 과제: 반복 실패 IP를 자동 차단하는 `fail2ban` 도입. 비밀번호 로그인이 꺼져 있어 우선순위는 낮다.

- **SSH 설정을 바꿀 때의 안전장치:** 설정을 바꾸기 전에 SSH 접속 창을 **하나 더 열어 두고**, 설정 문법을 검사(`sudo sshd -t`)한 뒤 적용한다. 잘못되면 열어 둔 창으로 되돌린다. 방화벽 규칙도 같은 방식이다(22번을 막으면 서버에 못 들어간다).
- 팀원 접속 방법(키 발급·등록 절차)과 키 보관 규칙은 `Infra/ACCESS.md`에 정리했다(초안, 사람마다 키를 따로 등록하는 방식은 제안 단계).
- 배포 러너 `ec2-deploy`의 Protected 설정은 담당자가 GitLab 화면에서 확인했다(2026-10-25, 담당자 보고 기준).

## 12. 통합 배포 뒤 점검 (2026-10-27)

FE(web)·AI(ai-api)를 포함해 `main`을 배포한 뒤 확인한 것이다.

- **외부 입구는 그대로다(설계 확인):** `web`(8080)과 `ai-api`(8000)는 `ports:`가 없고 내부 네트워크 이름으로만 접근한다. 바깥에서 `/`는 Nginx를 거쳐 FE가 응답하고, 인증이 필요한 API는 401로 거부되는 것을 확인했다. 배포 뒤 `ss -tlnp`로 목록을 다시 보는 것은 아직 안 했다(남은 점검).
- **컨테이너 사용자:** FE는 `nginx-unprivileged`(비root, 8080), AI는 `uid 10001`(`app`)로 실행한다. 두 이미지 모두 다단계 빌드라 빌드 도구가 최종 이미지에 남지 않는다.
- **헬스체크로 "떠 있음"과 "동작함"을 구분:** `docker ps`에서 `health`가 비어 있던 서비스(nginx, prometheus, node-exporter, alloy)에 헬스체크를 추가했다. 이미지마다 쓸 수 있는 도구가 달랐다(loki 이미지에는 셸·`wget`이 없어 헬스체크를 넣지 못하고 이유를 주석으로 남김, alloy에는 `wget`·`curl`이 없어 bash의 `/dev/tcp`로 확인). 재시작 정책(`unless-stopped`)은 `unhealthy` 컨테이너를 재시작하지 않으므로 헬스체크는 **감시용**이다.
- **재시작 반복 진단 절차(MLflow, `Infra/TROUBLESHOOTING.md` C10·C11):** `docker inspect`로 종료코드·`OOMKilled`·재시작 횟수를 보고, `docker top`·`docker stats`로 어떤 프로세스가 자원을 쓰는지 본다. 이번에는 메모리 부족이라는 첫 가설이 종료코드 0·`OOMKilled=false`로 틀린 것이 드러났다. 원인은 MLflow 3.x 작업 실행기가 만든 프로세스 121개였다.
- **쓰지 않는 기능은 끈다(공격 면적·자원 절감):** `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false`로 작업 실행기를 껐다(서버 시험: 프로세스 121→12개, 메모리 1.627GiB→346MiB, `healthy`, 재시작 0회). 환경변수 이름은 추측하지 않고 `mlflow.environment_variables`를 조회해 실제 이름을 확인했다.
- **서버 시험 중 권한이 막은 것(정상 동작):** `/srv/airdrum/Infra`는 배포 계정 소유이고 `.env`는 600이라 `ubuntu` 계정이 직접 수정하거나 `docker compose`로 읽지 못했다(`Permission denied`). 설계대로 `.env`가 보호되고 있다는 확인이다. 시험은 `sudo`로 하고, 시험 수정은 다음 배포에서 저장소 내용으로 덮어쓴다.
- **정리:** 통합 시험용 컨테이너(`fe-web-test`, `ai-api-test`, `ai-apt-test`)·이미지·`/tmp` 작업 폴더를 서버에서 삭제했다. 시험 컨테이너가 남아 있으면 의도하지 않은 포트나 옛 설정이 살아 있을 수 있다.
- **사고 기록:** 진단 출력의 DB 비밀번호가 채팅에 남은 일은 3.4에 적었다.
- **남은 점검:** 배포 뒤 `ss -tlnp`·외부 포트 재시험, Redis 수정의 운영 반영 확인(BE 연결 복구), DB 비밀번호 교체 여부 결정.
