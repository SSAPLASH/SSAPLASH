# 인프라 보안 점검 기록

서버·컨테이너·CI에서 **보안 관점으로 확인하고 결정한 것**을 모은다. 새로 점검하거나 결정할 때마다 항목을 추가한다. 문제를 겪은 사례는 `Infra/TROUBLESHOOTING.md`에, 여기에는 점검 기준과 결과를 둔다.

- 상태 표기: **확인함**(직접 시험·검증), **설계 반영**(코드·설정에 반영, 서버 시험은 별도), **원리 정리**(원리는 이해했고 서버에서 직접 확인은 전), **미확인**(아직 점검 전)
- 비밀값(토큰, 키, 비밀번호)은 적지 않는다.

## 2. 네트워크

### 2.1 외부에 닿는 포트는 최소로
- **원칙:** 인터넷에서 직접 닿는 입구는 Nginx(80, 곧 443) 하나로 하고, 나머지는 열지 않는다.
- **적용:** DB·Redis·SeaweedFS·Prometheus·Loki는 `ports:`로 공개하지 않고 내부 네트워크(`internal: true`)에만 둔다. Grafana(3000)와 MLflow(5000)는 `127.0.0.1`로만 공개하고 팀원은 SSH 터널로 접속한다.
- **확인 방법:** `docker compose config`의 `ports` 항목(공개된 포트 목록)을 본다. 서버 밖에서 실제로 닿는 포트는 별도로 스캔한다(미확인, 2.3).
- **이유:** 서비스가 하나 늘 때마다 공격 면이 늘어난다. 입구를 하나로 두면 점검·로그·인증서 관리가 한곳에 모인다.

### 2.2 방화벽은 두 겹이다
```
인터넷 → [① AWS 보안 그룹] → [② 서버 안 ufw] → Docker / Nginx
```
| 계층 | 누가 바꾸나 | 확인 방법 |
| --- | --- | --- |
| ① AWS 보안 그룹(클라우드 쪽) | AWS 콘솔 권한이 있어야 함(우리는 없음) | **바깥에서 포트 연결 시험** |
| ② ufw(서버 안) | 서버에서 `sudo ufw ...` | `sudo ufw status` |

- **확인함:** 443번이 바깥에서 닿는지를 콘솔 없이 시험했다. 서버에서 `ufw allow 443/tcp` 후 **빈 폴더에서** 임시 서버(`python3 -m http.server 443`)를 띄우고, 내 PC에서 `Test-NetConnection 서버 -Port 443`을 실행해 `TcpTestSucceeded : True`를 확인했다. → 보안 그룹이 443을 허용한다. 시험 후 서버를 종료하고 폴더를 삭제했다.
- **교훈:** 권한이 없어 설정을 못 봐도, **결과(실제로 닿는가)** 를 시험하면 상태를 알 수 있다.

### 2.3 Docker가 공개한 포트는 ufw를 우회한다
- **원리 정리:** Docker가 `ports:`로 포트를 공개하면 PREROUTING에서 목적지를 컨테이너 IP로 바꾼다(DNAT). 그러면 패킷이 "서버 자신"이 아니라 "다른 곳"으로 판정되어 INPUT이 아니라 **FORWARD 체인**을 지난다. ufw의 허용·차단은 주로 INPUT 체인에 걸려 있어서, 컨테이너로 가는 패킷에는 적용되지 않는다. FORWARD에는 Docker가 공개 포트를 허용하는 규칙을 먼저 넣어 둔다.
- **결과:** ufw에서 막아도 `ports:`로 공개한 컨테이너 포트는 열린다. 예를 들어 DB를 실수로 `ports: "5432:5432"`로 공개하면 ufw가 있어도 인터넷에 노출된다. 반대로 ufw에서 80을 허용하지 않아도 Docker로 공개한 Nginx 80은 열린다(정확한 확인은 시험이 필요함).
- **대응:** (1) DB·Redis·스토리지는 `ports:`를 쓰지 않는다. (2) 서버 안에서만 쓸 포트는 `127.0.0.1:포트:포트`로 공개한다. (3) 필요하면 `DOCKER-USER` 체인에 차단 규칙을 둔다.
- **서버에서 확인한 결과(2026-10-25, 읽기 전용 명령):**
  - `sudo ufw status verbose`: active, 기본 `deny (incoming)`·`deny (routed)`, 허용은 22, 80/tcp, 443/tcp(IPv4·IPv6).
  - `sudo iptables -t nat -L DOCKER -n`: DNAT 규칙이 `tcp dpt:80 → 172.19.0.2:80` 하나뿐이다. Docker가 공개한 포트는 80뿐이다.
  - `sudo iptables -L FORWARD -n --line-numbers`: 정책 DROP, 순서가 `DOCKER-USER`(1) → `DOCKER-FORWARD`(2) → `ufw-*`(3 이하)다. Docker 체인이 ufw보다 앞에 있다.
  - `sudo iptables -L DOCKER-USER -n`: **비어 있다.** 누가 실수로 `ports:`를 추가해도 막아 줄 규칙이 없다.
  - `docker ps`: 컨테이너 5개(api, nginx, seaweedfs, postgres, redis). 호스트에 공개된 것(`->` 표시)은 nginx의 80뿐이다. 나머지는 컨테이너 내부 포트만 열려 있다.
  - 모니터링·MLflow 컨테이너는 없다(서버에 아직 배포되지 않음).
- **바깥(내 PC)에서 접속 시험(2026-10-25, 공개 IP, 13개 포트, 4초 대기):** 22·80 열림. 443은 연결 거부(보안 그룹·ufw는 통과, 듣는 프로그램이 없어서 정상). 3000, 3100, 5000, 5432, 6379, 8080, 8333, 8888, 9090, 9333은 응답 없음(차단). 서버 안의 `ss`·`iptables` 결과와 일치한다. 한계: 흔한 포트만 본 것이고 전체 포트 스캔이 아니며, 응답 없음만으로는 보안 그룹과 ufw 중 어느 쪽이 막았는지 구분하지 못한다.
- **아직 안 한 것:** ufw 규칙을 지워도 Docker가 연 80이 계속 열리는지 직접 시험(우회 동작 확인), `DOCKER-USER`에 보호 규칙 추가 검토.
- **외부 전체 포트 검사(2026-10-26, 내 PC → 공개 IP, 1~65535번 전체):** **22(ssh) 열림, 80(http) 열림, 443 닫힘(연결 거부: 서버까지 닿았고 듣는 프로그램이 없음), 나머지 65532개는 응답 없음(차단).** 서버 안의 `ss`·`iptables` 결과와 일치한다. 예상 밖의 열린 포트는 없다.
  - 방법: `nmap`을 먼저 시도했으나 이 PC에서 Windows 네트워크 오류(`10014`)가 계속 나서 전체 결과를 쓸 수 없었다(`Infra/TROUBLESHOOTING.md` H6). 대신 PowerShell(.NET 소켓 접속 시험)로 250개씩 끊어 접속하고, 오류가 난 포트(구간마다 약 300개)는 20개씩 다시 검사해 끝내 오류가 남은 포트가 0개임을 확인했다. 구간 합계가 65535개와 맞는다.
  - 한계: 접속(TCP connect) 시험이라 UDP는 보지 않았고, "응답 없음"은 방화벽 차단과 서버가 응답을 버리는 경우를 구분하지 못한다. `nmap`으로 같은 확인을 다른 PC·네트워크에서 다시 하는 것은 선택 과제다.
- **점검 기준:** ufw 규칙이 아니라 **바깥에서 실제로 닿는 포트**로 점검한다(외부 스캔, `ss -tlnp`, 위 DNAT 규칙).

### 2.4 임시 포트 시험 때의 위험
- `python3 -m http.server`는 **현재 폴더의 모든 파일을 공개**한다. 홈 폴더에서 실행하면 `.ssh` 같은 중요한 파일이 노출될 수 있다. 반드시 빈 임시 폴더에서 실행하고 끝나면 종료한다.
- 시험용으로 연 포트·프로세스는 끝나면 닫는다(방화벽 규칙은 필요한 것만 남긴다).

## 3. 시크릿(비밀값) 관리

### 3.1 저장 위치와 누락 시 동작
- 비밀번호·키·토큰은 **서버의 `Infra/.env`에만** 둔다(권한 `600`, Git 무시). 저장소에는 값이 빈 `.env.example`만 둔다.
- 필수 값은 Compose에서 `${변수:?메시지}`로 지정해, **비어 있으면 실행 자체를 중단**한다(빈 비밀번호로 서비스가 뜨는 일을 막음). 단점: `docker compose down`도 변수가 없으면 중단된다.
- 서버 배포가 `.env`를 덮어쓰거나 지우지 않는다(`rsync --exclude .env`).

### 3.2 비밀값을 보지 않고 만들기
- 서버에서 `openssl rand -hex`로 만든 값을 `sed`/`tee`로 **`.env`에 직접 쓴다.** 값이 화면과 채팅에 출력되지 않는다. 확인은 값이 아니라 **개수**(`grep -c`)로 한다.
- 비밀번호에 `$`, `#`, `%`, `@`, `/`, `:` 같은 문자가 있으면 설정 파일·접속 주소가 깨질 수 있어 영문·숫자(hex)를 쓴다.

### 3.3 토큰 노출 사고
- `gitlab-runner list`가 러너 인증 토큰을 그대로 출력하는 것을 모르고 결과를 공유했다.
- 대응: 러너를 삭제하고 새로 만들어 토큰을 교체했다. 이후 상태 확인은 `systemctl status`로 한다.
- **원칙:** 도구가 비밀값을 출력하는지 모르면 출력 전에 확인한다. 노출됐다면 값을 **폐기(교체)** 한다. 노출 범위가 작아 보여도 교체가 가장 빠르다.

### 3.4 명령줄 인자로 넘긴 비밀번호는 `docker top`에 그대로 보인다 (2026-10-27)
- **발견:** MLflow의 재시작 반복 원인을 `docker top infra-mlflow-1`로 보다가, 출력에 DB 접속 주소의 **비밀번호가 평문으로** 나왔다. `mlflow server --backend-store-uri postgresql://사용자:비밀번호@…`처럼 비밀번호가 포함된 주소를 **명령줄 인자**로 넘겼기 때문이다. 명령줄은 `docker top`, `ps`로 서버에 들어온 사람이 읽을 수 있다.
- **2차 노출:** 이 출력을 진단 도구 결과로 채팅에 붙여 넣어 비밀번호가 **대화 기록에도 남았다.** 3.3의 러너 토큰 사고와 같은 모양이다("도구가 비밀값을 출력하는지 모르고 결과를 공유").
- **위험 평가:** PostgreSQL은 내부 네트워크에만 열려 있고 호스트 포트가 없어서, 비밀번호만으로 바깥에서 접속할 수는 없다. 그래서 즉시 악용 가능성은 낮다고 판단했다. 다만 서버 안에서 프로세스를 볼 수 있는 사람(docker 그룹, 4.4)에게는 열린 값이다.
- **조치(설계 반영):** DB 주소를 명령줄에서 빼고 `MLFLOW_BACKEND_STORE_URI` 환경변수로 넘기게 `Infra/docker-compose.yml`을 고쳤다. `mlflow server --help`에는 환경변수 표기가 없어서 지원 여부를 알 수 없었고, MLflow 소스(`cli/__init__.py`의 `envvar="MLFLOW_BACKEND_STORE_URI"`)로 이 옵션이 환경변수를 읽는 것을 확인했다.
- **서버 확인(2026-10-27):** 서버에 적용하고 `healthy`, 재시작 0회를 확인했다. `docker top infra-mlflow-1 -eo pid,args`에서 `postgresql://`이 든 명령줄이 0개다. 컨테이너 환경변수는 `postgresql`로 시작하고(비밀번호는 출력하지 않고 앞부분만 확인), `mlflow` DB에 MLflow 테이블이 있어 파일 저장소로 떨어지지 않았다.
- **시험 실수(기록):** 처음 `docker top -eo args`는 `Couldn't find PID field` 오류를 냈는데, 오류를 `grep -c`가 빈 입력으로 받아 `0`이 나왔다. 오류 때문에 나온 `0`이어서 유효한 시험이 아니었고, `-eo pid,args`로 다시 해서 확인했다. **명령이 실패했는지 먼저 본 뒤 결과를 믿는다.**
- **한계(솔직하게):** 환경변수로 옮겨도 `docker inspect`(컨테이너 환경)에서는 값이 보인다. 줄어드는 것은 `docker top`/`ps`처럼 흔히 쓰고 공유하기 쉬운 출력에서의 노출이다. docker 그룹은 이미 사실상 root라서(4.4) 그 사용자에게서 값을 완전히 숨길 수는 없다. 근본 대책은 비밀 관리 도구 또는 파일 기반 비밀(Docker secrets) 도입이며 후속 과제로 둔다.
- **같은 문제가 있던 곳(Redis, 조치함):** Redis는 `redis-server --requirepass ${REDIS_PASSWORD}`로 비밀번호를 넘겼다. Compose가 변수를 치환해 컨테이너 설정(`Cmd`)에 비밀번호가 글자 그대로 들어가고, 헬스체크의 `redis-cli -a 비밀번호`도 실행되는 동안 명령줄에 남는다. 조치: 비밀번호를 설정 파일(`/tmp/redis.conf`, 권한 600, 소유자 `redis`)에 쓰고 명령줄에는 파일 경로만 넘긴다. 헬스체크는 `-a` 대신 환경변수 `REDISCLI_AUTH`를 쓴다. 이미지의 시작 스크립트(`docker-entrypoint.sh`)를 거쳐야 root에서 `redis` 사용자로 내려가므로 `exec docker-entrypoint.sh`로 호출한다.
  - **서버 시험(2026-10-27, 가짜 비밀번호의 임시 컨테이너, 운영 Redis는 건드리지 않음):** 환경변수 인증 `PONG`, 인증 없이는 `NOAUTH`, 설정 파일 `-rw-------`·소유자 `redis`, 프로세스 사용자는 root가 아님(호스트에서 uid 999로 표시). 운영 반영은 다음 배포에서 하고 반영 뒤 BE 연결 복구를 확인한다.
  - **정정(내가 먼저 짚은 가설이 시험으로 틀린 부분):** 처음에는 예전 방식이 `docker top`에 비밀번호를 보였을 것이라 생각했지만, Redis가 시작 뒤 자기 프로세스 이름을 `redis-server *:6379`로 바꿔서 `docker top`에는 인자가 나오지 않는다. 실제 노출 경로는 `docker inspect`·`docker compose config`의 `Cmd`와 헬스체크 실행 중의 명령줄이었다. 환경변수로 넘기는 값은 `docker inspect`의 환경 항목에서 여전히 보인다(한계, 위와 같음).
- **비밀번호 교체(2026-10-27 수행):** 노출된 값이라 교체했다. 이 값을 쓰는 곳은 서버 `.env`의 `POSTGRES_PASSWORD` 한 곳과 이를 받는 서비스(`api`, `mlflow`, `mlflow-db-init`)뿐이었다(CI의 시험용 비밀번호는 별개).
  - **절차:** (1) `.env`를 권한 그대로 백업하고 BE 담당에게 짧은 중단을 알린다. (2) 새 값을 `openssl rand -hex 24`로 셸 변수에 만든다(화면에 출력하지 않고 길이만 확인). (3) `printf`로 `ALTER USER`를 만들어 파이프로 `psql`에 넘긴다(비밀번호가 명령줄에 남지 않음). (4) `.env`의 기존 줄을 지우고 `printf | sudo tee -a`로 새 줄을 추가한다(권한·소유자 유지, 줄 수와 변수 개수 확인). (5) **재시작 전에** 새 값으로 접속되는지, 옛 값은 `password authentication failed`로 거부되는지 확인한다(`-h postgres`로 소켓 신뢰 접속을 피함). (6) `docker compose up -d`로 환경변수가 바뀐 서비스만 다시 만든다. (7) `api`·`mlflow`가 `healthy`, 재시작 0회, 연결 실패 로그 0건인지 확인한다. (8) 옛 비밀번호가 든 백업 파일을 삭제한다.
  - **결과:** 새 값 접속 성공, 옛 값 거부, `api`·`mlflow` `healthy`(재시작 0회). 사이트 `/` 200. 다른 서비스는 재생성되지 않았다.
  - **주의(이번에 배운 점):** 확인 없이 재시작하지 않고 DB 쪽 교체를 먼저 검증했다. 비밀번호를 만드는 명령 자체가 노출 경로가 되지 않게 stdin·셸 변수로만 다뤘다. 옛 값은 DB에서 거부되므로 이 대화 기록에 남은 값은 더 이상 쓸 수 없다.
  - **남은 것:** 같은 계정이 BE와 MLflow에서 공유되고 슈퍼유저라는 점(MLflow 전용 계정 분리)은 후속 과제다.
- **원칙:** (1) 비밀번호가 포함된 주소·옵션을 명령줄에 두지 않는다. (2) 진단 출력(`docker top`, `docker inspect`, `ps`, `env`)은 비밀값이 섞일 수 있으니 **붙여 넣기 전에 훑는다.** (3) 노출됐으면 범위를 따지기 전에 교체를 먼저 검토한다.

### 3.5 키 파일
- SSH 키(`.pem`)는 소유자만 읽도록 권한을 제한한다(Windows는 `icacls`). 다른 사용자가 읽을 수 있으면 접속이 거부된다.
- 저장소·채팅·문서에 키를 올리지 않는다. 팀원 접속 키는 메신저로 주고받지 않는다.

### 3.6 서버 `.env`의 비밀값을 넣고, 조회하고, 전달하기 (2026-10-28)

서버 `.env`(`/srv/airdrum/Infra/.env`)는 소유자 `gitlab-runner`, 권한 `600`이라 `sudo`로만 다룬다.

**넣을 때** (소셜 로그인 값 4개, 관리자 이메일을 이 방식으로 넣었다)
- 값이 **명령줄·화면·셸 기록·채팅에 남지 않게** 숨김 입력과 파이프를 쓴다.
  - 입력: `read -rs -p "이름: " V` (입력이 화면에 보이지 않는다)
  - 반영: `sudo sed -i '/^이름=/d' .env && printf '이름=%s\n' "$V" | sudo tee -a .env > /dev/null; unset V` (기존 줄을 지우고 새 줄을 추가, 값은 명령줄이 아니라 파이프로만 전달)
- 입력 줄과 반영 줄은 **따로 실행**한다. 한꺼번에 붙여넣으면 둘째 줄이 값으로 읽힌다.
- 넣은 뒤에는 값 대신 **글자 수**로 확인한다: `sudo awk -F= '/^(이름1|이름2)=/{print $1, "글자수=" length($0)-length($1)-1}' .env`. 권한(`-rw-------`)·소유자·줄 수도 같이 본다.
- 반영은 컨테이너를 다시 만들어야 한다(`sudo docker compose -p infra up -d api`). 수정 전에 `.env` 백업을 만들고 끝나면 지운다(백업에도 다른 비밀값이 있다).
- 실제 사고: 숨김 입력 4개를 반복문으로 넣었더니 3개가 0글자로 저장됐다(`Infra/TROUBLESHOOTING.md` C12). 글자 수 확인이 없었다면 빈 값으로 반영될 뻔했다.

**조회할 때**
- 값은 **본인 터미널 화면에서만** 본다. 전체를 보려면 `sudo less .env`가 낫다(별도 화면이라 끝나면 사라진다). `cat`은 터미널 기록(스크롤백)에 값이 남는다.
- 값을 가리고 훑으려면 앞 4글자만 보이게 한다: `sudo sed -E 's/^([A-Z_]+)=(.{0,4}).*/\1=\2****/' .env`. 변수 이름만 보려면 `sudo cut -d= -f1 .env`.
- 화면 공유 중이거나 옆에 사람이 있을 때는 하지 않는다. 끝나면 `clear`.
- 출력을 복사해 채팅·메일·Jira·MR에 붙이지 않는다. 확인이 필요하면 **변수 이름과 글자 수**만 공유한다.

**다른 사람(BE 등)에게 전달할 때**
- `.env` **전체를 전달하지 않는다.** `POSTGRES_PASSWORD`, `JWT_SECRET`, 쓰기용 스토리지 키처럼 운영 서비스 전체 권한을 가진 값이 섞여 있다.
- **필요한 변수만**, 용도에 맞는 가장 약한 권한으로 준다. 로컬 개발에는 운영 키를 주지 않는다(개발용 값을 따로 만들거나 읽기 전용 키). 쓰기용 키는 서버 안에서만 쓴다.
- 전달은 비밀번호 관리자의 공유 기능이나 직접 전달로 한다. 이미 채팅·문서에 올렸다면 값을 **교체**한다(삭제로는 부족하다, 3.3·3.4).
- 서버 `.env`를 고치는 일은 인프라 담당이 하는 구조다. 다른 파트가 서버 `.env`를 직접 만지게 하지 않는다.

**한계:** `docker` 그룹이나 `sudo` 권한이 있는 서버 접속자는 `.env`와 컨테이너 환경변수를 볼 수 있다(4.4). 이 원칙은 노출 경로를 줄일 뿐 접속자에게서 값을 숨기지는 못한다. 근본 대책은 비밀 관리 도구 도입이며 후속 과제다.

## 4. 권한(최소 권한)

### 4.1 읽기 전용 마운트
- 인증서·모델 볼륨은 Nginx에 `:ro`로 연결한다. 호스트 파일 시스템을 읽는 `node-exporter`·`cadvisor`·`alloy`도 읽기 전용으로 마운트한다. 쓰기는 필요한 한 곳에만 둔다(인증서는 certbot만, 모델은 게시 도구만).
- **이유:** 서비스가 뚫려도 개인 키나 호스트 파일을 바꾸지 못하게 한다.

### 4.2 스토리지 키 분리
- 읽기용(reader)은 악보·반주 버킷 읽기만, 쓰기용(writer)은 서버 내부 적재·플레이 원본·임시 음원에 쓴다.
- **확인함:** 읽기 키로 악보·반주는 읽히고, 쓰기와 다른 버킷 접근은 거부된다(`Infra/README.md` 서버 시험 표). 읽기 키로 서명한 PUT URL의 동작은 기록이 없어 **미확인**이다.
- **이유:** 서명 URL은 서명한 키의 권한을 따른다. 사용자에게 나가는 URL을 만드는 키는 가장 작은 권한이어야 한다.

### 4.3 Docker 소켓은 서버 전체 권한이다
- 로그를 서비스 이름으로 구분하려고 `alloy`에 Docker 소켓을 마운트했다. 소켓은 **읽기 전용(`:ro`)으로 마운트해도 Docker API 호출은 막히지 않는다.** 소켓에 접근하는 프로세스는 컨테이너를 만들어 호스트를 장악할 수 있다.
- 완화: 포트를 열지 않고 내부 네트워크에만 둔다, 이미지 버전을 고정한다, 다른 서비스에는 소켓을 마운트하지 않는다, 위험을 README에 기록한다.
- **교훈:** 편의 기능(서비스 이름 라벨)과 위험(서버 전체 권한)을 비교해, 위험을 인정하고 완화책과 함께 선택했다. 더 안전한 대안(로그 파일 직접 읽기)은 완료 기준을 못 채워 택하지 않았다.

### 4.4 `docker` 그룹은 사실상 root
- 배포 러너(`gitlab-runner` 사용자)를 `docker` 그룹에 넣으면 그 사용자는 서버 root와 같은 일을 할 수 있다. 그래서 배포 러너는 **보호된(protected) 러너**로 두고 `main`의 잡만 받게 한다.

## 5. CI·배포

- **배포는 수동 승인**: `main` 파이프라인의 `deploy` 잡을 사람이 직접 실행해야 서버가 바뀐다. 병합이 곧 배포가 되지 않는다.
- **일반 CI와 배포를 분리**: 테스트·빌드는 격리된 Docker 컨테이너에서(`ec2-docker`), 서버를 바꾸는 배포는 별도 보호 러너(`ec2-deploy`)에서 한다.
- **서버 접속 키를 CI에 두지 않음**: 러너와 서버가 같은 머신이라 SSH 키 없이 서버 안에서 실행한다. CI 변수에 올리는 비밀이 없다.
- **저장소 접근은 읽기 전용 배포 토큰**: 서버가 코드를 받을 때 개인 토큰이 아니라 `read_repository` 권한만 가진 토큰을 쓴다. 서버에서 GitLab SSH(22번)가 막혀 있어 HTTPS 방식을 썼다.
- **MR 대상 브랜치 확인**: CD MR이 `develop-BE`가 아니라 `main`으로 병합된 사고가 있었다. 병합 통제(대상 브랜치, 리뷰)는 의도하지 않은 배포를 막는 수단이다. MR 설명 맨 위에 대상 브랜치를 적는다.
- **서버에서 검증된 뒤 병합**: 시험 전에 병합되는 일이 반복돼 Draft MR로 연다.
- **롤백과 DB 마이그레이션**: 마이그레이션은 앞으로만 진행한다. 새 마이그레이션이 적용된 뒤 옛 앱으로 롤백하면 시작하지 못할 수 있어 롤백 전에 확인한다.
- **예약 파이프라인과 기존 job 분리(2026-10-29)**: 약점 분석 보정 배치를 GitLab 예약 파이프라인으로 돌린다(14절). 예약 파이프라인에서는 `rules:changes`가 항상 참이라 BE 시험이 매번 돌고
  수동 배포·롤백 job도 대기 상태로 생긴다. 숨은 job `.calibration-guard`를 모든 기존 job의 rules 맨 앞에 붙여 보정 전용·예약 파이프라인에서는 `when: never`가 되게 했다.
  보정 job은 배포와 같은 보호 러너·같은 `resource_group`(`production`)이라 배포·롤백과 겹쳐 돌지 않는다.
  **변수 `COACH_CALIBRATION`을 프로젝트 CI/CD 변수로 등록하면 모든 파이프라인이 보정 전용이 되어 다른 job이 빠진다.** 예약·수동 실행에서만 준다.

## 6. 데이터

### 6.1 서명 URL
- **확인함:** 변조된 서명, 만료된 URL, 서명 없는 접근이 모두 403으로 거부된다. 브라우저 사전 요청(CORS)은 공개 주소로 허용 출처를 좁혔다.
- 서명에는 호스트와 경로가 포함되므로 프록시가 경로를 자르거나 `Host`를 바꾸면 서명이 틀어진다. 경로·`Host`를 그대로 전달하고 스토리지에 공개 주소를 알려 준다.

### 6.2 비공개 버킷
- 플레이 원본 버킷은 Nginx가 전달하지 않아 외부에서 접근되지 않는다(**확인함**). 앱만 내부 주소로 접근한다.
- 앱이 쓰는 비공개 버킷 조건: 외부 접근 차단, 버전 관리 꺼짐. 음원 임시 버킷 `airdrum-tmp-audio`는 서버에서 확인했다(2026-11-03): `s3.bucket.versioning`이 `Unconfigured`(한 번도 켠 적 없음, 켰다가 멈춘 `Suspended`와 다름)이고 서명 없는 요청은 403이다. 다른 버킷의 버전 관리는 확인 전이다.

### 6.3 개인정보·저작권
- 기획이 "사용자 음원 원본은 처리 후 즉시 폐기"를 확정했다. 임시 음원 버킷에 보관 기간(1일, 보험)을 걸었고, 즉시 폐기는 처리 끝에 BE·AI가 삭제하는 것으로 합의했다.
- S3 수명주기 API는 규칙만 저장되고 객체에 만료가 붙지 않아 **경로 TTL**을 썼다(실제 삭제를 시험으로 확인). 보안·개인정보 기능은 "설정됨"이 아니라 **실제 동작**을 시험해야 한다.
- 연주 기록(`play_sessions`·`hits`)을 약점 분석 기준 보정에 쓰는 방식은 **14절**에 있다. 동의한 기록만, 비식별 뷰로만, 집계만 남긴다.

## 7. 로그

- 로그에는 토큰·비밀번호·이메일이 섞일 수 있다. 로그 수집기(Alloy)에서 Loki로 보내기 전에 가린다(Bearer 토큰, JWT 형태, `password`·`secret`·`token`·`authorization` 값, 이메일).
- **확인함(결함 발견):** 샘플 로그로 시험하니 `Authorization: Bearer 토큰`에서 "Bearer"만 가려지고 토큰이 그대로 남았다. 규칙 순서 때문이었다(key=값 규칙이 먼저 "Bearer"를 잡음). Bearer 규칙을 앞에 두어 해결했다.
- **교훈:** 가림 규칙은 **실제 모양의 샘플로 시험**하고, 가려진 결과에 원문이 남았는지를 검사한다. 구체적인 규칙을 먼저, 일반 규칙을 나중에 둔다. 시험은 Python이었고 실제 엔진(Alloy의 Go 정규식)에서는 서버 확인이 남았다.
- 가림은 마지막 안전장치다. 앱이 비밀을 로그에 남기지 않는 것이 먼저다.
- 로그 보관은 Loki 7일, 컨테이너 로그 파일은 크기 한도(10MB×3)로 디스크를 보호한다(가용성).

## 8. 공급망·재현성

- 이미지는 `latest`를 쓰지 않고 **버전을 고정**한다(prometheus, grafana, loki, alloy, certbot, seaweedfs, MLflow 등). 어느 날 갑자기 동작이 바뀌거나 변조된 새 이미지를 받는 일을 줄인다.

## 9. 가용성·데이터 보호

- **백업 보관 30일:** 앱 DB, MLflow DB, SeaweedFS 백업은 서버 안팎 모두 30일 뒤 지운다. 탈퇴·철회로 지운 정보는 그때까지 백업에 남는다. 복원하면 백업 이후의 탈퇴·철회가 사라지므로 재처리 전에 서비스를 열지 않는다(`PORTING.md` 6절). 삭제 자동화와 탈퇴 재적용 도구는 아직 없다. 30일은 팀이 정한 값이고 법정 기한이 아니다.
- **`docker volume prune`, `docker system prune --volumes`를 서버에서 실행하지 않는다.** 사용하지 않는 볼륨을 지우기 때문에 멈춰 있는 서비스의 데이터와 인증서 볼륨이 삭제된다. 스토리지 볼륨이 사라진 사례가 있었다(원인은 확정하지 못함).
- PostgreSQL 비밀번호는 DB를 처음 만들 때 고정된다. 운영 데이터가 있으면 볼륨을 지우지 않고 DB 안에서 바꾼다.
- 메모리·디스크 한도(컨테이너별 `mem_limit`, 로그 크기 한도)를 두어 한 서비스가 서버 전체를 먹지 않게 한다.
- 알림 규칙: 디스크 85% 초과, 사용 가능 메모리 10% 미만, 핵심 컨테이너 중단(Grafana에 표시, 외부 전송은 후속).

## 10. TLS(HTTPS) — 적용함(2026-10-27), 일부 점검 남음

- **인증서 발급 원리(HTTP-01):** certbot이 토큰 파일을 만들고, Let's Encrypt가 80번으로 `/.well-known/acme-challenge/토큰`을 요청해 같은 값이 돌아오면 "도메인을 통제한다"고 인정한다. 그래서 80번과 챌린지 경로가 열려 있어야 하고, 80→443 리다이렉트에서도 이 경로는 예외로 둔다.
- **발급 횟수 제한:** 진짜 Let's Encrypt는 같은 도메인에 일주일에 발급할 수 있는 횟수가 제한되어 있다. **스테이징(시험용)으로 먼저 연습**한다.
- **개인 키 보호:** 인증서·키는 `letsencrypt` 볼륨에만 두고 Nginx에는 읽기 전용으로 연결한다. 저장소·채팅에 올리지 않는다. 볼륨을 `prune`으로 잃지 않게 한다.
- **갱신:** 인증서는 90일이다. 갱신이 끊기면 서비스가 멈춘다. 갱신 경로는 `certbot renew --dry-run`으로 **확인함**(2026-10-27, 모의 갱신 성공). **자동 갱신은 구성하지 않기로 했다**: 프로젝트가 만료(2027-01-25) 전에 끝나므로 수동 갱신으로 대체한다(`Infra/PORTING.md` 5절). 서버를 만료일 이후에도 쓰면 만료 30일 전부터 수동 갱신하고 Nginx를 reload해야 한다. 이 위험(갱신을 놓치면 브라우저 경고와 로그인 불가)은 알고 받아들인 것이다.
- **적용 결과(2026-10-27, 바깥에서 확인):**
  - `http://`는 `301`로 `https://`에 보낸다. `https://` 메인 `200`, 인증서 검증 통과(경고 없음), `/health` `200`, 인증이 필요한 API는 `401`.
  - 발급자 Let's Encrypt, 만료 2027-01-25.
  - TLS 1.2·1.3은 접속되고 1.0·1.1은 접속에 실패했다. 다만 이 실패가 서버의 거부인지 시험한 PC의 curl이 시도하지 않은 것인지는 구분하지 못했다(종료 코드가 달랐음). "오래된 TLS를 서버가 거부한다"는 외부 검증이나 서버 안 시험으로 확인하기 전에는 확정하지 않는다.
- **배포 순서의 교훈:** 443 설정은 인증서 파일을 가리켜서, 인증서 없이 배포하면 Nginx가 시작하지 못해 사이트가 내려간다. 그래서 인증서를 먼저 발급하고(스테이징 → 진짜), 새 설정은 임시 컨테이너로 `nginx -t`를 통과시킨 뒤 배포했다.
- **HSTS는 켜지 않았다:** 한 번 켜면 브라우저가 오랫동안 https만 쓰게 되어, 인증서 만료나 설정 오류 때 사용자가 접속하지 못하고 되돌리기도 어렵다. https가 안정된 뒤 짧은 기간(예: 며칠)부터 켜는 것을 검토한다.
- **남은 점검(미확인):** 오래된 TLS(1.0·1.1)와 약한 암호가 서버에서 실제로 거부되는지, HSTS 적용 시점, 외부 검증(SSL Labs), 폰·다른 브라우저 접속, 로그인 동작(제공자 콜백 등록 후).

## 11. 접근 제어(48번) — **아직 점검 전**

| 점검 | 확인 방법(서버, 읽기 전용) | 기준 |
| --- | --- | --- |
| SSH 비밀번호 로그인 | `sudo sshd -T \| grep -i passwordauthentication` | `no` |
| root 로그인 | `sudo sshd -T \| grep -i permitrootlogin` | `no` 또는 `prohibit-password` |
| 열린 포트 | `sudo ss -tlnp`, 외부에서 스캔 | 필요한 포트만(22, 80, 443) |
| Docker가 공개한 포트 | `sudo iptables -t nat -L DOCKER -n` | Nginx 외에 없음(루프백 제외) |
| 자동 보안 업데이트 | `systemctl status unattended-upgrades` | 켜져 있음 |
| 서버 접속 기록 | `last`, `sudo journalctl -u ssh` | 낯선 접속 없음 |
| 컨테이너 실행 사용자 | 각 이미지의 사용자 확인 | root가 아닌 서비스 확인(예외 기록) |

**점검 결과(2026-10-25, `sudo sshd -T`):** 비밀번호 로그인 `no`(기준 충족), 키 로그인 `yes`, 포트 22. root 로그인은 `without-password`(= `prohibit-password`, 키로만 허용)이고, root의 `authorized_keys`에는 AWS 기본 제한 키(`no-port-forwarding` 등 옵션과 안내 `command`)만 있어 쉘을 받을 수 없다. 키보드 대화형 인증 `no`, `AllowUsers` 제한 없음, `MaxAuthTries 6`, `LoginGraceTime 120`(기본값).
- **SSH 보강 적용(2026-10-26):** `/etc/ssh/sshd_config.d/10-hardening.conf`로 `PermitRootLogin no`, `MaxAuthTries 3`, `LoginGraceTime 30`을 적용했다. SSH 창을 하나 더 열어 두고 `sshd -t`로 문법을 검사한 뒤 `systemctl reload ssh`로 반영했고, `sshd -T`로 실제 적용 값(`no`, `3`, `30`, `passwordauthentication no` 유지)을 확인했다. 적용 상태에서 새로 SSH 접속해 정상임을 확인했다. 기본 설정 파일은 건드리지 않았고(이 파일만 지우면 원상복구), 기존 `60-cloudimg-settings.conf`와는 다른 항목이라 충돌하지 않는다.
- **주의(사고 기록):** 적용 직후 "되돌리기" 명령을 함께 실행해 설정이 해제된 상태로 새 접속 시험을 한 일이 있었다. 이때의 접속 성공은 보강 적용 여부와 무관하므로 시험으로 인정하지 않고, 적용 상태에서 다시 시험했다. 되돌리기 명령은 시험 실패 시에만 쓰도록 안내 방식을 바꿨다(`Infra/TROUBLESHOOTING.md` H4).
- **남은 항목:** `AllowUsers`는 팀원 접속 계정을 정리한 뒤 검토한다.

**열린 포트 점검 결과(2026-10-25, `sudo ss -tlnp`, 서버 안에서 본 목록):** 모든 곳에서 닿는 포트는 22(sshd)와 80(`docker-proxy`, Nginx)뿐이다. DB·Redis·스토리지·Prometheus·Loki 포트는 열려 있지 않다. 443은 아직 없다(39번 진행 중). `127.0.0.1:3000`, `127.0.0.1:5000`이 없어 Grafana와 MLflow는 이 시점에는 서버에 배포되지 않은 상태였다(2026-10-27 통합 배포로 올라왔고, 두 포트는 루프백에만 묶여 있다. 배포 뒤 `ss -tlnp` 재점검은 12절). 바깥에서 실제로 닿는지(보안 그룹 포함)는 별도 시험이 필요하다.

**자동 보안 업데이트 점검 결과(2026-10-25):**
- `unattended-upgrades`는 `enabled`/`active`이고 `20auto-upgrades`에서 목록 갱신과 자동 설치가 매일(`"1"`) 켜져 있다. 허용 출처에 `noble-security`와 ESM 보안 출처가 포함된다. 실행 기록(10/24, 10/25)에서 실제로 돌았다.
- **발견:** 보안 패치(커널 `linux-image-7.0.0-1014-aws`, `libc6`, `linux-base`)가 설치만 되고 재부팅 대기 중이었다(`/var/run/reboot-required`). 실행 중인 커널은 `1012`로 3일 넘게 옛 버전이었다. 자동 설치만으로는 커널·libc 패치가 적용되지 않는다.

**시크릿 파일 권한 점검 결과(2026-10-25, `ls -l /srv/airdrum/Infra/.env`):** `-rw-------`(600), 소유자 `gitlab-runner`. 다른 사용자는 읽을 수 없다. 수정 시각이 10/23이라 이후에 추가된 변수(`GRAFANA_ADMIN_PASSWORD` 등)가 서버 `.env`에 없을 수 있다.

**접속 기록 점검 결과(2026-10-25, `last`, `journalctl -u ssh`, 최근 3일):**
- 로그인 성공은 모두 `ubuntu` 계정이고 접속 IP는 4종류다. 4개가 팀원·담당자의 접속 장소인지 **소유 확인이 필요하다**(로그만으로는 알 수 없음).

- **접속 IP 소유 확인(담당자 추정, 로그로는 검증 불가):** 10/23 새벽에 서로 다른 IP 세 곳이 겹쳐 접속한 기록은, 서버를 지급받은 시기에 사무국 등 여러 곳에서 접속한 것으로 담당자가 추정했다. 오늘 접속 IP는 담당자의 접속이다. 모르는 접속이 확인되면 키를 교체한다(키가 하나라서 교체하면 모든 팀원의 접속 키가 바뀐다).
- **참고:** 서버 키(`.pem`)는 서버 지급 때 받은 한 쌍이라 사무국이 같은 키를 보관하는지는 확인하지 못했다. 필요하면 사무국에 문의한다.
- 키 한 쌍을 공유하면 접속자를 개인별로 구분할 수 없다. 팀 접속 가이드에서 사람마다 키를 따로 등록하는 방안을 다룬다.
- 선택 과제: 반복 실패 IP를 자동 차단하는 `fail2ban` 도입. 비밀번호 로그인이 꺼져 있어 우선순위는 낮다.

- **SSH 설정을 바꿀 때의 안전장치:** 설정을 바꾸기 전에 SSH 접속 창을 **하나 더 열어 두고**, 설정 문법을 검사(`sudo sshd -t`)한 뒤 적용한다. 잘못되면 열어 둔 창으로 되돌린다. 방화벽 규칙도 같은 방식이다(22번을 막으면 서버에 못 들어간다).
- 팀원 접속 방법(키 발급·등록 절차)과 키 보관 규칙은 `Infra/ACCESS.md`에 정리했다(초안, 사람마다 키를 따로 등록하는 방식은 제안 단계).
- 배포 러너 `ec2-deploy`의 Protected 설정은 담당자가 GitLab 화면에서 확인했다(2026-10-25, 담당자 보고 기준).

## 12. 통합 배포 뒤 점검 (2026-10-27)

FE(web)·AI(ai-api)를 포함해 `main`을 배포한 뒤 확인한 것이다.

- **외부 입구는 그대로다(설계 확인):** `web`(8080)과 `ai-api`(8000)는 `ports:`가 없고 내부 네트워크 이름으로만 접근한다. 바깥에서 `/`는 Nginx를 거쳐 FE가 응답하고, 인증이 필요한 API는 401로 거부되는 것을 확인했다. 배포 뒤 `ss -tlnp`로 목록을 다시 보는 것은 아직 안 했다(남은 점검).
- **컨테이너 사용자:** FE는 `nginx-unprivileged`(비root, 8080), AI는 `uid 10001`(`app`)로 실행한다. 두 이미지 모두 다단계 빌드라 빌드 도구가 최종 이미지에 남지 않는다.
- **헬스체크로 "떠 있음"과 "동작함"을 구분:** `docker ps`에서 `health`가 비어 있던 서비스(nginx, prometheus, node-exporter, alloy)에 헬스체크를 추가했다. 이미지마다 쓸 수 있는 도구가 달랐다(loki 이미지에는 셸·`wget`이 없어 헬스체크를 넣지 못하고 이유를 주석으로 남김, alloy에는 `wget`·`curl`이 없어 bash의 `/dev/tcp`로 확인). 재시작 정책(`unless-stopped`)은 `unhealthy` 컨테이너를 재시작하지 않으므로 헬스체크는 **감시용**이다.
- **재시작 반복 진단 절차(MLflow, `Infra/TROUBLESHOOTING.md` C10·C11):** `docker inspect`로 종료코드·`OOMKilled`·재시작 횟수를 보고, `docker top`·`docker stats`로 어떤 프로세스가 자원을 쓰는지 본다. 이번에는 메모리 부족이라는 첫 가설이 종료코드 0·`OOMKilled=false`로 틀린 것이 드러났다. 원인은 MLflow 3.x 작업 실행기가 만든 프로세스 121개였다.
- **쓰지 않는 기능은 끈다(공격 면적·자원 절감):** `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false`로 작업 실행기를 껐다(서버 시험: 프로세스 121→12개, 메모리 1.627GiB→346MiB, `healthy`, 재시작 0회). 환경변수 이름은 추측하지 않고 `mlflow.environment_variables`를 조회해 실제 이름을 확인했다.
- **서버 시험 중 권한이 막은 것(정상 동작):** `/srv/airdrum/Infra`는 배포 계정 소유이고 `.env`는 600이라 `ubuntu` 계정이 직접 수정하거나 `docker compose`로 읽지 못했다(`Permission denied`). 설계대로 `.env`가 보호되고 있다는 확인이다. 시험은 `sudo`로 하고, 시험 수정은 다음 배포에서 저장소 내용으로 덮어쓴다.
- **정리:** 통합 시험용 컨테이너(`fe-web-test`, `ai-api-test`, `ai-apt-test`)·이미지·`/tmp` 작업 폴더를 서버에서 삭제했다. 시험 컨테이너가 남아 있으면 의도하지 않은 포트나 옛 설정이 살아 있을 수 있다.
- **사고 기록:** 진단 출력의 DB 비밀번호가 채팅에 남은 일은 3.4에 적었다.
- **DB 비밀번호 교체:** 완료(3.4 참고).
- **남은 점검:** 배포 뒤 `ss -tlnp`·외부 포트 재시험, Redis 수정의 운영 반영 확인(BE 연결 복구), MLflow 전용 DB 계정 분리(최소 권한).

## 13. 약점 분석 API(`ai-api`) 보안 (2026-10-28)

BE가 플레이 후 호출하는 `POST /analysis/weak-segments`. 학습 모델 없는 통계 규칙 엔진이다(`AI/docs/coach-weak-segments.md`).

**노출과 인증**
- `ai-api`는 `ports:`가 없고 내부 네트워크에만 붙어 있다. 외부에서 닿지 않으며 호출자는 BE뿐이다.
- 인증은 없다. 내부망 신뢰에 기대는 구조이고, 내부 네트워크의 다른 컨테이너가 침해되면 호출할 수 있다는 점은 **알고 받아들인 위험**이다. 응답은 요청 데이터를 가공한 통계일 뿐 비밀값이 없다.
- 컨테이너는 비root(`uid 10001`)로 실행하고 다단계 빌드로 만든다(12절).

**입력 검증과 자원 보호**
- 본문 5 MiB 초과는 본문을 읽기 전에 `Content-Length`로 먼저 거르고(413), 타격 50,000건 초과도 413이다. 필수 필드 누락·타입 오류, `mode`가 `RHYTHM`/`SHEET`이 아닌 값, `PERFECT`/`GOOD`인데 `deltaMs`가 없는 경우는 400이다. 모르는 필드는 무시하고 모르는 패드 이름은 `OTHER`로 모아 처리한다.
- 컨테이너 메모리 한도는 1GiB다. 분석은 한 요청 안에서 끝나고 상태를 저장하지 않는다.
- **서버 확인(2026-10-28):** 타격 2만 건(약 2.7 MiB) 요청이 167ms에 처리됐고 요청 뒤 `docker stats`는 96MiB/1GiB였다. 이 메모리는 요청이 끝난 뒤의 값이라 **처리 중 최대치는 아니다**(Grafana "컨테이너 메모리 사용량"에서 확인). 목표는 5,000건 1초, 50,000건 3초이며 본문 5 MiB 상한이 먼저 걸려 실제 최대는 약 2~2.5만 건이다.

**오류 응답과 로그에서 정보 노출 줄이기**
- 400 응답은 **오류가 난 필드 이름만** 담는다(`{"error": "INVALID_REQUEST", "fields": ["mode"]}`). 입력 값(`input`)은 담지 않는다. 500은 `{"error": "INTERNAL_ERROR"}`만 돌려주고 예외 메시지·스택을 내보내지 않으며, 로그에는 예외 **종류**만 남긴다.
- 요청 본문(타격 데이터)과 `playId`는 로그에 남기지 않는다. 분석 뒤 요약 한 줄(걸린 패턴과 `severity`, 노트 수, `goodMs`, 처리 시간)만 남긴다. 개인을 식별할 수 있는 값이 없다.
- 이 정책은 시험으로 고정했다: 비밀 값이 든 입력(`SECRET-VALUE-123`)이 응답과 로그에 나오지 않는지, 예외 메시지(`secret body text`)가 로그에 나오지 않는지.
- 로그 수집(Alloy)의 마스킹 규칙(Bearer 토큰, JWT, `password=`류, 이메일)이 이 요약 줄을 건드리지 않음을 규칙 코드에서 확인했다. 로그 수정 배포 뒤 Grafana Explore(Loki)에서 이 요약 줄이 실제로 조회됨을 확인했다(`Infra/TROUBLESHOOTING.md` I1: 파이썬 로깅 설정 때문에 `INFO`가 버려지던 문제). 이후 `Infra/monitoring/grafana/dashboards/coach-weak-segments.json`("약점 분석 연동" 대시보드)로 요청 수·결과 종류·처리 시간·패턴별 횟수·호출 실패를 관측한다. 이 대시보드도 요약 줄과 BE 호출 실패 로그만 쓰며 본문·`playId`를 노출하지 않는다.

**서버 시험으로 확인한 것(2026-10-28, 사용자 실행·보고)**
- `ai-api` `healthy`, BE와 합의한 샘플 A(약점 있음)·B(없음)·C(표본 부족)가 기대 응답과 모두 일치, 잘못된 요청은 `400`, 큰 요청 통과.

**남은 점검·한계**
- 요약 로그의 운영 Loki 수집과 FE 업로드 → BE → ai-api 통합 흐름은 운영에서 확인했다. 남은 것은 대시보드를 서버에 배포해 실제 플레이로 패널이 채워지는지 보는 것(배포 전).
- 속도 제한은 없다. 호출자가 BE뿐이고 BE가 동시 처리 수와 재시도 횟수를 제한한다(분석 풀 2개, 재시도 1회).
- **저장되는 연주 기록의 개인정보 취급**: 연동되면 `play_sessions`·`hits`에 사용자 연주 데이터가 쌓이고, FE는 데이터 활용 동의(`consent`)를 `false`로 보낸다(2026-10-29 기준 `CONSENT = false` 고정, 동의 화면은 FE 요청 중). 분석에 쓰는 방식과 동의·탈퇴 정책은 **14절**에서 정했다. 보관 기간은 아직 미정이다.
- **배포 전 DB 백업**: 이번 배포에 DB 마이그레이션(`V15`~`V18`)이 들어가고 롤백으로 되돌려지지 않는다. 백업·복구 시험(133번)이 아직이라 배포 직전 `pg_dump`를 떠 두는 것을 권했다(파일에 사용자 데이터가 있으니 `600`, 나중에 서버 밖 보관). 수행 여부는 확인하지 못했다.

## 14. 약점 분석 실측 보정: 동의·비식별·접근 권한 (2026-10-29)

약점 분석 임계값은 실제 플레이 로그 없이 정한 가정값이다. 동의한 사용자의 연주 기록으로 임계값 **후보**를 만들어 MLflow에 기록하는 배치(`coach-calibration`)를 만들었다.
임계값을 자동으로 바꾸지 않고, 사람이 기록을 검토·승인한 뒤 MR로 바꾼다. 동작은 `AI/docs/coach-calibration.md`, 운영은 `Infra/README.md`에 있고 여기에는 **보안·개인정보 관점의 결정**만 적는다.
상태는 대부분 **설계 반영**이다. 비식별 뷰(BE), 읽기 전용 계정·소금(서버), 동의 화면(FE)이 아직 서버에 없어서 실제 DB 연결은 한 번도 시험하지 못했다.

**원칙**
- **동의한 기록만** 쓴다. 처음에는 FE `consent`가 `false` 고정이었고, 지금은 가입 때 받은 연주 기록 활용 동의가 플레이 시작 시점의 값으로 올라간다(2026-11-06 갱신).
- 분석 쪽은 **원본 테이블이 아니라 비식별 뷰**만 읽는다. 누가 쳤는지는 지우고, 어떻게 쳤는지만 남긴다.
- 결과는 **집계만** 기록하고, 개인이 드러날 수 있는 작은 집계는 가린다.
- 임계값 변경은 **사람이 승인**한다. 자동 적용은 없다.

**흐름과 경계**

| 구간 | 하는 일 | 지키는 것 |
| --- | --- | --- |
| FE → BE | 가입 때 필수 동의(철회는 탈퇴). 초기 설계의 선택 카드는 바뀌었다. 플레이 **시작 시점**의 동의 값을 `consent`로 업로드 | 기본 동의 금지, 동의하지 않아도 모든 기능 동일. 저장은 브라우저에서 시작해 BE 계정 저장으로 옮김(FE 회신) |
| BE → 뷰 | `coach_export_v`: `consent = true`인 세션만, 허용 열만 | 뷰가 곧 허용 목록. 마이그레이션 V21(BE MR !166. V20은 hits 패드 열 폭 수정) |
| 뷰 → AI 배치 | 읽기 전용 전용 계정으로 뷰만 읽음 | 원본 테이블 권한 없음, 연결은 읽기 전용·질의 시간 제한 |
| AI 배치 → MLflow | 집계 기록(산출물·지표) | 행 단위 값·세션 키 없음, 5개 미만 셀 가림 |

**비식별 방식 (BE 뷰)**

| 처리 | 내용 |
| --- | --- |
| 제거 | `user_id`와 회원 정보 전부, 키트·보정·`client_meta`(기기 정보가 섞일 수 있음), 원본 키, `payload_hash`, `live_coach_events`, `pitch`·`yaw`, `baseline_pad`·`predicted_pad`, 정확한 시작·종료 시각 |
| 변환 | 세션 키는 `sha256(id::text \|\| 소금)`의 해시. 소금은 DB 역할 설정(`app.export_salt`)에 두고 저장소에 없다. 소금이 없으면 **어떤 조회든 실패**한다(fail-closed, 데이터가 0건이어도). 빈 문자열 소금이면 행이 나오지 않는다. BE가 운영과 같은 이미지로 예행연습하다 `count(*)`가 소금 없이도 성공하는 허점(PostgreSQL이 조회에 쓰지 않는 뷰 열은 계산하지 않음)을 찾아 검사를 행 조건으로 옮겼다 |
| 축소 | 플레이 시각은 날짜(KST)까지. 사용자가 올린 개인 곡은 곡 번호를 `NULL`로 가리고 `PRIVATE`로만 표시(곡 번호가 사용자를 가리킬 수 있어서). 사용자당 최근 10개만 |
| 제외 | 탈퇴 회원의 세션은 뷰에서 바로 빠지고(V41), 세션 원본은 1분 주기 스케줄러가 동의 여부와 관계없이 지운다. 이미 MLflow 보정 기록에 반영된 집계만 남는다(행 단위 값 없음, 5개 미만 셀 가림) |
| 제외 | 팀원 시험 계정: `users.role = 'ADMIN'` 제외 + 운영 `ADMIN_EMAILS`에 팀원 등록(아래 한계 참고) |

**접근 권한 (최소 권한)**
- BE 마이그레이션이 **로그인 불가 그룹 역할**(`coach_export_reader`)을 만들고 뷰에만 `SELECT`를 준다. 로그인 계정(`coach_export`)·비밀번호·소금은 BE가 아니라 **서버에서 직접** 만든다(비밀이 저장소에 안 들어가게). 비밀번호는 서버 `.env`의 `COACH_EXPORT_PASSWORD`다.
- 뷰는 소유자 권한으로 원본을 읽고 `security_barrier`로 조회 쪽 함수가 필터 아래를 엿보지 못하게 한다(BE 구현 계획). 그룹 역할이 원본 테이블을 읽을 수 없다는 시험은 BE가 넣는다.
- 배치 연결은 읽기 전용이고 질의 시간 제한이 있다. 접속 문자열은 환경 변수로만 받고 로그·오류에 쓰지 않는다. 비밀번호가 비어 있으면 접속 전에 멈춘다.

**이중 방어**: BE 뷰가 허용 목록이지만, AI 배치도 **허용 목록 밖 열이 하나라도 있으면 행을 읽기 전에 실패**한다(열 이름만 오류에 담고 값은 담지 않음). 허용 열 목록은 시험으로 고정했다.

**출력 쪽 비식별 (MLflow·로그)**
- 기록에는 집계(걸림 비율, 분포 분위수, 후보 임계값)만 올린다. 걸린 세션이 1~4건이면 정확한 횟수 대신 상한만, 분포는 기여 세션이 5개 미만이면 전체를 가린다.
- 세션 키를 어디에도 저장하지 않는다. 동의 철회로 어제 있던 세션이 오늘 없을 수 있어서, 세션 **수의 증감**만으로 다시 돌릴지 판단한다.
- 배치의 상태 한 줄(`coach-calibration status=...`)과 실패 줄에는 예외 종류와 열 이름만 담고 메시지·접속 정보·값은 담지 않는다. 합성 데이터로 이를 시험했다.

**컨테이너 격리 (`coach-calibration`)**
- 평소에는 뜨지 않고(`profiles`) 예약·수동 실행 때만 뜬다. 내부 네트워크만, `cap_drop: ALL`, `no-new-privileges`, 메모리 1GiB, 정책 파일은 읽기 전용 마운트다.
- 정책 파일이 이미지에 없어서 조용히 빈 정책으로 도는 문제를 코드로 막았다(경로를 줬는데 파일이 없으면 실패, `TROUBLESHOOTING` I6).

**한계·남은 점검 (정직하게)**
- **실제 DB 연결은 미시험**이다. 모든 시험은 뷰를 모사한 메모리 행으로 했다. BE 뷰 적용, 읽기 전용 계정·소금 생성 뒤 연결 시험과 "원본 테이블 조회가 거부되는지" 확인이 필요하다.
- **팀원 기록 제외:** 동의 화면이 나가면 팀원 시험 기록도 쌓인다. 서버 `ADMIN_EMAILS`에 팀원 이메일을 등록해야 뷰에서 빠진다. 운영의 `consent=true` 기록 수는 서버에서 확인하지 않았다(2026-11-06 갱신).
- **`ADMIN_EMAILS`의 부작용**: 팀원 계정을 시험 계정으로 빼는 방법이 관리자 역할 부여다. 팀원 6명에게 ADMIN 권한이 같이 생긴다. 알고 하는 선택이며, 별도 시험 계정 표식은 만들지 않았다.
- **페달 타격 기록은 병합 뒤부터 쌓인다**: BE가 `hits.pad`가 `varchar(10)`이라 `HIHAT_PEDAL`(11자) 타격이 섞인 업로드가 저장되지 않던 버그를 같은 MR(V20)에서 고쳤다. 병합 전 운영 기록에는 페달 타격이 섞인 RHYTHM·SHEET 세션이 없으므로, 페달이 많은 곡의 분포는 병합 이후 기록부터 반영된다.
- **재식별 위험은 0이 아니다.** 사용자당 10개, 날짜 단위, 개인 곡 번호 가림, 작은 셀 가림으로 줄였지만 연주 습관 자체가 개인 특성일 수 있다. 법적 기준(개인정보보호법상 가명정보 처리 요건)은 팀·멘토 확인이 필요하다. 이 문서는 법적 판단을 하지 않는다.
- **철회·탈퇴 뒤 삭제**: 이미 비식별 처리돼 통계에 반영된 값은 개인별로 찾아 지울 수 없다. 동의 문구에 적었다(FE 확정 문구). 철회는 "철회 이후 세션부터 `consent=false`"이고 과거 세션은 유지된다. 과거까지 빼는 방법은 팀이 정하면 별도 요청한다.
- **보관 기간 미정**: 비식별 뷰는 조회할 때 계산돼 별도 저장이 없고, MLflow 기록(집계)의 보관 기간은 정하지 않았다.
- **소금 교체 정책 없음**: 소금을 바꾸면 세션 키가 모두 바뀐다(배치는 세션 키를 저장하지 않아 영향은 없다). 교체 주기는 정하지 않았다.
- **비밀번호는 `docker inspect`에서 보인다**: 접속 문자열이 환경 변수라 3.4와 같은 종류의 노출이다(MLflow DB 주소와 같은 수준). 이 계정은 비식별 뷰 읽기 외에 권한이 없고 접속 경로가 내부 네트워크뿐이라 영향 범위를 좁혔다.
- 예약 파이프라인 변수 `COACH_CALIBRATION`을 프로젝트 변수로 등록하면 다른 job이 빠진다(5절).
- 후보는 걸림 비율의 점추정으로 고른다. 표본이 작으면 구간이 넓어 승인할 때 같이 봐야 한다.

**서버에서 직접 해야 하는 일 (사용자 실행, BE 뷰 적용 뒤)**: 읽기 전용 로그인 계정 생성과 그룹 역할 구성원 추가, 소금 설정, `.env`에 `COACH_EXPORT_PASSWORD`와 `ADMIN_EMAILS` 팀원 등록, 접속·권한 확인. 값은 명령줄·화면·채팅에 남기지 않는다(3.6과 같은 방식).

## 15. AI 채보 워커 API의 외부 경로 (2026-10-30)

AI 채보 워커가 GPU가 필요해 EC2 밖(교내 GPU 서버)에서 돌게 되면서, BE의 워커 API(`/internal/v1/chart-jobs/`)를 EC2 밖에서 불러야 한다. 공개 Nginx는 `/internal/` 전체를 404로 막아 두었고 BE는 이 API를 "내부 네트워크에서만" 쓰는 전제로 만들었다. 이 전제가 바뀌어 **인터넷에서 닿는 경로 하나를 허용하도록 설정했다.** 요청은 AI 파트에서 왔고(CHART-003), 여기에는 설정에 반영한 보안 결정을 적는다. 서버 적용과 실제 접속은 확인 전이다.

**설정에서 무엇을 허용하나**
- Nginx 443에서 `^~ /internal/v1/chart-jobs/` **하나만** 열고, 다른 `/internal/` 경로는 계속 404다(80 포트는 `/internal/`을 계속 404로 막아 평문 HTTP로는 닿지 않는다).
- **(2026-11-04 추가)** LLM 총평 작업을 GPU 서버의 로컬 오픈소스 모델이 맡으면서 같은 방식(GPU 서버가 BE에서 작업을 가져가는 pull)의 경로 `^~ /internal/v1/coach-narratives/`를 하나 더 열었다. 같은 허용 IP·같은 BE 워커 토큰으로 지키고, 요청·응답이 작아 본문 한도는 64 KiB, 접근·오류 로그는 같은 이유로 끈다. 새로 열린 인터넷 경로는 이 하나뿐이며 외부 유료 LLM으로 나가는 통신은 없다. 서버 적용 전이다(`develop-BE → main` 배포 뒤 `nginx -t` 통과와 403/401 확인).
- 허용 출발지 IP는 GPU 서버가 바깥으로 나갈 때 쓰는 교내 공인 IP 하나다. 그 밖의 IP는 403이다.
- 요청 본문 상한 8MiB는 **이 경로에만** 적용한다(BE 결과 JSON 상한 5MiB). 서버 전체의 기본값은 바꾸지 않는다.
- 워커가 받는 음원 서명 URL을 공개 도메인으로 만들도록 `AUDIO_STORAGE_PUBLIC_ENDPOINT`를 `https://k15a307.p.ssafy.io`로 둔다. 서명 URL 경로(`airdrum-tmp-audio`)는 이미 Nginx가 스토리지로 넘기고 있어 Nginx에 더 추가한 것이 없다.

**지키는 방법 (층별)**

| 층 | 내용 | 강도 |
| --- | --- | --- |
| 네트워크 | 한 경로, 한 IP | **약함.** 아래 한계 참고 |
| 인증 | BE `WorkerTokenFilter`: `Authorization: Bearer 토큰`, 토큰 32바이트 미만이면 BE가 **시작을 거부**, 비교는 상수 시간, 토큰이 없거나 설정이 비어 있으면 모든 `/internal/**`가 401(안전한 쪽으로 닫힘) | **실질적인 보호.** 코드를 읽어 확인함 |
| 전송 | HTTPS(443)만. 토큰이 평문으로 가지 않는다 | 워커가 `https://`만 쓰는 것이 전제 |
| 크기 | 8MiB(이 경로), BE 결과 JSON 5MiB | 자원 보호 |
| 로그 | 워커 API와 서명 URL 스토리지 경로의 Nginx 접근·오류 로그를 끈다. BE·스토리지 메트릭으로 진단한다 | 설정 반영. 서버 적용 전 |

**한계 (정직하게)**
- **IP 허용은 인증이 아니다.** 교내 공인 IP는 같은 망의 다른 장비·사용자도 쓸 수 있어서(NAT), 이 IP에서 오는 다른 요청은 403을 받지 않고 BE의 토큰 검사까지 간다. 그래서 **토큰이 사실상 유일한 보호**이고, IP는 인터넷 전체에서 오는 시도를 줄이는 한 겹이다. 토큰이 32바이트 이상 난수라 추측으로는 뚫기 어렵다.
- **토큰이 유출되면** 같은 교내 IP에서 작업을 가로채거나 결과를 위조할 수 있다. 교체는 서버 `.env`의 `CHART_WORKER_CREDENTIALS` 값을 바꾸고 `api`를 다시 띄운 뒤 워커 쪽 값을 바꾸는 순서다. 옛 토큰은 `api` 재시작 순간부터 401이다.
- **교내 공인 IP가 바뀌면 워커가 403을 받아 멈춘다.** 알림이 없다. 워커 쪽에서 오류를 알아차려야 한다. IP는 `Infra/nginx/default.conf`에 있고 바꾸려면 MR과 배포가 필요하다.
- **403이 경로의 존재를 알려 준다**(다른 `/internal/`은 404). 알려져도 인증이 막는다.
- **요청 수 제한이 없다.** 같은 IP에서 다량의 잘못된 토큰을 보내는 시도는 막지 않는다(토큰 길이가 추측을 막고 BE는 상수 시간 비교를 쓴다). 필요해지면 `limit_req`를 이 location에 더한다.
- **음원이 공개 도메인을 지난다.** 서명 URL(서명·만료)이 보호하고 URL은 워커에만 간다. 단 음원 버킷의 버전 관리가 켜져 있으면 "처리 후 즉시 폐기"가 지켜지지 않으므로 `AUDIO_STORAGE_ENABLED`를 켜기 **전에** 비공개·버전 관리 꺼짐을 확인했다(2026-11-03, 6.2). 그 뒤 서버 `.env`에 `AUDIO_STORAGE_ENABLED=true`, `AUDIO_STORAGE_BUCKET=airdrum-tmp-audio`, `AUDIO_STORAGE_PRIVATE_BUCKET_CONFIRMED=true`를 넣고 `api`를 다시 만들어 `healthy`를 확인했다. `worker1` 토큰도 같은 날 서버에서 난수로 만들어 등록하고(컨테이너 환경에서 설정됨 확인) AI 담당자에게 직접 전달했다. 토큰 없는 `claim`은 401이다. **이 경로(`/internal/v1/chart-jobs/`)는 접근 로그를 끄고 있어(`access_log off`) 워커 요청이 Nginx 로그에 남지 않는다.** 출발지 IP는 이 절 끝의 방법대로 GPU 서버에서 토큰·쿼리 없이 `/health`를 요청해 일반 접근 로그에서 확인하고, 허용 IP와 일치하는지는 워커의 첫 요청이 403이 아닌지로도 본다.
- **반주 저장소 스위치(`CHART_ASSET_ENABLED`)가 꺼져 있으면 분리 결과 제출이 막힌다.** 워커 연결 뒤 `POST /internal/v1/chart-jobs/{id}/results/separation`이 `503 WORKER_UNAVAILABLE`로 계속 거절됐다(2026-11-03). BE는 이 스위치가 꺼져 있으면 반주 파일을 확정하는 쓰기 저장소를 만들지 않고, 결과 제출이 그 저장소를 못 찾으면 503을 돌려준다. 스위치를 켜기 전에 반주 버킷(`airdrum-accompaniments`)의 버전 관리가 꺼져 있고(`s3.bucket.versioning`이 `Unconfigured`) 익명 접근이 403인 것을 확인했다. 그 뒤 서버 `.env`에 `CHART_ASSET_ENABLED=true`를 넣고 `api`를 다시 만들었다. 이후 워커가 여러 작업(job 1~8)을 이어서 처리하고 있고 최근 로그에 503이 없다. 켜면 BE가 읽기 키 값이 비어 있을 때 시작을 거부하므로, 읽기 키가 설정돼 있다는 것도 함께 확인된다.

**토큰 운영 (3.6과 같은 원칙)**
- 토큰은 **서버에서 직접**, 화면에 출력하지 않고 만든다: `umask 077` 후 `openssl rand -hex 32 > /안전한/경로/worker-token`, `chmod 600 /안전한/경로/worker-token`(64자, 특수문자가 없어 `.env`에서 안전). 다른 파트가 만든 값을 채팅·메일로 받지 않는다. BE는 `.env`의 값을 읽을 뿐이라 값을 알 필요가 없다.
- 워커를 돌리는 사람에게는 비밀번호 관리자나 직접 전달로만 주고, GPU 서버의 설정 파일은 소유자만 읽게 한다(권한 600). 문서·회신·Jira·MR에 값을 적지 않는다.

**반영 뒤 확인 (값이 아니라 응답 코드로)**
- 허용된 GPU 서버에서 토큰 없이 `POST /internal/v1/chart-jobs/claim` → **401**(Nginx를 지나 BE 인증까지 닿음)
- 다른 IP에서 같은 요청 → **403**
- 어디서든 `/internal/` 아래의 다른 경로 → **404**
- 워커 경로의 접근 로그는 비활성화되어 있다. GPU 서버에서 토큰·쿼리 없이 `/health`를 요청하고 일반 접근 로그에 실제 공인 출발지 IP가 표시되는지 확인한다. 허용 IP의 워커 요청이 BE 인증까지 도달하는지는 응답 코드로 확인한다.

## 16. ZAP 웹 취약점 분석 (2026-11-02)

OWASP ZAP 2.17.0으로 운영 도메인(`https://k15a307.p.ssafy.io`)을 **수동 탐색(passive)** 으로 분석했다. 직접 화면을 눌러 보며 오간 요청과 응답만 검사했고, 공격 요청을 보내는 스캔(active, fuzz)은 하지 않았다. 점검 대상은 **v2.0 배포 전의 운영 버전**이다. 점검 이후 `main`에는 v2.0이 들어갔으므로 배포 뒤에 같은 방법으로 다시 본다. 아래 헤더 조치는 `Infra/nginx/default.conf`에 **설정으로 반영**했고 로컬 시험으로 확인했지만, **운영 서버에는 아직 적용하지 않았다**(배포 뒤 응답 헤더로 확인한다).

**방법과 범위**
- 본인 소셜 로그인 계정으로 로그인한 상태를 포함해 화면을 직접 사용했다. 로그인 자체는 프록시를 거치지 않는 창에서 먼저 하고, 로그인된 브라우저 프로필을 ZAP 프록시를 켜고 다시 열었다. 소셜 계정 비밀번호가 ZAP 기록에 남지 않게 하려는 것이다. 소셜 제공자 쪽 로그인 구간은 우리 소관이 아니라 범위 밖이다.
- ZAP은 세션을 저장하지 않고 닫았고, 사용한 임시 브라우저 프로필은 지웠다. 보고서는 저장소 밖에 둔다. 로그인한 요청의 쿠키·토큰이 근거에 섞일 수 있어 저장소에 올리지 않는다.
- **이 수동 분석에서 확인하지 않은 것:** 공격 스캔과 권한이 다른 계정으로의 접근 제어(IDOR), 로그인 구간의 취약점. 운영 서버에 공격 스캔을 돌리면 실제 DB에 데이터가 쌓이고 서비스에 부하가 걸려, 공격 스캔은 **로컬에 띄운 환경에서 따로 했다**(아래 "공격 스캔").

**결과 요약:** 경고 11종. 위험 높음 0, 중간 4, 낮음 3, 정보 4.

**조치 (설정 반영, 서버 적용 전)**

헤더 조치 1~3과 5(Permissions-Policy)는 `Infra/nginx/default.conf`에 반영했다. 4(폰트)는 FE에 `mail`로 요청해 2026-11-03에 회신을 받았고, 합의 내용은 아래 "조치 계획"에 적었다. 폰트 관련 설정(CSP의 `cdn.jsdelivr.net` 제거, `font-src 'self'`, `/fonts/` 캐시)은 FE 이전이 배포되기 전까지 넣지 않는다.

**로컬 시험(2026-11-02):** 앞단 Nginx 설정을 그대로 쓰고 뒤쪽을 스텁 컨테이너로 바꿔 응답 헤더를 확인했다. `web` 스텁은 `FE/nginx.conf`를, `api` 스텁은 Spring처럼 `nosniff`·`X-Frame-Options`를 보내게 했다.
- `/`, `/api/*`, `/health`, 정적 파일에서 `Server: nginx`(버전 없음), `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, HSTS(`max-age=300`)가 **각각 한 번씩** 나간다. 뒤쪽이 같은 헤더를 보내도 `proxy_hide_header`가 지워서 값이 겹치지 않는다.
- `/models/*`는 `add_header`를 가진 location이라 상속이 끊겨 헤더를 따로 적었고, 시험에서 같은 헤더가 나가는 것을 확인했다.
- CSP는 `Content-Security-Policy-Report-Only`로 `/`와 `/api/*` 응답에 나가고, HTML이 아닌 `/models/*`에는 붙이지 않았다. 이 시험은 **헤더가 붙는지**만 본 것이다. CSP 위반 여부(실제 화면이 정책에 걸리는지)는 브라우저에서 화면을 눌러 보며 콘솔을 봐야 하고, 아직 하지 않았다.

**조치 계획 (순서)**
1. 부작용이 거의 없는 헤더부터: `server_tokens off`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`. 한 파일(`include`)로 모아 각 location에 넣는다. **Nginx는 location에 `add_header`가 하나라도 있으면 상위(server) 블록의 `add_header`를 상속하지 않는다.** `Infra/nginx/default.conf`의 `/models/`(Cache-Control을 붙이는 location)처럼 이미 `add_header`가 있는 곳은 공통 헤더를 따로 넣어야 한다. 이 상속 규칙을 몰라서 헤더가 빠지는 실수가 흔하다.
2. HSTS는 `max-age`를 짧게(5분~1일) 시작해 점차 늘린다. **`includeSubDomains`와 `preload`는 쓰지 않는다.** `ssafy.io`는 우리가 소유한 도메인이 아니라 같은 도메인의 다른 서비스에 영향을 줄 수 있다. 한 번 길게 건 HSTS는 브라우저에서 되돌리기 어렵다.
3. CSP는 바로 강제하지 않고 `Content-Security-Policy-Report-Only`로 먼저 넣어 위반을 본다. 웹 오디오·ONNX 모델(WASM)·블롭·웹 시리얼을 쓰는 앱이라 정책이 거칠면 화면이 깨질 수 있다. FE와 같이 본다.
4. **폰트 자체 호스팅(FE 회신, 2026-11-03 합의).** 폰트를 하나씩 옮기는 대신 규약을 정했다: 폰트는 전부 같은 출처에서만 서빙하고, 경로는 `/fonts/{패밀리}/{버전}/`, 내용이 바뀌면 버전 경로를 바꾼다(같은 URL의 내용은 고치지 않는다). Pretendard는 빌드 때 `node_modules`에서 복사하고 git에는 넣지 않는다. FE 이전은 다음 스프린트 초(`[EXTRA] 추가 작업` S15P31A307-289의 서브 작업)다. **Infra는 FE 변경이 배포된 뒤에** 한 번에 적용한다: CSP의 `https://cdn.jsdelivr.net` 제거와 `font-src 'self'`, `/fonts/`의 `Cache-Control: public, max-age=31536000, immutable`. 순서가 거꾸로면(버전 없는 기존 폰트에 장기 캐시가 먼저 걸리면) 파일을 바꿔도 브라우저가 1년간 옛 파일을 쓸 수 있다. 앞단 Nginx에서 `/fonts/`에 `add_header`를 쓰면 server 블록의 보안 헤더를 상속하지 못하므로 다시 적고, 뒤쪽(`FE/nginx.conf`의 `location /`)이 보내는 `Cache-Control: no-cache`와 겹치지 않게 `proxy_hide_header Cache-Control`을 함께 쓴다. `font-src`의 `data:`는 Report-Only에서 위반이 없는 것을 본 뒤 뺀다.
5. **Permissions-Policy:** `camera=(), microphone=(), geolocation=(), payment=(), usb=()`에 FE가 동의했다. 스틱 연결에 쓰는 **Web Bluetooth(`bluetooth`)와 Web Serial(`serial`)은 목록에 넣지 않고 앞으로도 막지 않는다**(이 둘이 없으면 센서가 연결되지 않는다. `usb`는 Web Serial과 별개 기능이다). `default.conf`의 server 블록에 추가했다(2026-11-03). `/models/*`는 HTML이 아니라 따로 적지 않았다. 문법 검사(`nginx -t`)와 응답 헤더(`/health`)는 로컬 컨테이너에서 확인했다.
6. **CSP 사전 정보(FE 실측):** 인라인 스타일이 31개 `.tsx` 파일(`style={...}`)에 있어 `style-src 'unsafe-inline'`은 유지한다. 반주 음원은 BE가 준 서명 URL을 `fetch`로 받으므로 그 도메인이 `connect-src`에 있어야 한다. 운영 음원 서명 URL의 공개 주소는 `https://k15a307.p.ssafy.io`(같은 출처, `connect-src 'self'`로 충분)로 확인했다(2026-11-03). 반주 음원용 `CHART_ASSET_PUBLIC_ENDPOINT`도 서버에서 확인했고(2026-11-03) `https://k15a307.p.ssafy.io`로 같은 출처다. 그래서 CSP에 추가할 외부 도메인은 없다.
   **CSP 차단 모드 전환 (2026-11-04):** `Content-Security-Policy-Report-Only`를 `Content-Security-Policy`로 바꿨다.
   - XSS로 주입된 인라인 스크립트를 브라우저가 실행하지 않는다(`script-src 'self'`에 `'unsafe-inline'` 없음). 가입 동의 API를 화면 없이 부른 시험에서 보았듯(18절) 쿠키가 붙은 대리 호출은 `HttpOnly`로 막을 수 없어 이 방어가 필요하다.
   - **CSP로 막히지 않는 것:** 개발자 도구 콘솔에 사용자가 직접 입력한 코드. 사용자가 본인 계정으로 API를 부르는 것은 막을 수 없고 막는 목표도 아니다. CSP가 막는 대상은 **다른 사람이 심은 스크립트**다.
   - 스틱 브리지(`ws://localhost:8765`, FE `WebSocketStickSource` 기본 주소)가 `connect-src 'self'`에 막히지 않게 `ws://localhost:*`, `ws://127.0.0.1:*`를 더했다.
   - **병합 전 FE 확인 목록** — 운영 화면에서 개발자 도구 콘솔을 열고 `[Report Only]` 위반 메시지가 없는지 본다(지금 운영은 Report-Only라 위반이 콘솔에 남는다): ① 로그인·가입 동의 ② 곡 목록·반주 재생 ③ 연주 화면·리포트 ④ 악보·내 곡 업로드 ⑤ 폰트(`cdn.jsdelivr.net`) ⑥ 채보 진행 WebSocket ⑦ **스틱 브리지**: 기본 주소가 아닌 다른 PC·다른 주소로 연결하는 설정이 있으면 그 주소가 `connect-src`에 막힌다(허용 주소를 더하거나 정책을 넓혀야 한다).
   - 위반이 있으면 병합하지 않고 정책을 고친다. 병합 뒤 문제가 생기면 `default.conf`의 헤더 이름을 `Content-Security-Policy-Report-Only`로 되돌려 배포한다(차단만 풀린다).
   - 확인하지 못한 것: 로그인한 상태의 실제 화면 전체. 이 PC에서는 열어 보지 못했다.

   **CORP 적용 (2026-11-04):** 모든 응답에 `Cross-Origin-Resource-Policy: same-origin`을 붙였다(ZAP 재검증의 "CORP 없음" 경고 대응).
   - 다른 사이트가 우리 응답을 `<img>`·`<audio>`·`<script>` 태그로 끌어가는 것을 브라우저가 거절한다. 다른 출처의 페이지가 그 응답을 자기 프로세스 메모리에 올리지 못하므로 Spectre 같은 부채널로 읽히는 위험도 줄인다.
   - **영향 없는 것:** 같은 출처의 `fetch`, `fetch`+CORS 요청(CORP와 별개), 브라우저가 아닌 클라이언트(GPU 워커 등). FE가 다른 사이트·서브도메인의 임베드, 공유 링크 미리보기(OG 이미지), `iframe`, `navigator.share`가 없음을 코드로 확인했다(`INFRA_보안헤더-CSP-화면확인` 회신 5).
   - 뒤쪽 서버가 같은 헤더를 보내 두 번 나가지 않게 `proxy_hide_header`로 먼저 지웠다. `/models/` 두 위치는 server 블록의 헤더를 물려받지 못해 따로 적었다.
   - 다른 사이트에 우리 이미지·음원을 보여 주는 기능(공유 미리보기, 임베드)이 생기면 그 경로만 `same-site` 또는 `cross-origin`으로 범위를 다시 정한다.
   - 시험: `test_upload_limits.py`가 고정 응답(`/health`), 모델 경로, 프록시 경로의 응답에 헤더가 정확히 한 번 있는지 본다. 이 PC에서는 포트를 열 수 없어 실행하지 못했고 `nginx -t`만 통과했다.

**공격 스캔 (로컬, 2026-11-02)**

`main` 코드로 `Infra/docker-compose.yml`의 최소 구성(`nginx`, `web`, `api`, `postgres`, `redis`, `seaweedfs`)을 로컬에 띄우고 ZAP(`zap-api-scan`, 공식 Docker 이미지)으로 공격 스캔했다. **운영 서버에는 어떤 요청도 보내지 않았다.** 환경은 로컬 전용 난수 비밀값을 쓰고 끝난 뒤 볼륨까지 지웠다. 소셜 로그인은 로컬에서 쓸 수 없어, 로컬 DB에 테스트 사용자를 넣고 로컬 `JWT_SECRET`으로 서명한 토큰(일반 2명, 관리자 1명)을 썼다. 대상 API는 BE의 OpenAPI 문서에서 가져온 53개다(로컬 `api`만 문서를 켰고 운영은 `SWAGGER_ENABLED=false`).

- **결과: 실패(FAIL) 0건.** 일반 사용자·관리자 각 1회, 경고 종류는 같다(높음 2건은 아래 오탐, 낮음·정보 위주).
- **SQL Injection 경고 2건: 오탐.** `POST /api/presets`의 `layout`·`sounds`에 대한 불리언 기반 탐지였다. ZAP이 이 필드를 객체가 아니라 문자열로 보내면 `1=1`, `1=2`, 원본이 모두 같은 `400`이었고, 올바른 형식으로 `' OR 1=1 --`를 이름에 넣으면 그 글자 그대로 저장됐다. 코드(`KitPresetRepository`)도 JPA 파생 쿼리와 파라미터 바인딩만 쓴다.
- **서버 오류(500)가 약 1,170건: 입력 검증 누락(BE에 알림).** 보안 취약점은 아니지만(응답 본문에 스택·내부 정보 없음) 클라이언트 오류가 서버 오류로 나간다.
  - 업로드 API(`songs/audio`, `songs/midi`, `admin/songs/*/cover·charts/midi·accompaniment`, `plays/*/raw`)에서 **본문이 끊기거나 형식이 깨진 multipart**가 `MultipartException`으로 `500`이 된다(`400`이어야 한다).
  - **검색어(`q`)에 NUL 문자(`%00`)** 를 넣으면 `GET /api/v1/sheets`·`/api/v1/songs`가 DB 오류(`invalid byte sequence`)로 `500`이 된다. 재현했다.
  - 영향: 오류 로그가 불어나고 모니터링 `5xx` 알림이 거짓으로 울릴 수 있다.
- **CSP 없음(5)·Permissions-Policy 없음·CORP 없음(낮음):** 대상이 `/internal/v1/chart-jobs/*` 같은 API 응답이다. CSP는 `Report-Only`로 넣어 ZAP의 "CSP 없음" 규칙(강제 CSP만 인정)에는 계속 걸린다. Permissions-Policy와 CORP는 웹 오디오·시리얼 같은 기능과 충돌할 수 있어 FE 확인 전에는 넣지 않았다(이후 Permissions-Policy는 FE와 값을 합의해 추가했다. 조치 계획 5. CORP는 FE 답을 받은 뒤 정한다).
- **Unexpected Content-Type(39), 4xx 응답, 캐시 지시:** 스캐너가 없는 경로를 불러 SPA의 HTML이 돌아온 것 등으로 조치 대상이 아니다.
- **URL에 `userId` 파라미터(정보):** 텔레메트리 API(`/api/telemetry/sessions`)의 `userId`는 관리자만 쓸 수 있고 일반 사용자는 `403`이다(아래 수동 점검).

**한계와 교훈**
- 스캔은 OpenAPI 문서에 있는 API만 다룬다. 문서에 없는 경로, WebSocket(`/ws/jobs/`), 워커 API(IP 허용 한 겹이라 로컬에서는 `403`)와 소셜 로그인 흐름, 업로드 **정상 파일의 내용 검증**(악성 파일·거대 파일의 실제 처리)은 점검하지 않았다.
- **첫 시도는 무효였다.** 탈퇴 API(`DELETE /api/users/me`)를 스캔 설정(`globalexcludeurl`)으로 제외하려 했지만 적용되지 않았고, ZAP이 테스트 사용자를 탈퇴시켜 이후 요청 약 2만 건이 `401`로 끝났다. 이 결과는 버리고 **문서에서 그 작업을 빼서** 다시 돌렸다. 교훈은 두 가지다. 파괴적인 API는 설정 제외에 의존하지 말고 입력(문서)에서 뺀다. 그리고 **"실패 0건·통과 N개"만 보지 말고 응답 코드 분포(`401` 비율)와 테스트 계정의 상태를 확인해 스캔이 실제로 인증된 요청이었는지 본다.**
- 로컬 환경은 `ssaplash-local` 프로젝트로 분리했고 끝난 뒤 `docker compose down -v`로 지웠다. 보고서는 저장소 밖에 둔다.

**수동 공격 재현 (로컬, 2026-11-03, curl로 직접 실습)**

ZAP 자동 스캔과 별개로, 같은 로컬 환경(`victim`/`attacker`/`admin` 3계정, 로컬 `JWT_SECRET`으로 서명한 토큰)에서 대표 공격을 curl로 하나씩 직접 보내 응답을 확인했다. 목적은 자동 스캔 결과를 손으로 재현해 어느 코드가 막는지 이해하는 것이다.

| 번호 | 공격 | 명령 요지 | 결과 | 판정 |
| --- | --- | --- | --- | --- |
| 1 | 토큰 없이 보호 API 호출 | `GET /api/presets` (Authorization 없음) | `401` | 정상 방어 |

**BE 수정 (로컬, 2026-11-03) — 완료**

깨진 multipart와 NUL 문자 입력이 `500`이 되던 결함을 고쳤다.

- `NulParameterFilter`(신규, `common/error`): 요청 파라미터에 NUL 문자(`\u0000`)가 있으면 컨트롤러·DB 전에 `400 INVALID_INPUT`으로 거절한다. multipart 요청은 검사하지 않는다(멀티파트 파싱 전에 `getParameterMap()`을 부르면 본문 스트림을 먼저 소모해 이후 파싱이 깨질 수 있어서).
- `GlobalExceptionHandler`에 `MultipartException`(경계 없음·크기 초과 포함) 핸들러를 추가해 `500` 대신 `400 INVALID_INPUT`으로 매핑했다.
- **검증:** curl 재현(위 6·6-2번)이 `400`으로 바뀐 것을 확인했고, 정상 검색어는 그대로 `200`(회귀 없음). 신규 테스트(`NulParameterFilterTest` 4개, `GlobalExceptionHandlerTest`의 멀티파트 케이스)가 통과한다. 전체 테스트는 수정 전후로 같은 4개 클래스만 실패하며, 이는 이 PC의 외부 자원(ffprobe·소켓 바인딩) 제약으로 이번 수정과 무관함을 수정 전 코드로 같은 테스트를 돌려 확인했다.

**재검증 — ZAP Active Scan 재실행 (로컬, 2026-11-03)**

위 BE 수정이 반영된 `api`를 재빌드하고, 같은 로컬 환경에서 Active Scan을 일반 사용자(attacker, id 2)·관리자(admin, id 3) 토큰으로 각각 다시 돌렸다. OpenAPI 문서는 실행 중인 `api`에서 새로 받았고, 탈퇴 API(`DELETE /api/users/me`)는 지난번 교훈대로 다시 입력 문서에서 뺐다.

| 항목 | 2026-11-02(수정 전) | 2026-11-03(수정 후) |
| --- | --- | --- |
| 서버 오류(500) | 약 1,170건 | **0건** |
| FAIL-NEW | 0 | 0 |
| SQL Injection 경고 | 2건(오탐) | 3건(같은 오탐, `POST /api/presets`) |
| CSP·Permissions-Policy 없음 | 있음(`/internal/*` 응답) | 그대로(FE 확인 대기, 변화 없음) |
| Cross-Origin-Resource-Policy(CORP) 없음 | 기록 안 함 | **신규 발견**: `/api/v1/sheets`·`/api/v1/plays`·`/api/auth/logout`·`/api/presets`·`/api/v1/songs` 등 7~8건 |

- **500이 완전히 사라졌다.** NUL 문자·멀티파트 깨짐을 ZAP이 자동으로 수천 번 변형해 두드려도 서버가 더 이상 죽지 않는다는 걸 자동 스캔으로도 확인했다.
- **관리자 토큰 스캔에서도 추가 경고 없음.** 일반 사용자와 같은 5종, 수가 조금 늘어난 건(7→8) 관리자만 호출 가능한 API가 스캔 대상에 하나 더 포함된 정도다.
- **CORP 헤더 없음은 새로 짚힌 항목이다.** 다른 출처가 우리 API 응답을 가져다 쓰는 걸 브라우저 단에서 막는 2차 방어 헤더(Spectre류 사이드채널 완화 목적)다. 지금 CORS가 1차로 막고 있어 긴급하지 않으나, Permissions-Policy와 같은 이유로 FE가 다른 출처에서 이 응답을 끌어다 쓰는 경우(iframe, 다른 서브도메인 등)가 없는지 확인한 뒤 `same-origin`으로 넣는다.

**후속**
- 변경 적용 뒤 같은 방법(수동 탐색, 로그인 포함)으로 다시 분석해 경고가 줄었는지 본다. 보안 헤더가 실제로 붙었는지는 응답 헤더로 직접 확인한다.
- Permissions-Policy는 FE와 값을 합의해 추가했다(조치 계획 5). CORP는 다른 출처가 우리 응답을 태그로 끌어 쓰는 기능이 없는지 FE 답을 받은 뒤, `/api/`에 `same-origin`을 넣을지 정한다.
- 이번 분석은 **운영에서 확인한 사실(수동 분석)** 과 **로컬에서 확인한 사실(공격 스캔·수동 공격 재현·재검증)** 을 나눠 적었다. 위 헤더 조치는 설정만 바뀌고 아직 서버에 반영되지 않았으므로 "적용함"으로 쓰지 않는다.

## 17. API 응답 압축(gzip)과 녹음 저장 한도 (2026-11-03)

BE의 녹음 상세 응답이 최대 약 3.5MB(타격 배열 JSON)라 앞단 Nginx에 응답 압축을 넣었다(REC-001, `Infra/nginx/default.conf`). 같은 변경에서 `POST /api/v1/recordings`의 본문 한도 5 MiB와 413 응답도 추가했다.

- **압축 범위:** API JSON(`application/json`, `application/problem+json`)이 1 KiB 이상일 때만, 압축 수준 5. 프론트 정적 파일은 FE 컨테이너(`FE/nginx.conf`)가 이미 압축하고, 프록시 응답에 `Content-Encoding`이 있으면 앞단은 다시 압축하지 않는다. 음원·이미지·모델은 이미 압축된 형식이라 제외했다. 요청 본문 압축은 BE가 받지 않는다(400).
- **BREACH(압축을 이용한 정보 추출) 검토:** HTTPS 응답을 압축하면, 같은 응답에 비밀 값(토큰 등)과 공격자가 넣은 입력이 함께 반사되고 공격자가 응답 크기를 관찰할 수 있을 때 비밀 값을 한 글자씩 추정할 수 있다. BE의 설명으로는 사용자 입력을 그대로 되돌리는 응답이 토큰 응답과 겹치지 않는다. 토큰 응답(`/api/auth/*`)은 JWT 한 개 수준이라 1 KiB보다 작아 압축되지 않을 것으로 보지만, **실제 크기는 확인하지 않았다.** 그래서 별도 location으로 제외하지 않았다. 토큰 응답이 커지거나 입력을 반사하는 필드가 생기면 `/api/auth/`에 `gzip off`를 넣는다.
- **로컬 시험(포트를 열지 않고 컨테이너 안에서 확인):** 합성 JSON 278,172바이트가 압축 요청에서 31,497바이트로 줄었다. 합성 데이터는 반복이 많아 실제 녹음은 이보다 압축률이 낮을 수 있다. `Content-Encoding: gzip`과 `Vary: Accept-Encoding`이 붙고, 1 KiB 미만 응답과 `/health`는 압축되지 않으며, 보안 헤더는 그대로다. 녹음 저장은 5 MiB는 200, 5 MiB + 1바이트는 413 `RECORDING_TOO_LARGE`(`application/problem+json`)이고, `/api/v1/recordings/{id}`는 기본 1 MB 한도를 유지한다. `Infra/nginx/test_upload_limits.py`에 케이스를 추가했지만 이 PC에서는 Python이 없고 포트 바인딩이 막혀 스크립트 자체는 돌리지 못했다.
- **운영에서는 아직 확인하지 않았다.** 병합과 배포 뒤 실제 녹음 상세 응답의 크기 감소와 `Content-Encoding`을 `curl`로 확인한다.

## 18. 가입 동의 API의 화면 우회와 XSS 영향 (2026-11-04)

**발견:** 로그인한 브라우저의 개발자 도구 콘솔에서 두 요청만으로 동의 화면 없이 가입을 완료할 수 있었다.
1. `POST /api/auth/refresh`(`credentials: same-origin`)로 액세스 토큰을 받는다. 로그인 쿠키는 `HttpOnly`라 스크립트가 읽지는 못하지만, 같은 출처에서 `fetch`하면 **브라우저가 쿠키를 대신 실어 보낸다.**
2. 그 토큰으로 `POST /api/users/me/signup-consent`를 직접 부르면 서버가 저장하고 `signupCompleted`가 `true`가 된다.

**원인 (코드를 읽어 확인, develop-BE):**
- `SignupGateFilter`의 허용 목록(가입 미완료 회원도 부를 수 있는 요청)에 `POST /api/users/me/signup-consent`와 `POST /api/auth/refresh`가 들어 있다. 가입 동의는 화면이 아니라 이 API로 끝나도록 설계돼 있다.
- `SignupConsentRequest`는 약관·개인정보 판(`termsVersion`, `privacyVersion`, `dataConsent.version`)에 `@NotBlank @Size(max=50)`만 검사하고, `SignupConsentService`는 "판은 비교·해석하지 않고 저장만 한다"고 주석에 적은 대로 **어떤 문자열이든 저장한다.**

**영향 (정직하게):**
- **권한 상승·타인 계정 접근은 아니다.** 본인 계정에 본인이 동의를 저장한 것이다.
- **동의의 증거 가치가 약하다.** 서버는 사용자가 약관 화면을 보았는지 알 수 없고, 현재 판이 아닌 값이나 존재하지 않는 판으로도 저장된다. 나중에 "어떤 약관에 동의했는가"를 서버 기록만으로 입증하기 어렵다.
- **XSS 피해의 크기를 보여 준다.** 같은 코드를 XSS로 주입하면 피해자 몰래 피해자 계정으로 그 계정이 할 수 있는 모든 API를 부를 수 있다. `HttpOnly`는 쿠키를 읽는 것을 막을 뿐 **쿠키가 붙은 요청을 보내는 것은 막지 못한다.** 가입 동의는 그 한 예일 뿐이다.
- 시험한 환경(로컬·운영)과 운영 계정에 동의가 저장됐는지는 **아직 확인하지 못했다.**

**대응 방안 (우선순위):**
| 순서 | 대응 | 막는 것 | 상태 |
| --- | --- | --- | --- |
| 1 | **CSP를 차단 모드로 전환**(`script-src 'self'`): 주입된 인라인 스크립트를 브라우저가 실행하지 않는다 | XSS로 인한 대리 호출 전반 | 현재 `Content-Security-Policy-Report-Only`. FE 화면 확인 후 전환(16절) |
| 2 | **서버가 약관·개인정보 판을 검증**: 허용된 현재 판만 저장한다 | 존재하지 않는 판·옛 판으로 저장되는 것 | 설계 중. 허용 판 목록을 설정으로 두면 FE 판 변경 때 배포 순서를 맞춰야 한다 |
| 3 | 재인증이 필요한 동작(탈퇴 등)을 더 좁게 보호 | 한 번의 XSS로 계정 파괴 | 소셜 로그인이라 이번 범위 밖 |

**한계:** 서버 검증(2)은 사용자가 스스로 스크립트로 부르는 것을 막지 못한다. 본인 계정에 대한 호출을 막을 방법은 없고, 막는 목표도 아니다. 이 항목의 목적은 (가) 저장되는 판 값이 유효하게 하는 것과 (나) 다른 사람이 심은 스크립트의 영향을 줄이는 것이다.

## 19. 곡 추천 R3 후보 배치: 동의·가명·접근 권한 (2026-11-05)

곡 추천 모델(R3)은 사용자별 연주 기록으로 학습한다. 연주 기록 활용 동의와 목적이 달라 별도의 선택 동의를 받고, AI 쪽에 사용자 신원이 가지 않게 했다. **코드만 준비된 상태이고 기능은 꺼져 있다.**

| 구간 | 하는 일 | 지키는 것 |
| --- | --- | --- |
| FE → BE | 선택 동의 저장. 기본 미동의, 설정에서 철회 | 거절해도 모든 기능을 쓸 수 있다 |
| BE → 뷰 | `recommend_*_v`: 동의한 ACTIVE 사용자와 공개 공용 곡만 | 뷰가 곧 허용 목록(V37), `security_barrier` |
| 뷰 → 배치 | 읽기 전용 계정으로 뷰만 읽음. 파일로 남기지 않음 | 원본 테이블 권한 없음, 한 스냅숏, 허용 밖 열이 있으면 행을 읽지 않음 |
| 배치 → BE | 사용자 키와 곡 id 목록만 적재. 내부 네트워크, 토큰 인증 | 알 수 없는 사용자와 미동의 사용자는 버림 |
| BE → 응답 | 동의, 롤아웃, 모델, 낡음을 다시 확인 | 하나라도 어긋나면 규칙 추천 |

- **동의 확인 3단계:** 뷰, 적재, 서빙 세 곳에서 따로 확인한다. 한 곳이 뚫려도 미동의 사용자의 학습이나 노출로 이어지지 않게 하려는 것이다.
- **철회·탈퇴:** 후보 행을 같은 트랜잭션에서 지우고 다음 읽기부터 뷰에서 빠진다. 철회는 판 검사를 건너뛰어 옛 판 화면에서도 막히지 않는다. 생성 후 7일이 지난 후보는 한 시간마다 지운다. `consent=false` 세션은 학습 입력에서 뺀다(V42). 동의 이력은 응답마다 추가하고, 철회·탈퇴일부터 2년 뒤 지운다(V43). AI 계정에는 권한이 없다. 적재 중에는 동의 행과 회원 행을 잠가 철회와 겹쳐도 후보가 남지 않는다. 이미 학습에 반영된 값은 개인별로 찾아 지울 수 없어 동의 문구에 적어야 한다.
- **가명 키:** `user_key`는 동의할 때 만드는 무작위 값이다(V45). 처음에는 비밀 값 해시였는데, 뷰가 세션 설정을 읽어야 해서 배치 계정이 비밀 값을 볼 수 있었고 `user_id`가 작은 정수라 전수 대입이 됐다. HMAC으로 바꿔도 같은 문제라 값을 계산하지 않는 방식으로 바꿨다. 대응표는 뷰만 읽고 배치 역할에는 권한이 없다. 철회·탈퇴하면 지운다. 대응표는 앱 DB 백업에 들어가지만, 그 백업에는 이미 원본 연주와 `user_id`가 있다.
- **외부 노출을 늘리지 않았다:** 처음에는 GPU 서버에서 돌리려고 SSH 터널과 Nginx IP 허용을 계획했다. 배치에 GPU가 필요 없어 앱 서버 내부 컨테이너로 바꿨다. 공개 Nginx의 `/internal/` 404 규칙과 DB 포트는 그대로다.
- **진행 중 배치와 철회:** 철회 전에 읽은 기록은 배치가 끝날 때까지 메모리에 남는다. 전체 시간 제한(기본 1시간)으로 최대 시간을 보장하고, 철회한 사용자의 후보는 적재에서 버려진다.
- **컨테이너 격리:** 평소에는 뜨지 않고 내부 네트워크만 쓴다. `cap_drop: ALL`, `no-new-privileges`, 메모리 2GiB.
- **출력:** 표준 출력과 MLflow에는 개수와 해시만 남는다. 사용자 키, 사용자 벡터, 접속 문자열, 토큰은 남기지 않는다. 뜻밖의 오류는 예외 종류만 출력한다.

**한계·남은 점검 (정직하게)**

- **서버에서는 일부만 확인했다.** 표 권한과 비밀 값 제거는 20절대로 확인했다. 계정 생성, 실제 DB 연결, 토큰, 공개 경로 차단은 아직 시험하지 않았다. 켜기 전 점검표는 `README.md`의 "곡 추천 R3 후보 배치"에 있다.
- **토큰 범위가 넓다:** 워커 토큰 필터는 경로를 가리지 않아 `recommend-batch` 토큰으로 채보 워커 API도 부를 수 있다. 내부 네트워크에서만 쓰여 위험을 받아들였고, 경로별 토큰은 후속 과제다.
- **비밀 값은 `docker inspect`에서 보인다:** 환경 변수로 전달하는 다른 값과 같은 수준이다(14절).
- **가명은 익명이 아니다:** BE는 대응표로 사용자를 되찾을 수 있고, 연주 이력 자체가 개인 특성일 수 있다. 동의가 필요한 이유다.
- **교체 주기 미정:** 제안은 유출이 의심될 때와 연 1회다. 바꾸는 절차는 `README.md`에 있다.
- **동의 문구 미확정:** 켜기 전에 약관 담당 검토가 필요하다.

## 20. 추천 동의 문구와 실제 동작 대조 (2026-11-06)

약관 담당의 문구안을 코드와 하나씩 대조했다. **문구는 구현의 약속이다.** "7일 뒤 삭제"라고 쓰려면 삭제 코드가 있어야 한다. 코드를 읽어 찾은 내용이고, 실제 경합이나 서버 동작을 재현한 것은 아니다. 상세 판단은 사용자의 개인 검토 문서에 있다.

| # | 발견 | 위험 | 처리 | 상태 |
| --- | --- | --- | --- | --- |
| 1 | 후보 삭제 코드가 없고 서빙만 막음 | 문구와 다르고 행이 무기한 남음 | 한 시간마다 만료 후보 삭제 | 배포함. 후보가 없어 삭제 동작은 못 봄 |
| 2 | 탈퇴와 적재가 겹치면 후보가 남을 수 있음 | 지울 경로가 없는 행 | 적재가 회원 행도 잠금 | 배포함. 동시 실행 시험은 못 함 |
| 3 | 철회에도 판 검사를 함 | 판이 바뀌면 옛 화면의 철회가 422로 막힘 | 철회는 판 검사 생략 | 배포함 |
| 4 | `consent=false` 세션이 R3 학습에 들어감 | 학습 활용에 동의하지 않은 기록 사용 | 뷰에서 제외(V42) | 배포함. V42 적용 확인 |
| 5 | 철회 뒤 노출 기록이 90일 남음 | R3 평가 근거로 쓰일 수 있음 | 철회 전 기록만 집계로 평가하기로 결정 | 문서만. 약관 검토 대기 |
| 6 | 실데이터 평가가 CSV 폴더를 읽음 | "파일 미저장" 문구와 충돌 | 뷰에서 메모리로 읽고 P2 CSV 입력 차단 | 배포함. 실제 DB 실행은 전 |
| 7 | 배치 계정이 가명 비밀 값을 읽음 | `user_id` 전수 대입으로 키와 사용자 대응 | 무작위 대체 키(V45) | 확인함. 배치 역할은 표를 못 읽고, 역할 설정과 `.env`에 비밀 값 없음 |
| 8 | 배치 전체 시간 제한이 없음 | 철회자 기록이 메모리에 남는 시간을 말할 수 없음 | 기본 1시간 제한 | 배포함. 실제 시간 초과 시험은 전, 값은 실측 필요 |
| 9 | 문구가 바뀌어도 옛 판 동의자가 학습에 쓰임 | 항목이 늘면 동의 범위 초과 | 아직 처리 안 함. 지금은 공개 동의가 없다 | 미처리 |
| 10 | 백업 보관 기간이 없음 | 지운 정보가 복원으로 되살아남 | 30일 보관, 재처리 절차 | 문서 반영. 만료 백업 없음 확인, 복원 시험은 전 |
| 11 | 동의 이력이 없음 | 철회하면 무슨 판에 동의했는지 사라짐 | 이력 표, 철회·탈퇴일부터 2년 보관 | 배포함. V43 적용 확인, 이력 0건 |
| 12 | 필수 동의 문구는 탈퇴 시 연주 기록 삭제인데 동의 세션이 남음 | 이미 받는 동의와 동작 불일치 | 세션을 지우고 MLflow 집계만 남김 | 배포함. 탈퇴 세션 0건 |

**가명에서 익명 집계로 바꾼 이유:** 처음에는 탈퇴 기록을 가명 처리해 2년 보관하기로 했다. 가명 정보는 개인정보라 철회 뒤 보관 근거가 따로 필요했다. 탈퇴 기록의 목적이 통계라서, 원본을 지우고 이미 있는 MLflow 집계(행 단위 값 없음, 5개 미만 셀 가림)만 남기기로 했다. 새 집계 표는 만들지 않았다. 보정은 타격 행으로 다시 계산해서 고정 집계를 쓸 수 없고, 쓰는 곳 없는 데이터를 쌓지 않기 위해서다.

**남은 위험**

- **법 조문은 비공식 사이트로 확인했다.** 인용 전에 국가법령정보센터에서 다시 확인한다. 법률 자문을 받은 내용이 아니다.

## 21. 실시간 코칭 판단 기록과 서버 모델 배포 구조 (2026-11-09~10)

실시간 코칭이 놓침 원인을 고르고, 작은 모델로 지적을 거르고, 앞으로 모델을 서버에서 받아 실험군으로 비교하게 되면서 생긴 보안·개인정보 항목이다. 설계는 `COACH-001` 원인 코칭 설계 문서다.

**플레이 로그에 남는 판단 기록**

| 태그 | 담는 것 | 담지 않는 것 |
| --- | --- | --- |
| 지적 행 | 상태 키(예: `LIVE_PAD_MISS:SMALL_TOM`), 로그용 문장, 고른 원인 | 사용자 id, 기기 정보 |
| `LIVE_CAUSE` | 원인 후보(원인·강도·패드·출발 패드·대신 친 패드), 고른 원인, 고른 주체(`RULE`), 판정 단계 | 원본 타격, 시각 외 개인 특성 |
| `LIVE_GATE_*` | 거름 점수, 문턱, 모델 이름(`이름@버전`), 실행 방식, 계산 시간, 실험군 | 입력 값(지표 벡터) |
| `LIVE_ARM` | 배정된 실험군 이름(규칙만이면 `rule`). 판 시작에 한 건 | 사용자 id, 배정에 쓴 해시 값 |

- 기록은 연주 세션의 `live_coach_events`(JSON)에 들어간다. 탈퇴하면 세션과 함께 지워진다(20절의 탈퇴 세션 삭제와 같은 경로).
- BE 검증 한도(태그 64자, 문장 2,048자, 1,000건)는 거름 기록에 대해 FE 시험으로 확인한다. `LIVE_CAUSE`는 후보가 많아야 4개라 한도 안이지만 따로 시험하지는 않았다.
- **학습 활용은 동의 세션만**으로 정했다(설계 U5, 14절 보정 뷰와 같은 기준). 기록 자체는 동의와 무관하게 남는다. 지적이 얼마나 맞았는지는 서비스 품질 확인이라 남기고, 모델 학습에 쓸 때만 동의를 거른다. 학습용 뷰는 아직 없다.

**서버 모델 배포(구현함 2026-11-10, 서버 게시 전)**

FE `coach/live/models`, AI `coach_live_model`(`--register`, `experiment`), 절차는 `Infra/mlflow/README.md`. 매니페스트의 이름·버전·파일 경로는 게시 도구와 같은 허용 문자 규칙으로 다시 검사해 경로 이동 문자열(`..`)을 받지 않는다. 가중치는 입력 수에 맞는 모양인지까지 확인한다.

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 모델 파일 검증 | 매니페스트의 `sha256`과 크기가 다르면 쓰지 않는다 | 전송 중 손상·중간 교체를 거른다 |
| 입력 버전 | `meta.json`의 `featureVersion`이 FE가 아는 값과 다르면 쓰지 않는다 | 입력 계산이 다른 모델이 엉뚱한 판단을 내리는 것을 막는다 |
| 실패 시 | 규칙만으로 동작한다. 실행 실패나 100ms 초과는 `FALLBACK`으로 남긴다 | 모델이 없어도 코칭과 연주가 멈추지 않게 |
| 실험군 배정 | 로그인 사용자는 사용자 id 해시로 0~99 구간, 비로그인은 판마다 무작위 | 같은 사람이 같은 모델을 계속 받게. 로그에는 실험군 이름만 남긴다 |

**한계 (정직하게)**

- **`sha256`은 서명이 아니다.** 매니페스트와 모델 파일이 같은 서버에서 나오므로, 서버가 침해되면 둘 다 바꿀 수 있다. 막는 것은 손상과 섞임이지 의도적 교체가 아니다. 게시는 서버의 `publish-model`로만 하고, 서명은 후속 과제다.
- **개인화(곡 수 단계)의 동의 근거를 확인하지 못했다.** 사용자 자신의 기록으로 코칭하는 처리지만, 가입 약관(`signupTerms.ts`)에는 개인 코칭 목적이 없고 `privacy`는 시안이다(설계 U11). 개인화 구현(P1) 전에 닫는다.
- **원인 문구는 근거가 약해도 화면에 나간다.** 합성 시험에서 원인 없는 연주의 12%가 패드 이동으로 골렸다(처음 55%에서 비교 조건으로 줄임). 틀린 지시는 보안 문제는 아니지만, 운영 `LIVE_CAUSE`로 다시 확인한다.

**연주 중 LLM 구간 코칭 (2026-11-10, 구현함·서버 적용 전)**

연주 중 마디 구간이 끝날 때 구간 요약을 BE를 거쳐 교내 GPU 서버의 로컬 LLM(리포트 총평과 같은 모델)에 보내고, 안내 칸 문구를 받아 띄운다. 설계는 `COACH-001` 연주 중 LLM 코칭 설계, 계약은 `AI/docs/live-coach-llm.md`.

| 항목 | 결정 |
| --- | --- |
| 보내는 것 | 구간의 판정 개수, 타이밍 요약, 문제 패드 최대 3개, 약한 손, 규칙 지적·원인, 직전 구간 판정 수와 직전 문구. 타격 원본·`playId`·곡 정보·회원 번호는 보내지 않는다(워커가 받는 사실에도 사용자 번호가 없다) |
| 어디로 | 우리 BE의 작업 큐 → 교내 GPU 서버 워커(pull). 외부 API로 나가지 않는다 |
| 얼마나 남나 | 큐 행은 5분 뒤 지운다. 조회는 60초까지. 문구는 플레이 로그 `LIVE_LLM`에만 남고, 그 로그는 연주 세션과 함께 탈퇴 시 지워진다 |
| 누가 쓰나 | 로그인 사용자만. 판당 10번, 사용자당 1분 6번 상한(429). 남의 요청 결과는 404 |
| 워커 경로 | `^~ /internal/v1/live-coach-jobs/`는 채보·총평 워커와 같은 GPU 서버 IP 허용과 BE 워커 토큰. 본문 16 KiB |
| 출력 검증 | 워커 가드레일(길이, 숫자·금지어·외국 글자, 키보드면 스틱 표현, 사실 밖 패드, 반복)과 BE 길이·제어 문자 검사 |
| 켜기 | BE `LIVE_COACH_LLM_ENABLED`(기본 꺼짐)와 실험 설정 `llm` 둘 다 켜야 한다. 처음은 `shadow` |

- **한계:** 큐는 사용자 번호와 구간 사실을 5분 동안 DB에 둔다(상한 계산용). 모델 출력은 가드레일이 잡는 것만 거르고, 사실과 어긋난 내용(예: 잘 친 패드를 지적)은 운영 `LIVE_LLM`을 사람이 읽어 확인해야 한다. 개인정보 처리 목적에 "연주 중 코칭 문구 생성"이 들어가는지는 약관 검토 항목이다(설계 U7).
