# 인프라 트러블슈팅 기록

인프라 작업(CI 러너, Docker Compose, 서버, 스토리지, 배포, 모니터링)에서 실제로 겪은 문제와 해결을 모았다. 같은 증상을 다시 만났을 때 원인을 빨리 좁히고, 같은 실수를 반복하지 않기 위한 기록이다.

- 기간: 2026-10-19 ~ 2026-10-23
- 각 항목은 **증상 → 원인 → 해결 → 재발 방지** 순서다. 원인을 확정하지 못한 항목은 "원인 미확인"으로 표시했다.
- 비밀값(토큰, 키, 비밀번호)은 적지 않았다.

## A. CI·러너

### A1. Windows 러너 초기 설정 문제
- **증상:** 러너가 `pwsh`를 찾지 못함, 한글이 들어간 스크립트가 구문 오류, `Filename too long`, `.gitlab-ci.yml`이 YAML 오류.
- **원인:** 러너 PC에 PowerShell 7이 없었고, Windows PowerShell 5.1은 한글 인코딩 문제가 있었다. Gradle 캐시 경로가 Windows 경로 길이 제한을 넘었다. `echo` 문자열 안의 `: `(콜론+공백)를 YAML이 키로 해석했다.
- **해결:** PowerShell 7 설치, `core.longPaths` 활성화와 빌드 경로 단축, 문자열의 콜론을 다른 문구로 변경.
- **재발 방지:** YAML 문자열에 `: `를 넣지 않는다. 긴 경로 문제는 Linux 러너로 옮겨 근본적으로 없앴다(A2).

### A2. BE 테스트가 `Bad address: listen`으로 실패
- **증상:** `be-test`, `be-timescale-test`가 `java.net.SocketException: Bad address: listen`으로 실패하고 간헐적으로 통과했다. 같은 코드를 러너 PC에서 직접 돌리면 통과했다.
- **원인:** 처음에는 테스트 태스크의 `systemProperty`가 늦게 적용된다고 추정했으나 틀렸다. 실패한 잡의 Gradle 데몬 실행 명령에 `-Djava.net.preferIPv4Stack`이 **없었다.** `gradle.properties`의 `org.gradle.jvmargs`에 넣은 `-D` 옵션은 Gradle이 가변 속성으로 분류해 데몬 시작 인자에서 빼기 때문이다. 이 속성은 JVM 시작 때 한 번만 읽어서 늦게 적용되면 소용이 없다. 환경(Windows 네트워크 상태)에 따라 IPv6 소켓 열기가 실패했다.
- **해결:** CI 준비 스크립트가 `CI=true`일 때 `JAVA_TOOL_OPTIONS`로 IPv4 옵션을 전달해 모든 JVM이 시작부터 읽게 했다(`8060b62`). 이후 러너를 EC2의 Linux Docker 러너로 옮겨 Windows 소켓 문제 자체를 없앴다.
- **재발 방지:** 네트워크 관련 JVM 옵션은 `gradle.properties`가 아니라 환경변수로 시작 전에 준다. 원인을 추정할 때 실패한 잡의 **실행 명령**(`Process command line`)을 먼저 본다. 로컬에서 통과하고 CI에서만 실패하면 환경 차이를 의심한다.
- **근거:** `Infra/README.md`(CI 러너), `Infra/deploy/README.md`, 커밋 `8060b62`.

### A3. 임베디드 PostgreSQL이 시작하지 못함
- **증상:** `Gave up waiting for server to start after 10000ms`, 테스트 다수가 한꺼번에 실패.
- **원인:** 러너 PC에서 `initdb`만 10~15초가 걸려 시작 대기 시간(10초)을 넘겼다. 이전 실행이 남긴 `postgres` 프로세스가 있었고 권한 문제로 종료할 수도 없었다(접근 거부).
- **해결:** PC 상태를 정리하고 러너를 Linux 컨테이너로 옮겼다. 컨테이너는 매번 깨끗한 환경이다.
- **재발 방지:** 테스트가 로컬 프로세스에 기대면 CI 환경 차이에 취약하다. CI는 깨끗한 컨테이너에서 돌린다.

### A4. 잡이 오래 멈춤
- **증상:** `be-timescale-test`가 30분째 진행 중으로 보이고, 한 번은 캐시 저장 단계에서 멈춘 것처럼 보였다.
- **원인:** 러너 프로세스를 다시 띄우면서 GitLab 쪽에는 "진행 중"으로 남은 잡이 있었다. 캐시 저장 지연의 정확한 원인은 **확정하지 못했다.**
- **해결:** 잡을 취소하고 다시 실행.
- **재발 방지:** 진행 중인 잡이 있을 때 러너를 재시작하지 않는다. 오래 멈춘 잡은 로그의 마지막 줄을 먼저 본다.

### A5. EC2 러너로 옮긴 뒤 일부 파이프라인이 대기
- **증상:** FE 파트 MR 파이프라인이 `stuck`(러너를 찾지 못함)으로 멈췄다. 새 CI 파일을 쓰는 브랜치는 통과했다.
- **원인:** 새 러너를 "태그 없는 잡은 받지 않음"으로 만들었는데, FE·AI·EMB·`main`의 옛 CI 파일은 태그가 없는 골격 잡만 있었다.
- **해결:** 러너 설정에서 **Run untagged jobs**를 켰다.
- **재발 방지:** 러너를 바꿀 때 아직 새 CI 파일을 받지 않은 브랜치의 잡이 어디서 돌지 먼저 확인한다.

### A6. 러너 토큰이 대화에 노출
- **증상:** `gitlab-runner list` 출력에 러너 인증 토큰이 그대로 들어 있었고 그 출력을 공유했다.
- **원인:** 이 명령이 토큰을 출력한다는 것을 모르고 결과를 붙였다.
- **해결:** 러너를 삭제하고 새로 만들어 토큰을 교체했다. 서버에서는 토큰을 가려서 보는 명령을 쓴다.
- **재발 방지:** `gitlab-runner list`와 `config.toml`의 내용을 공유하지 않는다. 확인은 `systemctl status gitlab-runner`로 한다. 토큰은 서버 터미널에만 입력한다.

## B. 로컬 Docker(Windows)

### B1. 포트 공개 실패 `invalid pointer address`
- **증상:** `docker compose up`에서 `listen tcp 0.0.0.0:80: ... invalid pointer address`로 Nginx가 시작하지 못했다. 다른 포트로는 되기도 했다.
- **원인:** A2와 같은 Windows 소켓 오류(`WSAEFAULT`)다. 이 PC의 네트워크 상태 문제이고 코드나 Compose 설정 문제가 아니다.
- **해결:** 다른 포트로 다시 시도하거나 PC를 재시작했다. 최종 확인은 Linux 서버에서 했다.
- **재발 방지:** 포트 공개가 필요 없는 확인은 내부 네트워크에서 한다. 로컬에서만 재현되는 소켓 오류는 서버에서 같은지 먼저 확인한다.

### B2. 이미지 받기 실패(`EOF`)
- **증상:** `docker pull`이 중간에 `EOF`로 끊겼다.
- **원인:** Docker Hub 접속이 불안정했다.
- **해결:** 같은 명령을 다시 실행(받은 층은 이어서 받는다).
- **재발 방지:** 큰 이미지(약 700MB)는 서버에서 미리 받아 둔다.

### B3. Docker Desktop이 꺼져 있음
- **증상:** `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`.
- **원인:** Docker Desktop이 실행 중이 아니었다.
- **해결:** Docker Desktop을 켠다.

## C. Compose·서버

### C1. `.env`에 기본 값이 없어 Redis가 비정상, 앱이 시작하지 못함
- **증상:** `variable is not set. Defaulting to a blank string` 경고, `redis` 컨테이너가 `unhealthy`, 앱이 `dependency failed to start`.
- **원인:** 기존 `.env`에 `POSTGRES_*`, `REDIS_PASSWORD`가 없었다. 빈 비밀번호로 시작한 Redis의 헬스체크(`redis-cli -a $REDIS_PASSWORD`)가 실패했고, 앱은 Redis가 정상이어야 시작한다.
- **해결:** `.env`에 값을 채우고 `docker compose down -v` 후 다시 시작.
- **재발 방지:** `.env.example`을 기준으로 필요한 변수를 모두 채운다. 필수 값은 `${변수:?메시지}`로 비어 있으면 멈추게 했다.

### C2. DB 비밀번호가 맞지 않아 앱이 시작하지 못함(502)
- **증상:** 앱 로그에 `FATAL: password authentication failed for user "app"`, Nginx가 `502 Bad Gateway`.
- **원인:** PostgreSQL 비밀번호는 **DB를 처음 만들 때 한 번만** 적용된다. 이후 `.env`를 바꿔도 기존 볼륨의 DB는 옛 비밀번호를 쓴다.
- **해결:** 시험 데이터뿐일 때 `docker compose down -v`로 볼륨을 지우고 새 비밀번호로 다시 만들었다.
- **재발 방지:** 운영 데이터가 생기기 전에 비밀번호를 확정한다. 운영 데이터가 있으면 볼륨을 지우지 않고 DB 안에서 `ALTER USER`로 바꾼다. 502가 나오면 `docker compose logs api`로 앱이 떴는지 먼저 본다.

### C3. 네트워크 구성(외부 접속, 호스트 포트)
- **증상(설계 중 발견):** 소셜 로그인은 앱이 Google·SSAFY 서버에 접속해야 하는데 `internal` 네트워크는 외부 접속이 막혀 있다. 호스트에 포트를 열려면 `internal`이 아닌 네트워크가 필요하다.
- **해결:** 앱, Grafana, MLflow처럼 외부 접속이나 호스트 포트가 필요한 서비스는 `public`에도 붙이고, 호스트 공개는 `127.0.0.1`(루프백)이나 Nginx 80번으로 제한했다.
- **재발 방지:** DB·Redis·스토리지는 `internal`에만 둔다. Docker는 방화벽(`ufw`)을 건너뛰므로 어떤 서비스에도 DB·Redis 포트를 `ports:`로 공개하지 않는다.

### C4. Nginx가 `/api`를 떼고 전달하면 404
- **증상(구현 전 확인):** 앱의 컨트롤러 주소가 `/api/...`로 시작하는데, 프록시가 `/api`를 떼고 전달하면 앱이 404를 낸다.
- **해결:** `/api/` 요청을 주소 변경 없이 그대로 전달한다(변수로 `proxy_pass`를 지정하면 원래 주소가 그대로 간다). 앱 컨테이너가 재시작해도 주소를 따라가도록 Docker 내부 DNS를 주기적으로 다시 조회한다.
- **재발 방지:** 프록시 경로 규칙을 정하기 전에 앱의 실제 경로를 코드에서 확인한다.

### C5. 필수 변수가 없으면 `docker compose down`도 실패
- **증상:** 스토리지 키를 `.env`에 넣기 전에 `docker compose down`을 실행하니 `required variable ... is missing`으로 중단됐다.
- **원인:** Compose는 어떤 명령이든 파일 전체를 읽으며 필수 변수(`:?`)를 검사한다. 의도한 안전장치다.
- **해결:** 변수를 먼저 채운 뒤 명령을 실행.
- **재발 방지:** 새 필수 변수를 추가하면 서버 `.env`도 같이 바꾼다(C9).

### C6. 서버 구성이 최신이 아님(스토리지 컨테이너·볼륨이 없음)
- **증상:** `docker ps`에 스토리지 컨테이너가 없고 `infra_seaweeddata` 볼륨도 없었다. 서버 코드의 Compose 파일에 스토리지 서비스가 없었다(`grep -c` 결과 0).
- **원인:** 서버의 저장소가 최신 `develop-BE`를 받지 않은 상태에서 서비스를 다시 올렸다. 스토리지 볼륨이 사라진 것은 사용하지 않는 볼륨을 정리하는 명령 때문일 가능성이 있으나 **확정하지 못했다.**
- **해결:** 최신 코드를 받고 배포 스크립트로 다시 구성. 스토리지 데이터는 시험 파일뿐이라 손실이 없었다.
- **재발 방지:** 서버에서 서비스를 올리기 전에 `git pull`과 변경 내용을 확인한다. **`docker volume prune`, `docker system prune --volumes`를 서버에서 실행하지 않는다**(멈춘 서비스의 데이터가 삭제된다).

### C7. 서버의 Nginx가 내려가 있음(원인 미확인)
- **증상:** 서버 안 `/health`가 `000`, 80번을 듣는 프로세스 없음, 방화벽은 정상.
- **원인:** 스택 전체가 내려가 있었다. 서버 재부팅인지 `docker compose down` 실행인지 **확정하지 못했다.**
- **해결:** `docker compose up -d`로 복구(데이터 볼륨은 유지).
- **재발 방지:** 서버 재부팅 뒤 컨테이너가 자동으로 올라오는지(`restart: unless-stopped`)를 보안·운영 작업(48번)에서 확인한다. 상태 확인은 `docker compose ps`로 한다.

### C8. 환경변수 이름 `S3_*` 혼란
- **증상:** "AWS S3를 안 쓰는데 왜 S3 키가 필요한가"라는 혼란.
- **원인:** 이름이 저장소가 아니라 접속 규칙(S3 방식)을 따랐다. AWS S3로 오해하기 쉬웠다.
- **해결:** `OBJECT_STORAGE_*`로 변경하고 설명을 `.env.example`과 README에 추가(`5e1d365`). 서버 `.env`의 이름도 함께 바꿨다.
- **재발 방지:** 환경변수 이름에 외부 서비스의 상표나 방식을 쓰지 않는다.

### C9. 서버 `.env`의 새 키가 없어 배포가 막힘
- **증상:** 최신 Compose에서 `required variable OBJECT_STORAGE_...` 오류.
- **원인:** 서버의 `.env`에 이후에 추가한 스토리지 키가 없었다(다시 만들어진 파일로 보임).
- **해결:** 서버에서 무작위 값을 만들어 `.env`에 추가하고 개수를 확인(값은 출력하지 않음).
- **재발 방지:** 새 필수 변수를 추가하는 MR에는 서버 `.env` 변경 절차를 적는다. 배포 전에 `.env` 변수 개수를 확인한다.

### C10. MLflow가 서버에서 시작하자마자 죽고 다시 시작을 반복(`No module named 'psycopg'`)
- **증상:** `main` 통합 배포 뒤 `infra-mlflow-1`이 `Restarting (1)`. 로그 끝에 `ModuleNotFoundError: No module named 'psycopg'`. 다른 컨테이너와 사용자 서비스(FE·API)는 정상이었다.
- **원인:** `Infra/mlflow/Dockerfile`이 `psycopg2-binary`(예전 PostgreSQL 드라이버)만 설치했는데, 함께 설치되는 SQLAlchemy 2.1이 `postgresql://` 주소의 기본 드라이버를 `psycopg`(v3)로 바꿔서 그것을 요청했다. 모니터링·MLflow는 코드로만 만들고 서버에서 한 번도 기동해 보지 않은 채 `main`에 들어갔다.
- **해결:** 이미지에 `psycopg[binary]==3.3.6`을 추가했다(`psycopg2-binary`는 그대로). 설치 조합(`mlflow 3.17.2`, `sqlalchemy 2.1.6`)이 충돌 없이 해결되는 것은 `uv pip compile`로 확인했고, 서버 기동은 배포 후 확인한다.
- **재발 방지:** 서버에서 처음 기동하는 서비스는 병합 전에 서버에서 한 번 띄워 본다(이번 FE·AI는 그렇게 해서 문제가 없었다). 이미지에 데이터베이스 드라이버를 넣을 때는 DB 주소가 쓰는 드라이버 이름(`postgresql+psycopg` 등)이 실제로 설치되는지 확인한다.
- **근거:** `Infra/mlflow/Dockerfile`, 서버 `docker logs infra-mlflow-1`.

## D. 스토리지(SeaweedFS)

### D1. 만료 정책이 적용되지 않음
- **증상:** S3 수명주기 API로 규칙을 저장하고 조회할 수 있었지만 새 객체의 만료 시간(`ttlSec`)이 `0`이었다.
- **원인:** 이 버전(4.48)에서는 규칙이 저장만 되고 객체에 만료가 붙지 않았다.
- **해결:** SeaweedFS의 **경로 TTL**(`fs.configure -locationPrefix=... -ttl=...`)을 쓰고 시험으로 삭제를 확인했다.
- **재발 방지:** 기능이 "설정된다"와 "동작한다"는 다르다. 만료·삭제처럼 시간이 걸리는 기능은 실제 동작을 시험한다.

### D2. 볼륨 슬롯 부족 `Not enough data nodes found`
- **증상:** TTL을 건 경로에 업로드하면 `InternalError`로 실패.
- **원인:** 버킷마다 데이터 볼륨이 여러 개 잡히고 TTL 경로는 전용 볼륨이 더 필요한데, 시험에서 `-volume.max=20`으로 제한해 슬롯이 모자랐다.
- **해결:** `-volume.max=0`(디스크 여유에 맞춰 자동)으로 변경.
- **재발 방지:** 개수 제한 옵션은 버킷·정책 수를 늘릴 때 부족해질 수 있다. 자동 설정을 기본으로 둔다.

### D3. 프록시 뒤에서 서명 URL이 맞지 않을 위험
- **증상(설계 중 발견):** 서명에는 호스트와 경로가 들어 있어 프록시가 경로를 자르거나 `Host`를 바꾸면 서명이 틀어진다.
- **해결:** 도메인 루트 주소를 쓰고 버킷 이름 경로로 라우팅하며 `Host`를 그대로 전달. SeaweedFS에는 공개 주소를 알려(`-s3.externalUrl`) 프록시 뒤에서도 서명을 검증하게 했다. 외부(PC)에서 서명 PUT·GET이 통과하는 것을 확인했다.
- **재발 방지:** 서명 URL을 쓰는 서비스는 프록시 설정(경로, `Host`)을 먼저 맞춘다.

## E. 배포(CD)

### E1. 파일 하나를 연결한 설정이 배포 후 바뀌지 않음(구현 전 확인)
- **증상(예측):** Nginx 설정처럼 파일 하나를 컨테이너에 직접 연결한 경우, 복사 도구가 새 파일로 교체하면 컨테이너가 옛 파일을 계속 본다.
- **해결:** 복사 시 `rsync --inplace`로 같은 파일을 덮어쓰고, 배포 뒤 `nginx -s reload`를 실행한다.
- **재발 방지:** 파일 단위 마운트는 교체 방식으로 갱신하지 않는다. 설정 변경 후 해당 서비스를 다시 읽게 한다(Prometheus·Loki·Alloy는 재시작).

### E2. 러너 사용자가 홈 폴더를 읽지 못함
- **증상(구현 전 확인):** 배포 러너(`gitlab-runner` 사용자)가 `~/S15P31A307`의 소스를 읽지 못한다.
- **원인:** 서버의 홈 폴더는 다른 사용자가 읽을 수 없다.
- **해결:** 소스를 읽기 가능한 임시 폴더에 풀어 실행한다. DRY_RUN은 소유자 권한으로 한다.

### E3. CD MR이 `develop-BE`가 아니라 `main`으로 병합됨
- **증상:** CD 변경과 함께 BE 코드·`Infra`가 `main`에 정기 릴리즈(`[DEPLOY]`) 없이 들어갔다(`f76515b`).
- **원인:** MR 대상 브랜치가 기본값(`main`)이었다. 리뷰도 대상 브랜치를 확인하지 못했다.
- **해결:** 되돌리지 않고 영향을 정리했다. 금요일 `[DEPLOY]`와 이후 `[SYNC]`로 맞춘다.
- **재발 방지:** MR을 열 때 **Target branch를 확인**한다. MR 설명 맨 위에 대상 브랜치를 적는다.

### E4. `main`을 그대로 배포하면 서버가 퇴보
- **증상(예방):** `main`에는 스토리지 구성이 없어 지금 `main`을 배포하면 서버에서 스토리지 경로가 사라진다.
- **해결:** `[DEPLOY]`로 `develop-BE`가 `main`에 들어간 뒤에 `main`을 배포한다. 그 전의 시험은 `develop-BE` 소스로 스크립트를 수동 실행한다.
- **재발 방지:** 배포 전에 서버가 쓰는 브랜치와 `main`의 차이를 확인한다.

### E5. 서버에서 GitLab SSH(22번) 접속 불가
- **증상:** 서버에서 `ssh -T git@lab.ssafy.com`이 멈춤, 22번 연결 시험이 막힘.
- **원인:** 서버에서 GitLab의 SSH 포트가 막혀 있다.
- **해결:** 배포 키(SSH) 대신 **읽기 전용 배포 토큰(HTTPS)** 으로 저장소를 받았다.
- **재발 방지:** 포트 연결은 `timeout 5 bash -c '</dev/tcp/호스트/포트'`로 먼저 시험한다.

## F. 모니터링·로그

### F1. 로그의 토큰·이메일이 그대로 남음
- **증상:** 비밀 가림 규칙을 시험하니 `Authorization: Bearer 토큰`이 `Authorization: *** 토큰`으로 바뀌었다. 즉 "Bearer"라는 단어만 가려지고 **토큰은 그대로 노출**됐다. 이메일 주소도 가려지지 않았다.
- **원인:** 규칙 순서 문제다. `Authorization: 값` 형태를 먼저 가리는 규칙이 값으로 "Bearer"를 잡아 먼저 바꿨고, 그 뒤 Bearer 토큰 규칙은 이미 바뀐 문자열에 적용되지 못했다. 이메일 규칙은 없었다.
- **해결:** Bearer 규칙을 key=값 규칙보다 앞에 두고 JWT·이메일 규칙을 추가했다. 샘플 로그 7줄로 다시 시험해 토큰·이메일이 모두 가려지고 일반 로그(`GET /api/... 401`)는 그대로인 것을 확인했다.
- **재발 방지:** 가림 규칙을 추가하거나 바꿀 때는 **실제 로그 모양으로 시험**하고, 가려진 결과에 원문 비밀이 남아 있는지를 확인한다. 규칙은 구체적인 것(Bearer, JWT)부터 일반적인 것 순서로 둔다. 정규식 시험은 Python으로 했으므로 Alloy(Go 정규식)에서 서버로 다시 확인한다.
- **근거:** `Infra/monitoring/alloy/config.alloy`(주석에 순서 이유), `Infra/monitoring/README.md`.

## H. 보안 점검

점검 기준과 결과는 `Infra/SECURITY.md`에 있다. 여기에는 점검하다 겪은 문제를 적는다.

### H1. ufw로 막아도 Docker가 공개한 포트는 열린다
- **증상(의문):** "Docker 포트를 열어도 ufw가 막지 않는가?"라는 질문에서 시작했다. 앞서 `ufw allow 80`이 Docker로 공개한 Nginx에 필요하다고 잘못 안내했다.
- **원인:** Docker가 `ports:`로 포트를 공개하면 NAT(DNAT)로 목적지를 컨테이너로 바꾸고, 패킷이 INPUT이 아니라 FORWARD 체인을 지난다. 서버에서 `iptables -L FORWARD`로 `DOCKER-USER` → `DOCKER-FORWARD` → `ufw-*` 순서임을 확인했다. ufw 규칙은 Docker 규칙 뒤에 있어서 컨테이너로 가는 패킷에는 적용되지 않는다.
- **해결:** 안내를 바로잡았다. 서비스 설계로는 DB·Redis·스토리지에 `ports:`를 쓰지 않는다. 지금 공개된 포트는 Nginx 80뿐이고(nat `DOCKER` 체인에 DNAT 한 개), `DOCKER-USER`는 비어 있다.
- **재발 방지:** 방화벽 점검은 ufw 규칙이 아니라 **바깥에서 실제로 닿는 포트**를 기준으로 한다(`ss -tlnp`, `iptables`, 외부 접속 시험). `ufw allow`를 근거로 Docker 포트가 열린다고 설명하지 않는다.

### H2. 콘솔 권한이 없을 때 443이 열려 있는지 확인
- **증상:** AWS 보안 그룹을 볼 권한이 없어 443이 열려 있는지 알 수 없었다.
- **해결:** 서버에서 `ufw allow 443/tcp` 후 **빈 폴더에서** 임시 서버(`python3 -m http.server 443`)를 띄우고 내 PC에서 `Test-NetConnection`으로 연결을 시험했다(`TcpTestSucceeded : True`). 시험 후 서버를 종료하고 폴더를 지웠다.
- **재발 방지:** 설정을 볼 수 없으면 결과(실제로 닿는가)로 확인한다. 임시 서버는 현재 폴더 전체를 공개하므로 빈 폴더에서만 실행하고 끝나면 종료한다.

### H3. 붙여넣기 오류(`2~`, 여러 줄 명령이 합쳐짐)
- **증상:** 서버 터미널에 `2~`가 입력되고(`2~: command not found`), 여러 줄(heredoc) 명령이 한 줄로 합쳐져 `tee`가 단어들을 파일 이름으로 받는 형태가 되었다(`>` 입력 대기 상태).
- **원인:** `Shift+Insert`처럼 터미널이 붙여넣기로 처리하지 않는 단축키가 Insert 키 신호(`ESC[2~`)로 서버에 전달된 것으로 보인다. 여러 줄 명령은 붙여넣기 방식에 따라 줄이 합쳐졌다.
- **해결:** `Ctrl+C`로 입력을 취소했다(명령이 실행되기 전이라 파일은 만들어지지 않았음을 `ls`로 확인). 우클릭 또는 `Ctrl+Shift+V`로 붙여넣고, 여러 줄 대신 **한 줄 명령**(`printf ... | sudo tee ...`)을 썼다.
- **재발 방지:** 서버에 설정을 쓰는 명령은 한 줄로 만든다. 입력이 `>`에서 멈추면 Enter를 더 치지 말고 `Ctrl+C`로 취소한다. 붙여넣기 전에 `echo`로 시험한다.

### H4. 되돌리기 명령이 함께 실행되어 시험이 무효가 됨
- **증상:** SSH 보강을 적용하고 `sshd -T`로 값을 확인한 직후, "새 접속이 안 될 때만 쓰라"고 한 되돌리기 명령(`sudo rm 10-hardening.conf && reload`)까지 실행되었다. 이후 새 접속이 성공했지만 **보강이 해제된 상태**였다.
- **원인:** 안내에서 되돌리기 명령이 바로 실행하기 쉬운 블록으로 이어져 있어서 순서가 섞였다.
- **해결:** 현재 상태를 확인하고 파일을 다시 만들어 적용했다. 적용된 상태에서 새로 접속해 성공을 확인했다.
- **재발 방지:** 되돌리기 명령은 실패했을 때만 쓰는 별도 단계로 나눠서 안내한다. **시험은 변경이 적용된 상태에서** 해야 한다. 시험 전에 `sshd -T` 같은 명령으로 실제 상태를 한 번 더 확인한다.

### H5. 서버 `.env`에 이후 추가된 변수가 없음
- **증상(점검에서 발견):** 서버 `.env`가 10/23 이후 수정되지 않아 `GRAFANA_ADMIN_PASSWORD`가 없었다. 이 상태로 배포하면 Compose 필수 변수 검사에서 멈춘다.
- **해결:** 값을 출력하지 않는 방식(`grep -q "^이름=."`)으로 필수 변수 11개를 점검하고, 없는 하나만 서버에서 `openssl rand -hex 16`으로 만들어 `tee -a`로 추가했다. 수정 전에 백업을 만들고 끝난 뒤 삭제했다.
- **재발 방지:** 새 필수 변수를 추가하는 MR에는 서버 `.env` 변경 절차를 함께 적는다(C9와 같은 원칙). 배포 전에 필수 변수를 값 없이 점검한다.

### H6. PC에서 외부 포트 스캔이 네트워크 오류로 중단
- **증상:** `nmap -p-`(전체 포트)를 실행하니 `Strange read error from ... (10014 - 'Unknown error')`가 수백 줄 반복되고 끝나지 않았다. 같은 PC에서 PowerShell로 한 번에 500개씩 접속해도 `ConnectAsync` 호출이 "잘못된 포인터 주소" 오류로 실패했다. 작은 범위(80여 개)와 소규모 접속 시험(13개)은 정상이었다.
- **원인:** `10014`는 Windows의 `WSAEFAULT`(잘못된 주소)로, CI에서 겪은 `Bad address: listen`과 같은 계열이다. 이 PC의 네트워크 계층이 한 번에 많은 연결을 다루지 못하는 환경 문제로 보인다(원인 자체는 확정하지 못함). 서버·방화벽과는 관계없다. 또 처음에 `nmap`을 **서버 안에서** 실행하려 했으나, 바깥에서 본 모습을 확인하는 스캔이라 서버에서 하면 의미가 없고 서버에 도구를 늘릴 필요도 없다.
- **해결:** 연결을 한 번에 250개로 제한하고, 오류가 난 포트(구간마다 약 300개)를 20개씩 다시 검사해 끝내 오류가 0개가 되게 했다. 전체를 세 구간(1~22000, 22001~44000, 44001~65535)으로 나눠 실행했고 합계가 65535개와 맞았다. 결과는 22·80 open, 443 closed, 나머지 filtered(`Infra/SECURITY.md` 2절).
- **재발 방지:** 외부 스캔은 **내 PC에서**, **내 서버에만** 한다. 도구가 오류를 쏟아내면 결과를 그대로 믿지 않고 속도를 낮추거나 범위를 나눈다. 오류 난 대상은 따로 재검사하고, 구간 합계가 전체 수와 맞는지, 서버 안쪽 정보(`ss`, `iptables`)와 일치하는지 교차 확인한다. 환경 문제가 계속되면 다른 PC·네트워크에서 `nmap`으로 다시 확인한다.
