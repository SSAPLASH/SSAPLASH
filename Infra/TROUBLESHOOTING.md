# 인프라 트러블슈팅 기록

인프라 작업(CI 러너, Docker Compose, 서버, 스토리지, 배포, 모니터링)에서 실제로 겪은 문제와 해결을 모았다. 같은 증상을 다시 만났을 때 원인을 빨리 좁히고, 같은 실수를 반복하지 않기 위한 기록이다.

- 기간: 2026-10-19 ~ 2026-11-17
- 각 항목은 **증상 → 원인 → 해결 → 재발 방지** 순서다. 원인을 확정하지 못한 항목은 "원인 미확인"으로 표시했다.
- 비밀값(토큰, 키, 비밀번호)은 적지 않았다.

## A. CI·러너

### A1. Windows 러너 초기 설정 문제
- **증상:** 러너가 `pwsh`를 찾지 못함, 한글이 들어간 스크립트가 구문 오류, `Filename too long`, `.gitlab-ci.yml`이 YAML 오류.
- **원인:** 러너 PC에 PowerShell 7이 없었고, Windows PowerShell 5.1은 한글 인코딩 문제가 있었다. Gradle 캐시 경로가 Windows 경로 길이 제한을 넘었다. `echo` 문자열 안의 `: `(콜론+공백)를 YAML이 키로 해석했다.
- **해결:** PowerShell 7 설치, `core.longPaths` 활성화와 빌드 경로 단축, 문자열의 콜론을 다른 문구로 변경.
- **재발 방지:** YAML 문자열에 `: `를 넣지 않는다. 긴 경로 문제는 Linux 러너로 옮겨 근본적으로 없앴다(A2).

### A2. BE 테스트가 `Bad address: listen`으로 실패
- **증상:** `be-test`, `be-timescale-test`가 `java.net.SocketException: Bad address: listen`으로 실패하고 간헐적으로 통과했다. 같은 코드를 러너 PC에서 직접 돌리면 통과했다.
- **원인:** 처음에는 테스트 태스크의 `systemProperty`가 늦게 적용된다고 추정했으나 틀렸다. 실패한 잡의 Gradle 데몬 실행 명령에 `-Djava.net.preferIPv4Stack`이 **없었다.** `gradle.properties`의 `org.gradle.jvmargs`에 넣은 `-D` 옵션은 Gradle이 가변 속성으로 분류해 데몬 시작 인자에서 빼기 때문이다. 이 속성은 JVM 시작 때 한 번만 읽어서 늦게 적용되면 소용이 없다. 환경(Windows 네트워크 상태)에 따라 IPv6 소켓 열기가 실패했다.
- **해결:** CI 준비 스크립트가 `CI=true`일 때 `JAVA_TOOL_OPTIONS`로 IPv4 옵션을 전달해 모든 JVM이 시작부터 읽게 했다(`8060b62`). 이후 러너를 EC2의 Linux Docker 러너로 옮겨 Windows 소켓 문제 자체를 없앴다.
- **재발 방지:** 네트워크 관련 JVM 옵션은 `gradle.properties`가 아니라 환경변수로 시작 전에 준다. 원인을 추정할 때 실패한 잡의 **실행 명령**(`Process command line`)을 먼저 본다. 로컬에서 통과하고 CI에서만 실패하면 환경 차이를 의심한다.
- **근거:** `Infra/README.md`(CI 러너), `Infra/deploy/README.md`, 커밋 `8060b62`.

### A3. 임베디드 PostgreSQL이 시작하지 못함
- **증상:** `Gave up waiting for server to start after 10000ms`, 테스트 다수가 한꺼번에 실패.
- **원인:** 러너 PC에서 `initdb`만 10~15초가 걸려 시작 대기 시간(10초)을 넘겼다. 이전 실행이 남긴 `postgres` 프로세스가 있었고 권한 문제로 종료할 수도 없었다(접근 거부).
- **해결:** PC 상태를 정리하고 러너를 Linux 컨테이너로 옮겼다. 컨테이너는 매번 깨끗한 환경이다.
- **재발 방지:** 테스트가 로컬 프로세스에 기대면 CI 환경 차이에 취약하다. CI는 깨끗한 컨테이너에서 돌린다.

### A4. 잡이 오래 멈춤
- **증상:** `be-timescale-test`가 30분째 진행 중으로 보이고, 한 번은 캐시 저장 단계에서 멈춘 것처럼 보였다.
- **원인:** 러너 프로세스를 다시 띄우면서 GitLab 쪽에는 "진행 중"으로 남은 잡이 있었다. 캐시 저장 지연의 정확한 원인은 **확정하지 못했다.**
- **해결:** 잡을 취소하고 다시 실행.
- **재발 방지:** 진행 중인 잡이 있을 때 러너를 재시작하지 않는다. 오래 멈춘 잡은 로그의 마지막 줄을 먼저 본다.

### A5. EC2 러너로 옮긴 뒤 일부 파이프라인이 대기
- **증상:** FE 파트 MR 파이프라인이 `stuck`(러너를 찾지 못함)으로 멈췄다. 새 CI 파일을 쓰는 브랜치는 통과했다.
- **원인:** 새 러너를 "태그 없는 잡은 받지 않음"으로 만들었는데, FE·AI·EMB·`main`의 옛 CI 파일은 태그가 없는 골격 잡만 있었다.
- **해결:** 러너 설정에서 **Run untagged jobs**를 켰다.
- **재발 방지:** 러너를 바꿀 때 아직 새 CI 파일을 받지 않은 브랜치의 잡이 어디서 돌지 먼저 확인한다.

### A6. 러너 토큰이 대화에 노출
- **증상:** `gitlab-runner list` 출력에 러너 인증 토큰이 그대로 들어 있었고 그 출력을 공유했다.
- **원인:** 이 명령이 토큰을 출력한다는 것을 모르고 결과를 붙였다.
- **해결:** 러너를 삭제하고 새로 만들어 토큰을 교체했다. 서버에서는 토큰을 가려서 보는 명령을 쓴다.
- **재발 방지:** `gitlab-runner list`와 `config.toml`의 내용을 공유하지 않는다. 확인은 `systemctl status gitlab-runner`로 한다. 토큰은 서버 터미널에만 입력한다.

## B. 로컬 Docker(Windows)

### B1. 포트 공개 실패 `invalid pointer address`
- **증상:** `docker compose up`에서 `listen tcp 0.0.0.0:80: ... invalid pointer address`로 Nginx가 시작하지 못했다. 다른 포트로는 되기도 했다.
- **원인:** A2와 같은 Windows 소켓 오류(`WSAEFAULT`)다. 이 PC의 네트워크 상태 문제이고 코드나 Compose 설정 문제가 아니다.
- **해결:** 다른 포트로 다시 시도하거나 PC를 재시작했다. 최종 확인은 Linux 서버에서 했다.
- **재발 방지:** 포트 공개가 필요 없는 확인은 내부 네트워크에서 한다. 로컬에서만 재현되는 소켓 오류는 서버에서 같은지 먼저 확인한다.

### B2. 이미지 받기 실패(`EOF`)
- **증상:** `docker pull`이 중간에 `EOF`로 끊겼다.
- **원인:** Docker Hub 접속이 불안정했다.
- **해결:** 같은 명령을 다시 실행(받은 층은 이어서 받는다).
- **재발 방지:** 큰 이미지(약 700MB)는 서버에서 미리 받아 둔다.

### B3. Docker Desktop이 꺼져 있음
- **증상:** `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`.
- **원인:** Docker Desktop이 실행 중이 아니었다.
- **해결:** Docker Desktop을 켠다.

## C. Compose·서버

### C1. `.env`에 기본 값이 없어 Redis가 비정상, 앱이 시작하지 못함
- **증상:** `variable is not set. Defaulting to a blank string` 경고, `redis` 컨테이너가 `unhealthy`, 앱이 `dependency failed to start`.
- **원인:** 기존 `.env`에 `POSTGRES_*`, `REDIS_PASSWORD`가 없었다. 빈 비밀번호로 시작한 Redis의 헬스체크(`redis-cli -a $REDIS_PASSWORD`)가 실패했고, 앱은 Redis가 정상이어야 시작한다.
- **해결:** `.env`에 값을 채우고 `docker compose down -v` 후 다시 시작.
- **재발 방지:** `.env.example`을 기준으로 필요한 변수를 모두 채운다. 필수 값은 `${변수:?메시지}`로 비어 있으면 멈추게 했다.

### C2. DB 비밀번호가 맞지 않아 앱이 시작하지 못함(502)
- **증상:** 앱 로그에 `FATAL: password authentication failed for user "app"`, Nginx가 `502 Bad Gateway`.
- **원인:** PostgreSQL 비밀번호는 **DB를 처음 만들 때 한 번만** 적용된다. 이후 `.env`를 바꿔도 기존 볼륨의 DB는 옛 비밀번호를 쓴다.
- **해결:** 시험 데이터뿐일 때 `docker compose down -v`로 볼륨을 지우고 새 비밀번호로 다시 만들었다.
- **재발 방지:** 운영 데이터가 생기기 전에 비밀번호를 확정한다. 운영 데이터가 있으면 볼륨을 지우지 않고 DB 안에서 `ALTER USER`로 바꾼다. 502가 나오면 `docker compose logs api`로 앱이 떴는지 먼저 본다.

### C3. 네트워크 구성(외부 접속, 호스트 포트)
- **증상(설계 중 발견):** 소셜 로그인은 앱이 Google·SSAFY 서버에 접속해야 하는데 `internal` 네트워크는 외부 접속이 막혀 있다. 호스트에 포트를 열려면 `internal`이 아닌 네트워크가 필요하다.
- **해결:** 앱, Grafana, MLflow처럼 외부 접속이나 호스트 포트가 필요한 서비스는 `public`에도 붙이고, 호스트 공개는 `127.0.0.1`(루프백)이나 Nginx 80번으로 제한했다.
- **재발 방지:** DB·Redis·스토리지는 `internal`에만 둔다. Docker는 방화벽(`ufw`)을 건너뛰므로 어떤 서비스에도 DB·Redis 포트를 `ports:`로 공개하지 않는다.

### C4. Nginx가 `/api`를 떼고 전달하면 404
- **증상(구현 전 확인):** 앱의 컨트롤러 주소가 `/api/...`로 시작하는데, 프록시가 `/api`를 떼고 전달하면 앱이 404를 낸다.
- **해결:** `/api/` 요청을 주소 변경 없이 그대로 전달한다(변수로 `proxy_pass`를 지정하면 원래 주소가 그대로 간다). 앱 컨테이너가 재시작해도 주소를 따라가도록 Docker 내부 DNS를 주기적으로 다시 조회한다.
- **재발 방지:** 프록시 경로 규칙을 정하기 전에 앱의 실제 경로를 코드에서 확인한다.

### C5. 필수 변수가 없으면 `docker compose down`도 실패
- **증상:** 스토리지 키를 `.env`에 넣기 전에 `docker compose down`을 실행하니 `required variable ... is missing`으로 중단됐다.
- **원인:** Compose는 어떤 명령이든 파일 전체를 읽으며 필수 변수(`:?`)를 검사한다. 의도한 안전장치다.
- **해결:** 변수를 먼저 채운 뒤 명령을 실행.
- **재발 방지:** 새 필수 변수를 추가하면 서버 `.env`도 같이 바꾼다(C9).

### C6. 서버 구성이 최신이 아님(스토리지 컨테이너·볼륨이 없음)
- **증상:** `docker ps`에 스토리지 컨테이너가 없고 `infra_seaweeddata` 볼륨도 없었다. 서버 코드의 Compose 파일에 스토리지 서비스가 없었다(`grep -c` 결과 0).
- **원인:** 서버의 저장소가 최신 `develop-BE`를 받지 않은 상태에서 서비스를 다시 올렸다. 스토리지 볼륨이 사라진 것은 사용하지 않는 볼륨을 정리하는 명령 때문일 가능성이 있으나 **확정하지 못했다.**
- **해결:** 최신 코드를 받고 배포 스크립트로 다시 구성. 스토리지 데이터는 시험 파일뿐이라 손실이 없었다.
- **재발 방지:** 서버에서 서비스를 올리기 전에 `git pull`과 변경 내용을 확인한다. **`docker volume prune`, `docker system prune --volumes`를 서버에서 실행하지 않는다**(멈춘 서비스의 데이터가 삭제된다).

### C7. 서버의 Nginx가 내려가 있음(원인 미확인)
- **증상:** 서버 안 `/health`가 `000`, 80번을 듣는 프로세스 없음, 방화벽은 정상.
- **원인:** 스택 전체가 내려가 있었다. 서버 재부팅인지 `docker compose down` 실행인지 **확정하지 못했다.**
- **해결:** `docker compose up -d`로 복구(데이터 볼륨은 유지).
- **재발 방지:** 서버 재부팅 뒤 컨테이너가 자동으로 올라오는지(`restart: unless-stopped`)를 보안·운영 작업(48번)에서 확인한다. 상태 확인은 `docker compose ps`로 한다.

### C8. 환경변수 이름 `S3_*` 혼란
- **증상:** "AWS S3를 안 쓰는데 왜 S3 키가 필요한가"라는 혼란.
- **원인:** 이름이 저장소가 아니라 접속 규칙(S3 방식)을 따랐다. AWS S3로 오해하기 쉬웠다.
- **해결:** `OBJECT_STORAGE_*`로 변경하고 설명을 `.env.example`과 README에 추가(`5e1d365`). 서버 `.env`의 이름도 함께 바꿨다.
- **재발 방지:** 환경변수 이름에 외부 서비스의 상표나 방식을 쓰지 않는다.

### C9. 서버 `.env`의 새 키가 없어 배포가 막힘
- **증상:** 최신 Compose에서 `required variable OBJECT_STORAGE_...` 오류.
- **원인:** 서버의 `.env`에 이후에 추가한 스토리지 키가 없었다(다시 만들어진 파일로 보임).
- **해결:** 서버에서 무작위 값을 만들어 `.env`에 추가하고 개수를 확인(값은 출력하지 않음).
- **재발 방지:** 새 필수 변수를 추가하는 MR에는 서버 `.env` 변경 절차를 적는다. 배포 전에 `.env` 변수 개수를 확인한다.

### C10. MLflow가 서버에서 시작하자마자 죽고 다시 시작을 반복(`No module named 'psycopg'`)
- **증상:** `main` 통합 배포 뒤 `infra-mlflow-1`이 `Restarting (1)`. 로그 끝에 `ModuleNotFoundError: No module named 'psycopg'`. 다른 컨테이너와 사용자 서비스(FE·API)는 정상이었다.
- **원인:** `Infra/mlflow/Dockerfile`이 `psycopg2-binary`(예전 PostgreSQL 드라이버)만 설치했는데, 함께 설치되는 SQLAlchemy 2.1이 `postgresql://` 주소의 기본 드라이버를 `psycopg`(v3)로 바꿔서 그것을 요청했다. 모니터링·MLflow는 코드로만 만들고 서버에서 한 번도 기동해 보지 않은 채 `main`에 들어갔다.
- **해결:** 이미지에 `psycopg[binary]==3.3.6`을 추가했다(`psycopg2-binary`는 그대로). 설치 조합(`mlflow 3.17.2`, `sqlalchemy 2.1.6`)이 충돌 없이 해결되는 것은 `uv pip compile`로 확인했고, 서버 기동은 배포 후 확인한다.
- **재발 방지:** 서버에서 처음 기동하는 서비스는 병합 전에 서버에서 한 번 띄워 본다(이번 FE·AI는 그렇게 해서 문제가 없었다). 이미지에 데이터베이스 드라이버를 넣을 때는 DB 주소가 쓰는 드라이버 이름(`postgresql+psycopg` 등)이 실제로 설치되는지 확인한다.
- **근거:** `Infra/mlflow/Dockerfile`, 서버 `docker logs infra-mlflow-1`.

### C11. psycopg를 고친 뒤에도 MLflow가 약 11초마다 종료·재시작을 반복(작업 실행기)
- **증상:** C10 수정 뒤 `docker ps`는 `Up 7 seconds (health: starting)`이었고, `docker inspect`의 재시작 횟수가 210에서 211로 늘었다(시작 시각이 11초 간격으로 갱신). 로그에는 `Traceback` 없이 `Uvicorn running`, `Started parent process [14]`만 같은 모양으로 반복됐다.
- **확인한 것:** 종료코드 `0`, `OOMKilled=false`라서 메모리 부족으로 죽은 것이 아니었다. `docker stats`는 시작 직후 CPU 360%, 메모리 708MiB/1GiB, 프로세스 37개였고, 안정된 뒤에는 프로세스 121개, 메모리 1.627GiB였다.
- **잘못 짚었던 가설:** 메모리 한도(1g) 초과로 인한 OOM. 종료코드와 `OOMKilled`를 확인하자 아니었다.
- **원인:** MLflow 3.x는 서버를 띄울 때 작업 실행기(`_job_runner`와 `huey_consumer` 7개)도 함께 띄우고, 프로세스마다 같은 라이브러리를 올려 시작 때 CPU·메모리를 한꺼번에 쓴다. 시작 직후 이 부하와 컨테이너 한도가 겹쳐 기동이 끝나기 전에 종료를 반복한 것으로 보인다(종료 직전 상황을 직접 잡지는 못해 이 부분은 추정). 이 서버는 실험 기록과 모델 저장만 해서 작업 큐가 필요 없다.
- **해결:** 서버에서 시험해 확인한 뒤 `Infra/docker-compose.yml`에 반영했다.
  1. `--workers 1`: 웹 서버 워커를 1개로 줄여 이것만으로 `healthy`가 됐다(재시작 0, 메모리 1.627GiB, 프로세스 121개).
  2. `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false`: 작업 실행기를 껐다(이름은 `mlflow.environment_variables`를 `dir()`로 조회해 실제 있는 것을 확인). 프로세스 12개, 메모리 346MiB로 줄었고 `healthy`, 재시작 0회.
  3. 한도는 원래의 `1g`로 유지(346MiB로 충분).
- **재발 방지:** 오류 없이 재시작을 반복할 때는 `docker inspect`로 종료코드·`OOMKilled`·재시작 횟수를 먼저 본다. `docker top`과 `docker stats`로 프로세스 수·메모리 상위를 보면 어떤 프로세스가 자원을 쓰는지 드러난다. 환경변수 이름은 추측하지 말고 해당 버전에서 조회해서 쓴다.
- **참고(보안):** 이 진단 중 `docker top` 출력에 DB 비밀번호가 평문으로 보였다. `--backend-store-uri`에 비밀번호가 들어 있어 명령줄에 노출되기 때문이다. 환경변수로 옮기는 개선은 별도 작업으로 한다(`Infra/SECURITY.md` 참고).
- **근거:** 서버 `docker inspect`, `docker stats`, `docker top` 출력, `Infra/docker-compose.yml`.

### C12. 서버 `.env`에 OAuth 값을 넣었는데 글자 수가 0 (숨김 입력)
- **증상:** 구글·SSAFY 로그인 값 4개를 `read -rs`(입력을 숨기는 입력창)로 한꺼번에 넣었는데, 값은 출력하지 않고 글자 수만 보는 확인(`awk`)에서 3개가 `0`이었고 `GOOGLE_CLIENT_ID`만 36자였다. 구글 클라이언트 ID는 보통 70자 안팎이라 36자도 의심스러웠다.
- **원인:** 붙여넣은 값이 입력창에 도달하지 못한 것으로 추정한다. 이 서버 터미널은 붙여넣기에서 문제가 있었던 전례가 있다(H3). **원인은 확정하지 못했다.** 값이 비어 있는 채로 `.env`에 쓰였다(`NAME=`).
- **해결:** 4개를 반복문으로 한 번에 넣는 방식을 버리고, 변수마다 **입력 줄과 반영 줄을 따로** 실행했다(두 줄을 한꺼번에 붙여넣으면 둘째 줄이 값으로 읽힌다). 넣을 때마다 글자 수를 확인했다. 최종 확인에서 구글 시크릿 35자, SSAFY ID·시크릿 36자, 관리자 이메일 33자가 나왔다. 이후 BE가 구글 값만 다시 받아 달라고 해서 같은 방식으로 교체했다(앞의 36자 ID와 관련 있는지는 확인하지 못했다).
- **재발 방지:** 비밀값을 넣은 뒤에는 **반드시 글자 수로 확인**하고 반영(`docker compose up -d api`)한다. 값은 명령줄·화면·채팅에 올리지 않는다. 붙여넣기는 우클릭이나 `Ctrl+Shift+V`를 쓴다(`Shift+Insert`는 `2~`가 섞인다). 반영 전에 `.env` 백업을 만들고 끝나면 지운다.
- **근거:** 서버 `awk`로 본 글자 수(값은 출력하지 않음), `Infra/SECURITY.md` 3.6.

## D. 스토리지(SeaweedFS)

### D1. 만료 정책이 적용되지 않음
- **증상:** S3 수명주기 API로 규칙을 저장하고 조회할 수 있었지만 새 객체의 만료 시간(`ttlSec`)이 `0`이었다.
- **원인:** 이 버전(4.48)에서는 규칙이 저장만 되고 객체에 만료가 붙지 않았다.
- **해결:** SeaweedFS의 **경로 TTL**(`fs.configure -locationPrefix=... -ttl=...`)을 쓰고 시험으로 삭제를 확인했다.
- **재발 방지:** 기능이 "설정된다"와 "동작한다"는 다르다. 만료·삭제처럼 시간이 걸리는 기능은 실제 동작을 시험한다.

### D2. 볼륨 슬롯 부족 `Not enough data nodes found`
- **증상:** TTL을 건 경로에 업로드하면 `InternalError`로 실패.
- **원인:** 버킷마다 데이터 볼륨이 여러 개 잡히고 TTL 경로는 전용 볼륨이 더 필요한데, 시험에서 `-volume.max=20`으로 제한해 슬롯이 모자랐다.
- **해결:** `-volume.max=0`(디스크 여유에 맞춰 자동)으로 변경.
- **재발 방지:** 개수 제한 옵션은 버킷·정책 수를 늘릴 때 부족해질 수 있다. 자동 설정을 기본으로 둔다.

### D3. 프록시 뒤에서 서명 URL이 맞지 않을 위험
- **증상(설계 중 발견):** 서명에는 호스트와 경로가 들어 있어 프록시가 경로를 자르거나 `Host`를 바꾸면 서명이 틀어진다.
- **해결:** 도메인 루트 주소를 쓰고 버킷 이름 경로로 라우팅하며 `Host`를 그대로 전달. SeaweedFS에는 공개 주소를 알려(`-s3.externalUrl`) 프록시 뒤에서도 서명을 검증하게 했다. 외부(PC)에서 서명 PUT·GET이 통과하는 것을 확인했다.
- **재발 방지:** 서명 URL을 쓰는 서비스는 프록시 설정(경로, `Host`)을 먼저 맞춘다.

## E. 배포(CD)

### E1. 파일 하나를 연결한 설정이 배포 후 바뀌지 않음(구현 전 확인)
- **증상(예측):** Nginx 설정처럼 파일 하나를 컨테이너에 직접 연결한 경우, 복사 도구가 새 파일로 교체하면 컨테이너가 옛 파일을 계속 본다.
- **해결:** 복사 시 `rsync --inplace`로 같은 파일을 덮어쓰고, 배포 뒤 `nginx -s reload`를 실행한다.
- **재발 방지:** 파일 단위 마운트는 교체 방식으로 갱신하지 않는다. 설정 변경 후 해당 서비스를 다시 읽게 한다(Prometheus·Loki·Alloy는 재시작).

### E2. 러너 사용자가 홈 폴더를 읽지 못함
- **증상(구현 전 확인):** 배포 러너(`gitlab-runner` 사용자)가 `~/S15P31A307`의 소스를 읽지 못한다.
- **원인:** 서버의 홈 폴더는 다른 사용자가 읽을 수 없다.
- **해결:** 소스를 읽기 가능한 임시 폴더에 풀어 실행한다. DRY_RUN은 소유자 권한으로 한다.

### E3. CD MR이 `develop-BE`가 아니라 `main`으로 병합됨
- **증상:** CD 변경과 함께 BE 코드·`Infra`가 `main`에 정기 릴리즈(`[DEPLOY]`) 없이 들어갔다(`f76515b`).
- **원인:** MR 대상 브랜치가 기본값(`main`)이었다. 리뷰도 대상 브랜치를 확인하지 못했다.
- **해결:** 되돌리지 않고 영향을 정리했다. 금요일 `[DEPLOY]`와 이후 `[SYNC]`로 맞춘다.
- **재발 방지:** MR을 열 때 **Target branch를 확인**한다. MR 설명 맨 위에 대상 브랜치를 적는다.

### E4. `main`을 그대로 배포하면 서버가 퇴보
- **증상(예방):** `main`에는 스토리지 구성이 없어 지금 `main`을 배포하면 서버에서 스토리지 경로가 사라진다.
- **해결:** `[DEPLOY]`로 `develop-BE`가 `main`에 들어간 뒤에 `main`을 배포한다. 그 전의 시험은 `develop-BE` 소스로 스크립트를 수동 실행한다.
- **재발 방지:** 배포 전에 서버가 쓰는 브랜치와 `main`의 차이를 확인한다.

### E5. 서버에서 GitLab SSH(22번) 접속 불가
- **증상:** 서버에서 `ssh -T git@lab.ssafy.com`이 멈춤, 22번 연결 시험이 막힘.
- **원인:** 서버에서 GitLab의 SSH 포트가 막혀 있다.
- **해결:** 배포 키(SSH) 대신 **읽기 전용 배포 토큰(HTTPS)** 으로 저장소를 받았다.
- **재발 방지:** 포트 연결은 `timeout 5 bash -c '</dev/tcp/호스트/포트'`로 먼저 시험한다.

### E6. 같은 번호의 마이그레이션이 두 개 (2026-11-06, 배포 전에 발견)
- **증상:** `develop-BE`에 `V38__add_recommendation_drill.sql`과 `V38__add_song_metadata.sql`이 함께 있었다. 병합 뒤에 문서를 정리하다 발견했다. Flyway는 같은 버전이 둘이면 시작하지 못한다(설치된 12.4에 해당 오류 문구가 있음을 확인했고, 임시 DB 문제로 재현은 못 했다).
- **원인:** 두 브랜치가 각각 "다음 번호"를 V38로 잡았다. 파일 이름이 달라 Git 충돌이 나지 않는다.
- **해결:** 나중에 병합된 쪽을 V40으로 옮겼다. 시험의 Flyway 목표 버전을 올렸다.
- **이어서 생긴 문제:** `TimescaleMigrationTest`의 적용 개수(50행, 127행)를 올리지 않아 `be-timescale-test`가 실패 상태가 됐다. 팀원이 알려 줘서 다음 MR에 고쳤다.
- **재발 방지:** 마이그레이션을 추가하면 번호, `EmbeddedPostgresInitializer` 목표 버전, `TimescaleMigrationTest` 개수를 함께 올린다. MR 올리기 전에 원격 브랜치의 번호를 다시 확인한다.

### E7. `main`과 `develop-BE`의 V43이 서로 다름 (2026-11-06, 배포 전에 발견)
- **증상:** `main`의 V43은 `add_recommendation_consent_history`, `develop-BE`의 V43은 `add_sheet_music_song`이었다. 두 브랜치를 합치면 E6과 같이 시작하지 못한다.
- **원인:** 동의 이력 MR이 `develop-BE`가 아니라 `main`으로 병합됐고, 그사이 다른 MR이 `develop-BE`에서 같은 번호를 썼다. 이 MR이 왜 `main`으로 갔는지는 확인하지 못했다(E3과 같은 유형으로 보이지만 원인 미확인).
- **해결:** `main`을 기준으로 두고, `develop-BE`의 악보 연결을 V44로, 대체 키를 V45로 옮겼다(`fix/COACH-migration-v43-conflict`, `feat/COACH-recommend-random-key`). 이미 배포됐을 수 있는 쪽의 번호를 바꾸면 체크섬 오류가 나기 때문이다.
- **재발 방지:** `main`을 먼저 확인한 뒤 번호를 정한다. 번호를 바꾸기 전에 그 마이그레이션이 어느 DB에 적용됐는지 확인한다. E3의 대상 브랜치 점검을 MR 때마다 한다.

## F. 모니터링·로그

### F1. 로그의 토큰·이메일이 그대로 남음
- **증상:** 비밀 가림 규칙을 시험하니 `Authorization: Bearer 토큰`이 `Authorization: *** 토큰`으로 바뀌었다. 즉 "Bearer"라는 단어만 가려지고 **토큰은 그대로 노출**됐다. 이메일 주소도 가려지지 않았다.
- **원인:** 규칙 순서 문제다. `Authorization: 값` 형태를 먼저 가리는 규칙이 값으로 "Bearer"를 잡아 먼저 바꿨고, 그 뒤 Bearer 토큰 규칙은 이미 바뀐 문자열에 적용되지 못했다. 이메일 규칙은 없었다.
- **해결:** Bearer 규칙을 key=값 규칙보다 앞에 두고 JWT·이메일 규칙을 추가했다. 샘플 로그 7줄로 다시 시험해 토큰·이메일이 모두 가려지고 일반 로그(`GET /api/... 401`)는 그대로인 것을 확인했다.
- **재발 방지:** 가림 규칙을 추가하거나 바꿀 때는 **실제 로그 모양으로 시험**하고, 가려진 결과에 원문 비밀이 남아 있는지를 확인한다. 규칙은 구체적인 것(Bearer, JWT)부터 일반적인 것 순서로 둔다. 정규식 시험은 Python으로 했으므로 Alloy(Go 정규식)에서 서버로 다시 확인한다.
- **근거:** `Infra/monitoring/alloy/config.alloy`(주석에 순서 이유), `Infra/monitoring/README.md`.

## G. 작업 방식

### G1. 서버 명령을 다른 터미널에서 실행
- **증상:** `sudo ufw status`가 "Sudo가 이 컴퓨터에서 사용하지 않도록 설정되어 있습니다", DRY_RUN 출력의 소스 경로가 `/c/Users/...`, 서버 상태를 확인한다며 내 PC 결과를 받았다.
- **원인:** 프롬프트(`SSAFY@DESKTOP... MINGW64` = PC, `ubuntu@ip-...` = 서버)를 구분하지 않았다. 그 때문에 서버 결과로 단정한 안내가 틀린 적도 있었다.
- **재발 방지:** 명령을 실행하기 전에 프롬프트를 확인한다. 결과를 받을 때 어느 터미널인지 표시하게 한다.

### G2. `cmd`와 PowerShell을 혼동
- **증상:** `cmd`에서 `Copy-Item`, `Test-NetConnection`이 "내부 또는 외부 명령이 아닙니다".
- **원인:** PowerShell 전용 명령이다.
- **재발 방지:** `cmd`는 `copy`, PowerShell은 `Copy-Item`. 프롬프트 모양(`PS C:\>`)으로 구분한다.

### G3. 푸시한 커밋을 `amend`해서 이력이 갈라짐
- **증상:** 로컬이 `ahead 1, behind 1`.
- **원인:** 이미 푸시한 커밋을 `git commit --amend`로 고쳤다.
- **해결:** `git reset --soft origin/브랜치`로 되돌리고 **새 커밋**으로 만들었다.
- **재발 방지:** 푸시한 커밋은 `amend`하지 않고 새 커밋을 만든다.

### G4. 키 파일 이름 오타
- **증상:** `Identity file K15A301T.pem not accessible`, `Permission denied (publickey)`.
- **원인:** 파일 이름이 `K15A307T.pem`인데 `301`로 입력했다.
- **재발 방지:** 파일 이름은 `ls`로 확인하고 복사해서 쓴다.

### G5. 다른 사람이 용도를 바꾼 Jira 이슈를 수정
- **증상:** 37번 이슈를 수정했는데 팀원이 이미 "BE 프로젝트 초기화"로 용도를 바꿔 쓰고 있었다.
- **해결:** 설명을 원래대로 복원하고 이후 수정하지 않았다.
- **재발 방지:** 이슈를 수정하기 전에 현재 제목·담당자·상태를 확인한다.

### G6. `.gitignore` 병합 충돌
- **증상:** `develop-BE` 반영 중 `.gitignore` 충돌.
- **해결:** 양쪽 항목을 모두 남기는 방향으로 해결하고 커밋(`최신 develop-BE 반영`).
- **재발 방지:** 이미 있는 무시 패턴(`.env`, `*.pem` 등)을 추가하라고 안내하기 전에 현재 파일을 확인한다.

### G7. GitLab 일시 장애로 푸시가 실패
- **증상:** `git push`가 `The requested URL returned error: 502` 또는 `Failed to connect to lab.ssafy.com:443`으로 실패했다. 같은 일이 두 번 있었다(MLflow 수정 푸시, 로그 수정 푸시).
- **원인:** GitLab 서버 쪽 일시 장애로 보인다. 내 쪽 설정이나 인증 문제가 아니었다(시간이 지나 다시 하면 같은 명령이 성공했다).
- **해결:** 커밋은 로컬에 남아 있으니 잠시 뒤 같은 `git push`를 다시 했다. 브라우저로 GitLab이 열리는지 먼저 보면 장애인지 알 수 있다.
- **재발 방지:** 푸시 실패를 코드 문제로 오해하지 않는다. 커밋이 로컬에 있는지(`git log`)와 원격 반영(`git ls-remote --heads origin 브랜치`)을 확인한 뒤 재시도한다. 반복해서 실패하면 인증·네트워크를 따로 본다.

### G8. 로컬에서 BE DB 시험을 돌리지 못함 (2026-11-06, 원인 미확인)
- **증상:** 이 PC에서 BE 시험용 임시 DB(임베디드 PostgreSQL)가 `Bad address: listen`, `connect failed`로 뜨지 않아 DB 시험이 시작 단계에서 전부 실패했다. Python 서버도 같은 시기에 `WinError 10014`로 한 번 실패했다. 재시도, IPv4 옵션은 효과가 없었고, 샌드박스를 끈 실행은 Gradle 데몬이 뜨지 않았다.
- **원인:** 미확인. A2, A3, I3과 증상이 같다.
- **해결:** 없음. 컴파일과 단위 시험만 로컬에서 돌리고 DB 시험은 CI로 확인했다. 그 사실을 MR 본문에 적었다.
- **재발 방지:** 실패한 시험 수가 DB 시험 수 전체와 같은지 먼저 본다. 전부 실패면 환경 문제일 가능성이 높지만, 코드가 맞다는 증거는 아니다. "환경 탓"이어도 검증하지 못했다고 적는다.

## H. 보안 점검

점검 기준과 결과는 `Infra/SECURITY.md`에 있다. 여기에는 점검하다 겪은 문제를 적는다.

### H1. ufw로 막아도 Docker가 공개한 포트는 열린다
- **증상(의문):** "Docker 포트를 열어도 ufw가 막지 않는가?"라는 질문에서 시작했다. 앞서 `ufw allow 80`이 Docker로 공개한 Nginx에 필요하다고 잘못 안내했다.
- **원인:** Docker가 `ports:`로 포트를 공개하면 NAT(DNAT)로 목적지를 컨테이너로 바꾸고, 패킷이 INPUT이 아니라 FORWARD 체인을 지난다. 서버에서 `iptables -L FORWARD`로 `DOCKER-USER` → `DOCKER-FORWARD` → `ufw-*` 순서임을 확인했다. ufw 규칙은 Docker 규칙 뒤에 있어서 컨테이너로 가는 패킷에는 적용되지 않는다.
- **해결:** 안내를 바로잡았다. 서비스 설계로는 DB·Redis·스토리지에 `ports:`를 쓰지 않는다. 지금 공개된 포트는 Nginx 80뿐이고(nat `DOCKER` 체인에 DNAT 한 개), `DOCKER-USER`는 비어 있다.
- **재발 방지:** 방화벽 점검은 ufw 규칙이 아니라 **바깥에서 실제로 닿는 포트**를 기준으로 한다(`ss -tlnp`, `iptables`, 외부 접속 시험). `ufw allow`를 근거로 Docker 포트가 열린다고 설명하지 않는다.

### H2. 콘솔 권한이 없을 때 443이 열려 있는지 확인
- **증상:** AWS 보안 그룹을 볼 권한이 없어 443이 열려 있는지 알 수 없었다.
- **해결:** 서버에서 `ufw allow 443/tcp` 후 **빈 폴더에서** 임시 서버(`python3 -m http.server 443`)를 띄우고 내 PC에서 `Test-NetConnection`으로 연결을 시험했다(`TcpTestSucceeded : True`). 시험 후 서버를 종료하고 폴더를 지웠다.
- **재발 방지:** 설정을 볼 수 없으면 결과(실제로 닿는가)로 확인한다. 임시 서버는 현재 폴더 전체를 공개하므로 빈 폴더에서만 실행하고 끝나면 종료한다.

### H3. 붙여넣기 오류(`2~`, 여러 줄 명령이 합쳐짐)
- **증상:** 서버 터미널에 `2~`가 입력되고(`2~: command not found`), 여러 줄(heredoc) 명령이 한 줄로 합쳐져 `tee`가 단어들을 파일 이름으로 받는 형태가 되었다(`>` 입력 대기 상태).
- **원인:** `Shift+Insert`처럼 터미널이 붙여넣기로 처리하지 않는 단축키가 Insert 키 신호(`ESC[2~`)로 서버에 전달된 것으로 보인다. 여러 줄 명령은 붙여넣기 방식에 따라 줄이 합쳐졌다.
- **해결:** `Ctrl+C`로 입력을 취소했다(명령이 실행되기 전이라 파일은 만들어지지 않았음을 `ls`로 확인). 우클릭 또는 `Ctrl+Shift+V`로 붙여넣고, 여러 줄 대신 **한 줄 명령**(`printf ... | sudo tee ...`)을 썼다.
- **재발 방지:** 서버에 설정을 쓰는 명령은 한 줄로 만든다. 입력이 `>`에서 멈추면 Enter를 더 치지 말고 `Ctrl+C`로 취소한다. 붙여넣기 전에 `echo`로 시험한다.

### H4. 되돌리기 명령이 함께 실행되어 시험이 무효가 됨
- **증상:** SSH 보강을 적용하고 `sshd -T`로 값을 확인한 직후, "새 접속이 안 될 때만 쓰라"고 한 되돌리기 명령(`sudo rm 10-hardening.conf && reload`)까지 실행되었다. 이후 새 접속이 성공했지만 **보강이 해제된 상태**였다.
- **원인:** 안내에서 되돌리기 명령이 바로 실행하기 쉬운 블록으로 이어져 있어서 순서가 섞였다.
- **해결:** 현재 상태를 확인하고 파일을 다시 만들어 적용했다. 적용된 상태에서 새로 접속해 성공을 확인했다.
- **재발 방지:** 되돌리기 명령은 실패했을 때만 쓰는 별도 단계로 나눠서 안내한다. **시험은 변경이 적용된 상태에서** 해야 한다. 시험 전에 `sshd -T` 같은 명령으로 실제 상태를 한 번 더 확인한다.

### H5. 서버 `.env`에 이후 추가된 변수가 없음
- **증상(점검에서 발견):** 서버 `.env`가 10/23 이후 수정되지 않아 `GRAFANA_ADMIN_PASSWORD`가 없었다. 이 상태로 배포하면 Compose 필수 변수 검사에서 멈춘다.
- **해결:** 값을 출력하지 않는 방식(`grep -q "^이름=."`)으로 필수 변수 11개를 점검하고, 없는 하나만 서버에서 `openssl rand -hex 16`으로 만들어 `tee -a`로 추가했다. 수정 전에 백업을 만들고 끝난 뒤 삭제했다.
- **재발 방지:** 새 필수 변수를 추가하는 MR에는 서버 `.env` 변경 절차를 함께 적는다(C9와 같은 원칙). 배포 전에 필수 변수를 값 없이 점검한다.

### H6. PC에서 외부 포트 스캔이 네트워크 오류로 중단
- **증상:** `nmap -p-`(전체 포트)를 실행하니 `Strange read error from ... (10014 - 'Unknown error')`가 수백 줄 반복되고 끝나지 않았다. 같은 PC에서 PowerShell로 한 번에 500개씩 접속해도 `ConnectAsync` 호출이 "잘못된 포인터 주소" 오류로 실패했다. 작은 범위(80여 개)와 소규모 접속 시험(13개)은 정상이었다.
- **원인:** `10014`는 Windows의 `WSAEFAULT`(잘못된 주소)로, CI에서 겪은 `Bad address: listen`과 같은 계열이다. 이 PC의 네트워크 계층이 한 번에 많은 연결을 다루지 못하는 환경 문제로 보인다(원인 자체는 확정하지 못함). 서버·방화벽과는 관계없다. 또 처음에 `nmap`을 **서버 안에서** 실행하려 했으나, 바깥에서 본 모습을 확인하는 스캔이라 서버에서 하면 의미가 없고 서버에 도구를 늘릴 필요도 없다.
- **해결:** 연결을 한 번에 250개로 제한하고, 오류가 난 포트(구간마다 약 300개)를 20개씩 다시 검사해 끝내 오류가 0개가 되게 했다. 전체를 세 구간(1~22000, 22001~44000, 44001~65535)으로 나눠 실행했고 합계가 65535개와 맞았다. 결과는 22·80 open, 443 closed, 나머지 filtered(`Infra/SECURITY.md` 2절).
- **재발 방지:** 외부 스캔은 **내 PC에서**, **내 서버에만** 한다. 도구가 오류를 쏟아내면 결과를 그대로 믿지 않고 속도를 낮추거나 범위를 나눈다. 오류 난 대상은 따로 재검사하고, 구간 합계가 전체 수와 맞는지, 서버 안쪽 정보(`ss`, `iptables`)와 일치하는지 교차 확인한다. 환경 문제가 계속되면 다른 PC·네트워크에서 `nmap`으로 다시 확인한다.

### H7. SSH 창이 멈춘 것처럼 보이고 Ctrl+C도 안 먹힘 (certbot 갱신 시험 중)
- **증상:** `certbot renew --dry-run`이 `Simulating renewal …`에서 3분 넘게 바뀌지 않았고 `Ctrl+C`도 먹지 않았다.
- **확인한 것:** 바깥에서 사이트(`https://`, `/health`, 갱신 경로)가 모두 정상이었다. 새 SSH 창에서 보니 `certbot-run` 임시 컨테이너가 남아 있지 않았다. 같은 명령을 새 창에서 다시 실행하니 몇 초 만에 `all simulated renewals succeeded`로 끝났다.
- **원인:** 서버나 certbot의 문제가 아니라 처음 사용한 SSH 창이 멈춘 것으로 보인다(정확한 원인은 확정하지 못함). 같은 증상이 이전에도 한 번 있었고 그때도 서버는 정상이었다.
- **해결:** 새 SSH 창을 열어 서버 상태를 확인하고 같은 명령을 다시 실행했다. 멈춘 창은 닫았다.
- **재발 방지:** 화면이 멈추면 서버가 멈췄다고 가정하지 말고 **바깥에서**(`curl`) 서비스 상태를 먼저 확인한다. 오래 걸릴 수 있는 명령에는 `timeout`을 붙인다. 새 창으로 남은 임시 컨테이너(`docker ps -a --filter name=...`)를 확인한다. 서버에 접속할 키는 `ls`로 실제 파일 이름을 확인하고 쓴다(예시 이름을 그대로 쓰면 `No such file`로 접속이 거부된다).

### H8. 시험 명령이 실패했는데 결과가 `0`으로 보여 무효 시험
- **증상:** MLflow DB 주소를 환경변수로 옮긴 뒤 "명령줄에 `postgresql://`이 남았는지"를 `docker top infra-mlflow-1 -eo args | grep -c "postgresql://"`로 확인했더니 `0`이 나왔다. 그런데 같은 출력에 `Error response from daemon: Couldn't find PID field in ps output`이 함께 찍혀 있었다.
- **원인:** `docker top`이 실패해서 `grep`이 빈 입력을 받았고, 그래서 개수가 `0`으로 나온 것이다. **명령이 실패한 결과를 "없음"으로 읽은 것**이라 시험이 아니었다. `-eo`로 출력 항목을 줄 때는 `pid`가 반드시 있어야 한다.
- **해결:** `-eo pid,args`로 다시 실행했고 이번에는 오류 없이 `0`이 나왔다. 컨테이너 환경변수가 `postgresql`로 시작하는지, DB에 MLflow 테이블이 있는지도 함께 확인해 파일 저장소로 떨어지지 않았음을 보였다.
- **재발 방지:** 개수·존재 여부를 세는 시험(`grep -c`, `wc -l`)은 **앞 명령이 성공했는지** 먼저 본다. `0`이 나오면 "정말 없다"와 "명령이 실패했다"를 구분한다. 부정적 결과를 확인하는 시험은 반대편(있어야 하는 것이 있는지)도 같이 본다.
- **근거:** `Infra/SECURITY.md` 3.4절 시험 기록, 이 항목은 H4(적용되지 않은 상태에서 한 시험)와 같은 계열이다.

## I. AI 서버·연동

AI 서버(`ai-api`)에 약점 구간 분석을 올리면서 겪은 문제다. 설계·사용법은 `AI/docs/coach-weak-segments.md`에 있다.

### I1. 배포한 AI 서버의 요약 로그가 Loki에 안 나옴 (파이썬 로깅)
- **증상(배포 직후 점검 중 발견):** 분석 뒤 `INFO` 요약 한 줄(`weak-segments reason=… segments=[…] elapsedMs=…`)을 남기도록 만들었는데, 운영 컨테이너 로그에는 접근 로그만 있고 요약 줄이 없을 것이라는 점을 코드 점검에서 알게 됐다. 시험(`pytest`의 `caplog`)은 통과했다.
- **원인:** uvicorn은 자기 로거(`uvicorn`, `uvicorn.access`)만 설정하고 root 로거에는 핸들러를 달지 않는다. 우리 로거 `ssaplash_ai.coach`는 핸들러가 없어서 `WARNING` 이상(`logging.lastResort`)만 출력되고 `INFO`는 버려진다. `caplog`는 로깅 설정과 무관하게 레코드를 잡아서 이 차이를 못 잡았다.
- **확인:** uvicorn의 `LOGGING_CONFIG`를 적용한 파이썬 프로세스에서 `INFO`와 `ERROR`를 남기면 `ERROR`만 출력됨을 로컬에서 확인했다.
- **해결:** 이 로거에 표준 출력 핸들러를 달고 `INFO`로 설정했다(`propagate`는 유지해 `caplog` 시험도 동작). uvicorn 로깅 설정을 적용한 상태에서 요약 줄이 표준 출력으로 나가는지 확인하는 시험을 추가했다. 수정은 다음 배포에 반영된다.
- **배포 후 확인:** 수정 배포 뒤 Grafana Explore(Loki)에서 `{service="ai-api"} |= "weak-segments reason="`로 요약 줄이 조회됨을 확인했다. 이 쿼리들을 모아 "약점 분석 연동" 대시보드(`coach-weak-segments.json`)를 만들었다.
- **재발 방지:** 로그에 의존하는 기능은 **운영과 같은 로깅 설정에서** 출력되는지 시험한다. 배포 직후에는 `docker logs`와 Grafana(Loki)에서 실제로 찍히는지 본다.
- **근거:** `AI/src/ssaplash_ai/server/weak_segments.py`, `AI/tests/server/test_weak_segments.py`, `Infra/monitoring/alloy/config.alloy`(로그 수집 라벨 `service`).

### I2. 운영에 없는 FE 기능을 "있다"고 안내함
- **증상:** "플레이하면 서버 DB에 기록된다"고 안내하고 DB 조회 시험을 권했는데, 운영 FE에는 서버 업로드 코드가 없었다. 운영 FE는 기록을 브라우저 `localStorage`에만 쌓고 있었다.
- **원인:** 업로드 코드(`playUpload.ts`, `playSync.ts`, `api/plays.ts`)를 `develop-FE`에서 읽고 **운영(`main`)에 반영됐는지 확인하지 않았다.** 개발 브랜치의 코드를 운영 동작으로 착각했다.
- **해결:** `git ls-tree origin/main`으로 운영에 파일이 없음을 확인하고 정정했다. FE 담당에게 업로드(185)의 `main` 배포 일정을 묻기로 했다.
- **재발 방지:** 운영 동작을 설명하거나 서버에서 시험하기 전에 **배포 대상 브랜치(`main`)에 해당 코드가 있는지** 먼저 확인한다. 연동 시험의 선행 조건(어느 파트가 운영에 나가야 하는가)을 요청 문서에 적는다.
- **근거:** `git ls-tree origin/main FE/src/domain/playUpload.ts` 결과 없음, `FE/src/engine/playLog.ts` 주석("서버 업로드는 BE API가 나오면 붙인다").

### I3. `pytest`의 `TestClient`가 이벤트 루프를 못 만듦 (`WinError 10014`)
- **증상:** 서버 API 시험이 실행할 때마다 다른 테스트가 `OSError: [WinError 10014] … 잘못된 포인터 주소`로 실패했다. 기존 `test_health`도 같은 영향을 받았다. 오류 위치는 `socket.socketpair()`의 `listen()`이었다.
- **원인:** asyncio 이벤트 루프가 내부에서 루프백 소켓 쌍을 만들 때 이 PC의 네트워크 계층이 간헐적으로 실패한다. A2(`Bad address: listen`), H6(nmap `10014`)와 같은 계열의 환경 문제로 보이며 원인은 확정하지 못했다. 코드의 문제가 아니다.
- **해결:** 요청 처리 로직을 이벤트 루프 없이 부를 수 있는 동기 함수 `process_body`로 분리해 대부분의 시험이 이 함수를 직접 호출하게 했다. 라우팅 연결만 확인하는 시험 3개는 루프를 못 만드는 PC에서 이유를 밝히고 건너뛰게 했다(`pytest.skip`). 건너뛴 시험은 CI(Linux)에서 확인한다.
- **재발 방지:** 환경 문제를 시험 로직 우회로 숨기지 않고 **건너뛴 이유를 출력에 남긴다.** 이 PC에서 실패해도 코드 결함으로 단정하기 전에 같은 계열의 이전 사례(A2, H6)를 확인한다. 참고로 전체 테스트의 기존 12건(`test_bss_eval_metrics`, `test_benchmark_runner`)은 ffmpeg가 없어서 이 PC에서 실패하며 이번 변경과 무관하다.
- **근거:** `AI/tests/server/test_weak_segments.py`, `AI/src/ssaplash_ai/server/weak_segments.py`(`process_body`).

### I4. 일회성 컨테이너의 로그를 Alloy가 놓칠 수 있음 (예방, 서버 확인 전)
- **증상(예상, 아직 겪지 않음):** 약점 분석 보정 배치(`coach-calibration`)는 1분 안에 끝나는 일회성 컨테이너다. 끝에 남기는 상태 줄(`coach-calibration status=...`)을 Loki 알림이 보게 설계했는데, 이 줄이 Loki에 안 들어갈 수 있다.
- **원인(공식 문서로 확인):** Alloy `discovery.docker`의 새로고침 주기(`refresh_interval`) 기본값이 **1분**이다. 컨테이너가 떠 있는 동안 한 번도 새로고침이 안 되면 로그 수집 대상에 오르지 못한다. 새로 발견한 컨테이너의 로그를 처음부터 읽는지는 문서에 없다.
- **해결(예방):** 탐색 주기를 5초로 줄였다(`monitoring/alloy/config.alloy`). 배치는 시작 직후와 종료 직전에 15초씩 기다린 뒤 끝나게 해서(`docker-compose.yml`의 `entrypoint`), 탐색이 붙은 뒤에 상태 줄이 나오고 줄이 읽히기 전에 컨테이너가 사라지지 않게 했다. 그래서 한 번 실행에 최소 30초가 걸린다.
- **확인:** `docker compose config` 렌더링과 래퍼 스크립트(비밀번호 누락 중단, 인자·종료 코드 전달)는 시험했다. **Alloy가 일회성 컨테이너의 줄을 실제로 Loki에 넣는지는 서버에서 첫 실행 뒤 `{service="coach-calibration"}`로 확인해야 한다.**
- **재발 방지:** 일회성·단명 컨테이너의 로그에 의존하는 알림은 수집이 붙는 시간을 먼저 의심한다. 설정 파일을 마운트해 쓰는 Alloy는 `up -d`로 다시 읽지 않으므로 변경 뒤 `docker compose -p infra restart alloy`가 필요하다. 이 변경이 반영되기 전에는 "36시간 실행 기록 없음" 알림을 켜지 않는다(켜면 계속 울린다).
- **근거:** `Infra/docker-compose.yml`(`coach-calibration`), `Infra/monitoring/alloy/config.alloy`, `Infra/README.md`("약점 분석 보정 배치").

### I5. 예약 파이프라인에서 기존 job이 같이 도는 문제 (예방, MR 파이프라인에서 확인 필요)
- **증상(예상, 아직 겪지 않음):** 보정 배치를 GitLab 예약 파이프라인으로 돌리려고 하니, 예약 파이프라인에서 `lint`·`test`·`build`와 BE 시험(`be-*`)이 같이 돌고 `main`용 수동 배포·롤백 job도 대기 상태로 생기게 된다.
- **원인:** `workflow.rules`가 `main`이면 파이프라인을 만들고, 규칙이 없는 job은 모든 파이프라인에 들어간다. `be-*`의 `rules:changes`는 예약 파이프라인에서 **항상 참**으로 계산된다. 수동 배포·롤백은 `main`이면 만들어진다.
- **해결(예방):** 숨은 job `.calibration-guard`(`!reference`)를 만들어 `lint`·`test`·`build`·`.be-job`·`.deploy-job`의 `rules` 맨 앞에 붙였다. `COACH_CALIBRATION == "true"`이거나 예약 파이프라인이면 `when: never`다. 보정 job은 그 조건에서만 만들어진다. 일반 파이프라인(MR, `main` 병합)의 규칙은 이전과 같다.
- **주의:** `COACH_CALIBRATION`을 프로젝트 CI/CD 변수로 등록하면 모든 파이프라인이 보정 전용이 되어 다른 job이 빠진다.
- **확인:** `.gitlab-ci.yml`을 파싱해 구조는 확인했다. GitLab의 `!reference` 처리와 실제 파이프라인 생성은 **MR 파이프라인이 만들어질 때** 확인한다.
- **재발 방지:** 예약·수동 전용 job을 넣을 때는 기존 job이 그 파이프라인에 들어가는지부터 점검한다. `rules:changes`는 예약·수동 파이프라인에서 의미가 다르다.

### I6. 정책 파일이 서버 이미지에 없는데 조용히 빈 정책으로 동작 (코드로 막음)
- **증상(문서를 쓰다 발견, 운영에서 겪지 않음):** 보정 배치의 정책 파일(`AI/configs/coach/calibration_policy.yaml`)이 서버 이미지에 없는데, 정책 로더가 파일이 없으면 오류 없이 **빈 정책**(후보 없음)으로 넘어가서, 컨테이너에서 정책 마운트를 빠뜨려도 배치가 정상처럼 돌았을 것이다.
- **원인:** `AI/Dockerfile`이 `COPY src ./src`만 해서 `configs/`는 이미지에 안 들어간다. 로더는 "없으면 빈 정책"으로 만들어져 있었다.
- **해결:** 경로를 **명시했는데** 파일이 없으면 `PolicyError`로 실패하게 했다(`SSAPLASH_CALIBRATION_POLICY` 또는 `--policy`). 기본 경로만 빈 정책을 허용한다. 컨테이너는 정책 디렉터리를 읽기 전용으로 마운트하고 경로를 환경 변수로 준다.
- **재발 방지:** "없으면 기본값으로" 동작은 개발 편의와 운영 사고를 가른다. 운영에서 필수인 파일을 명시했는데 없으면 조용히 넘어가지 않고 실패하게 한다.
- **근거:** `AI/src/ssaplash_ai/coach_calibration/policy.py`, `AI/tests/coach_calibration/test_policy.py`, `Infra/docker-compose.yml`.

### I7. ZAP 공격 스캔이 테스트 계정을 탈퇴시켜 결과가 무효가 됨 (로컬에서 겪음, 문서에서 작업을 빼서 해결)
- **증상:** 로컬 환경에서 ZAP 공격 스캔을 돌렸더니 "실패 0건, 통과 117개"로 끝났다. 그런데 nginx 로그의 응답 코드 약 2만 건이 `401`이었다. 테스트 사용자 두 명(일반·관리자)이 `WITHDRAWN` 상태였다.
- **원인:** 스캔이 `DELETE /api/users/me`(회원 탈퇴)를 호출했다. 이 경로를 스캔 설정(`-z "-config globalexcludeurl..."`)으로 제외하려 했지만 적용되지 않았다. 탈퇴되자 이후 요청은 모두 "사용할 수 없는 계정" `401`이 되어, 스캔 대부분이 인증 없이 나간 것과 같았다. 요청이 모두 거절되면 공격이 "통과"한 것처럼 보인다.
- **해결:** OpenAPI 문서에서 그 작업(`DELETE /api/users/me`)을 **파일에서 지우고** 다시 돌렸다. 탈퇴된 사용자는 지우고 다시 만들었다.
- **재발 방지:** 탈퇴·삭제처럼 계정을 망가뜨리는 API는 스캔 설정의 제외 규칙에 맡기지 말고 입력에서 뺀다. 스캔이 끝나면 "통과 N개"만 보지 말고 응답 코드 분포(`401` 비율)와 테스트 계정 상태를 먼저 확인한다.
- **근거:** `Infra/SECURITY.md` 16절. 스캔 환경은 `ssaplash-local` 프로젝트로 분리했고 끝난 뒤 지웠다.

### I8. 동의 문구와 실제 동작이 다름 (2026-11-06, 문구 검토 중 발견)
- **증상:** 필수 동의 문구는 탈퇴 시 연주 기록이 삭제된다고 썼지만 `consent=true` 세션은 남았다. 추천 동의 문구안의 "최대 7일 보관 뒤 삭제"도 삭제 코드가 없었다.
- **원인:** 문구와 구현을 다른 시점에 다른 사람이 썼고, 대조하는 단계가 없었다. "서빙하지 않는다"를 "삭제한다"로 이해한 부분도 있었다.
- **해결:** 탈퇴 세션을 삭제하고, 만료 후보 삭제 작업을 넣었다. 나머지는 `SECURITY.md` 20절의 표대로 처리했다.
- **정정:** 처음에는 "이미 학습한 값은 지울 수 없다"고 설명했는데 틀렸다. 배치는 모델을 저장하지 않아 다음 배치에서 사라진다. 또 "복원하면 스케줄러가 다시 지운다"는 설명도 탈퇴 전 백업에서는 틀렸다.
- **재발 방지:** 개인정보 문구를 확정하기 전에 항목마다 코드 위치를 대조한다. 일반론이 아니라 실제 구조로 설명한다.
- **근거:** `SECURITY.md` 20절.

### I9. 추천 배치가 적재는 했는데 MLflow 기록에서 403으로 실패 (2026-11-17 예약 실행)
- **증상:** 매일 새벽 4시 `recommend-batch` 예약 job이 실패로 끝났다. 로그에는 후보 계산과 BE 적재(`accepted: 8`)가 끝난 뒤 `mlflow.set_experiment`에서 `403 != 200`, `Invalid Host header - possible DNS rebinding attack detected`가 찍혔다.
- **원인:** MLflow 3.x 서버는 요청의 `Host` 헤더를 검사하고 기본으로 `localhost`와 사설 IP만 받는다. 배치 컨테이너는 compose 서비스 이름 `http://mlflow:5000`으로 접속해서 `Host: mlflow:5000`이 거부됐다. `Infra/mlflow/README.md`에 "거부될 수 있다(아직 확인 못함)"로 적어 두었던 위험이 처음 다른 컨테이너에서 MLflow에 기록할 때 드러났다. 그동안은 SSH 터널(`localhost`)과 같은 컨테이너 안의 게시 도구(`127.0.0.1`)만 접속해서 몰랐다.
- **영향:** 추천 후보 적재는 끝난 뒤라 사용자 추천은 정상이었다. MLflow에 집계 값이 남지 않았고 job이 실패로 보였다. 같은 주소로 기록하는 `coach-calibration`도 같은 이유로 실패할 수 있었다.
- **해결:** compose `mlflow` 명령에 `--allowed-hosts mlflow,mlflow:5000,localhost,localhost:5000,127.0.0.1,127.0.0.1:5000`을 더했다. 이 옵션은 기본 목록을 대신하므로 기존 접속(`localhost`·`127.0.0.1`)도 함께 적었다. `*`(전부 허용)는 쓰지 않았다. 배포의 `up -d`가 명령이 바뀐 `mlflow` 컨테이너를 다시 만든다.
- **확인:** 배포 뒤 Run pipeline(`main`, `RECOMMEND_BATCH=true`)으로 한 번 실행해 마지막 줄이 `recommend-batch status=OK`인지 본다.
- **재발 방지:** 문서에 "아직 확인 못함"으로 남긴 위험은, 그 경로를 처음 쓰는 기능(새 배치 등)을 배포하기 전에 서버에서 한 번 확인한다. 새 컨테이너가 MLflow에 접속하게 되면 허용 목록에 그 호스트 이름이 있는지 본다.
