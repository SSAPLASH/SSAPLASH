# 모니터링·로그

서버·컨테이너 지표와 컨테이너 로그를 모아 Grafana에서 본다. 서비스별 커스텀 지표(채보 처리 시간 등)와 알림 전송 채널은 후속이다.

## 구성

| 서비스 | 역할 | 보관 | 호스트 포트 |
| --- | --- | --- | --- |
| `prometheus` | 지표 저장 | 15일 또는 5GB | 없음 |
| `node-exporter` | 서버(호스트) CPU·메모리·디스크 지표 | — | 없음 |
| `cadvisor` | 컨테이너별 지표 | — | 없음 |
| `loki` | 로그 저장 | 7일 | 없음 |
| `alloy` | 컨테이너 로그를 모아 Loki로 보냄(Promtail 후속) | — | 없음 |
| `grafana` | 지표와 로그를 한 화면에서 봄 | — | `127.0.0.1:3000`만 |

- **외부에 공개하지 않는다.** Grafana는 서버의 `127.0.0.1:3000`에만 열려 있고 나머지는 포트를 열지 않는다.
- 모든 서비스의 컨테이너 로그 파일은 크기를 제한한다(10MB × 3개). 로그 파일이 서버 디스크를 채우지 않게 하는 한도이고, 장기 보관과 검색은 Loki가 맡는다.
- 서비스별 메모리 한도 합계는 약 1.8GB다(서버 15GB). 실측 후 조정한다.

## 접속

서버 접속 권한이 필요하다. SSH 터널로 접속한다.

```
ssh -i <키 파일> -L 3000:localhost:3000 ubuntu@k15a307.p.ssafy.io
```

터널이 열린 상태에서 내 PC 브라우저로 `http://localhost:3000`을 연다. 계정은 `admin`이고 비밀번호는 서버 `Infra/.env`의 `GRAFANA_ADMIN_PASSWORD`다. 비밀번호를 채팅·이슈·문서에 붙이지 않는다. 비어 있으면 Compose가 실행을 멈춘다.

## 보는 법

- **대시보드:** `인프라` 폴더의 `인프라 개요`. CPU·메모리·디스크 사용률, 실행 중인 컨테이너 수, 컨테이너별 CPU·메모리, 컨테이너 로그가 있다.
- **로그 검색:** 대시보드 위쪽 `서비스` 선택(여러 개 가능)으로 서비스별 로그를 본다. 더 자세히는 Explore에서 Loki를 선택하고 `{service="api"}`처럼 검색한다. 라벨은 `service`(Compose 서비스 이름), `container`다.
- **알림:** Alerting → Alert rules의 `인프라` 폴더. 현재 규칙은 세 가지이고 조건을 넘으면 이 화면에 표시된다. 알림을 밖으로 보내는 채널(메신저 웹훅 등)은 비밀 값이 필요해 후속으로 붙인다.

| 규칙 | 조건 |
| --- | --- |
| 디스크 사용률 85% 초과 | 루트 파일 시스템 사용률이 5분 넘게 85% 초과 |
| 사용 가능 메모리 10% 미만 | 5분 넘게 10% 미만 |
| 핵심 컨테이너 중단 | 앱·DB·Redis·Nginx 중 하나 이상이 5분 넘게 보이지 않음(지표가 사라져도 경보) |

## 설정 파일

| 파일 | 내용 |
| --- | --- |
| `prometheus.yml` | 수집 대상. 보관 기간과 용량 한도는 `docker-compose.yml`의 실행 옵션에 있다 |
| `loki-config.yaml` | 로그 저장 위치와 보관 기간(7일) |
| `alloy/config.alloy` | 로그 수집, 서비스 라벨, **비밀·개인정보 가림 규칙** |
| `grafana/provisioning/` | 데이터 소스, 대시보드 위치, 알림 규칙. 서버를 다시 만들어도 같은 화면이 복원된다 |
| `grafana/dashboards/infra-overview.json` | 대시보드 원본. 화면에서 고쳐도 저장되지 않으므로 이 파일을 고친다 |

설정 파일을 고친 뒤에는 해당 서비스를 다시 시작해야 반영된다(파일 하나를 컨테이너에 연결한 방식이라 Compose가 변경을 감지하지 못한다).

```
docker compose -p infra restart prometheus loki alloy grafana
```

## 로그의 비밀·개인정보 가림

Alloy가 로그를 Loki로 보내기 전에 아래를 가린다. 첫 번째 그룹으로 잡힌 부분만 `***`로 바뀐다.

1. Bearer 토큰, 2. 로그인 토큰(JWT) 형태, 3. `password`·`secret`·`token`·`api key`·`authorization` 뒤의 값, 4. 이메일 주소

- **규칙 순서가 중요하다.** Bearer 규칙이 key=값 규칙보다 앞에 있어야 한다. 순서가 반대면 `Authorization: Bearer 토큰`에서 "Bearer"라는 단어만 가려지고 토큰이 그대로 남는다(시험에서 실제로 확인한 문제다, `Infra/TROUBLESHOOTING.md` F1).
- 규칙을 바꿀 때는 실제 로그 모양으로 시험하고 가려진 결과에 원문이 남지 않는지 확인한다.
- 앱 로그에 비밀·개인정보를 남기지 않는 것이 먼저다. 가림 규칙은 마지막 안전장치다.

## Docker 소켓 위험

로그를 서비스 이름으로 구분하려면 `alloy`가 Docker 소켓으로 컨테이너 목록을 알아야 한다. **Docker 소켓은 사실상 서버 전체 권한이다.** 읽기 전용(`:ro`)으로 마운트해도 API 호출은 막히지 않는다. 이를 줄이려고 다음을 지킨다.

- `alloy`는 포트를 열지 않고 내부 네트워크에만 둔다.
- 이미지 버전을 고정하고 임의로 올리지 않는다.
- 다른 서비스에 Docker 소켓을 마운트하지 않는다.

`node-exporter`와 `cadvisor`는 호스트의 파일 시스템과 컨테이너 정보를 읽기 전용으로만 마운트한다.

## 서버 반영 시 확인할 것

처음 반영할 때 확인한다(결과는 `Infra/TROUBLESHOOTING.md`에 기록).

- `cadvisor` 이미지(`gcr.io`)가 서버에서 받아지는지. 받아지지 않으면 대안 이미지를 찾는다.
- `cadvisor`가 특권 없이 컨테이너 지표를 내는지(안 되면 필요한 권한을 최소로 추가).
- Prometheus의 Targets 화면에서 `node`, `cadvisor`가 모두 `UP`인지.
- 대시보드의 디스크 사용률이 값을 보이는지(마운트 경로 표기가 환경마다 다를 수 있다).
- Grafana 로그에 프로비저닝 오류(데이터 소스, 대시보드, 알림 규칙)가 없는지.
- 로그 가림 규칙이 Alloy(Go 정규식)에서 시험과 같이 동작하는지. 가림 규칙을 시험한 환경은 Python이다.
- 앱의 실제 로그에 토큰·이메일이 남지 않는지, 남는 값이 있으면 BE에 알린다.
- Grafana가 외부에서 접근되지 않는지(서버 밖에서 3000번이 닫혀 있는지).

## 문제 해결

| 증상 | 원인과 해결 |
| --- | --- |
| `GRAFANA_ADMIN_PASSWORD`로 실행이 멈춤 | `.env`에 값을 채운다 |
| Grafana에 지표가 없음 | `prometheus`가 떠 있는지, Prometheus Targets가 `UP`인지 확인한다 |
| 로그가 안 보임 | `docker compose -p infra logs alloy --tail 40`. Docker 소켓 접근 오류인지 본다 |
| `loki`가 시작하지 않음 | `docker compose -p infra logs loki --tail 40`. 설정 파일 문법과 볼륨 권한을 확인한다 |
| 디스크가 빠르게 참 | 로그 한도(10MB×3)가 적용됐는지, `docker system df`로 이미지·볼륨 사용량을 본다. **`docker volume prune`은 실행하지 않는다** |
