# 작업 흐름 (workflow)

구현 요청은 **설계 → 계획 → 구현 → 검증** 네 단계로 진행한다. 설계 문서가 단일 진실이고, 단계마다 산출물 경로와 사용자 확인 지점이 정해져 있다. 어떤 실행 방식(한 세션 순차 / 서브에이전트 병렬)을 택하든 **산출물은 같다**.

## 원칙

1. **설계 문서 없이 구현을 시작하지 않는다.** 스캐폴딩(`npm create`, 폴더 생성)도 구현이다.
2. **구현 단계는 설계를 수정하지 않는다.** 설계와 어긋나는 점을 발견하면 코드를 더 쓰지 말고 설계 문서 "미결 사항"에 올린 뒤 사용자에게 보고한다.
3. **검증에는 설계 문서의 인수 조건과 코드만 준다.** 구현 과정(대화 기록, 시도한 것, 구현자의 설명)은 주지 않는다. 자기 구현을 자기가 검증하지 않게 하기 위해서다.
4. **인수 조건은 기능명세서(Notion `기능명세서`)의 "인수 조건 (완료 기준)" 열에서 가져온다.** 기능명세서에 없는 조건은 설계 문서가 추가하되 출처를 "이 문서"로 표시한다.
5. 설계 문서는 **한국어**로, 코드 블록 없이 쓴다. 타입·프로토콜은 표로 적는다.
6. **설계·계획·검증 문서는 개인 작업 문서다.** `.claude/plans/`에 두며 git으로 관리하지 않는다. `Docs/`에는 팀 전체가 공유할 문서만 둔다. 다른 파트와 맞춰야 하는 인터페이스는 `mail` skill로 요청 문서를 작성하고(전달은 사용자가 직접 한다), 팀 확정 문서로 올릴 내용은 사용자가 지시할 때만 `Docs/`에 옮긴다.

## 단계

| 단계 | 입력 | 산출물 | 경로 | 사용자 확인 |
| --- | --- | --- | --- | --- |
| 1 설계 | 사용자 요청, `Docs/Service Design/공통 명세서.md`, Notion 기능명세서·관련 설계 문서, 기존 코드 | 설계 문서 | `.claude/plans/{스토리 코드}-{주제}.md` (여러 스토리면 `{EPIC1}-{EPIC2}-{주제}.md`) | **필수.** 승인 전 코드 작성 금지 |
| 2 계획 | 승인된 설계 문서 | 작업 목록: 파일 단위 작업, 순서, 각 작업의 완료 기준, Jira 작업(Task) 후보 제목 | 설계 문서 끝에 "## 작업 계획" 절로 추가 | **필수.** 티켓 생성 여부·순서 결정 |
| 3 구현 | 설계 문서 + 작업 1개 (구현 브리프) | 코드, 파트 README 갱신, lint·빌드 통과 | 해당 파트 폴더 | 불필요. 작업 단위로 보고 |
| 4 검증 | 설계 문서 인수 조건 + 코드 (검증 브리프) | 검증 리포트: 조건별 통과/실패, 재현 절차, 실패 원인 추정 | 설계 문서 끝에 "## 검증 결과" 절로 추가 | 보고 후 **사용자가 커밋 판단** |

설계 문서는 [design-template.md](design-template.md)의 절 구성을 그대로 쓴다. 절을 추가·삭제·순서 변경하지 않는다. 계획·검증 절은 템플릿의 마지막에 이어 붙인다.

### 1 설계

- 공통 명세서와 Notion 기능명세서를 먼저 읽는다. 관련 스토리 코드(`PLAY-008` 등)를 문서 머리 표에 적는다.
- 다른 파트와 맞춰야 하는 인터페이스(API, 데이터 포맷, 통신 프로토콜)는 설계 문서에 적되, 합의 요청은 **설계 승인 후** `mail` skill로 요청 문서를 작성한다. 문서 경로를 알리면 전달은 사용자가 직접 한다. 설계 문서는 요청 문서가 아니다.
- 팀 결정이 필요한 것은 "미결 사항"에 번호를 붙여 모은다. 결정 없이 가정으로 진행하면 가정임을 표시한다.
- 문서 경로를 사용자에게 알리고 **멈춘다.**

### 2 계획

- 작업은 Jira 컨벤션 7장(권장 크기: 반나절~하루)에 맞춰 나눈다. 작업 제목은 Jira 컨벤션 3.4 형식(`[스토리 코드] 작업 내용`)으로 후보만 적고, **생성은 사용자가 한다. 사용자가 명시적으로 생성을 지시한 경우에만 Atlassian MCP로 만든다.**
- 스프린트가 이미 시작된 뒤 생긴 작업이면 후보 제목을 Jira 컨벤션 2.6 형식(`[스토리 코드 | 담당 영역] 작업명`, 본인 `[Extra] 추가 작업`의 서브 작업)으로 적는다. 이 서브 작업도 사용자의 명시적 지시 없이는 만들지 않는다. 어느 경우든 활성 스프린트에 작업을 새로 넣거나 스토리 포인트를 입력하는 일은 하지 않는다 (CLAUDE.md 커밋·브랜치 규칙 참고).
- 각 작업에 "완료 기준"을 한 줄씩 적는다. 검증 단계가 이걸 본다.
- 브랜치는 Git 컨벤션대로 **Epic prefix**(`feat/{Epic prefix}-{내용}`), 커밋은 **Task 키**(`[S15P31A307-N] type: subject`)를 쓴다. 계획 절에 브랜치 이름 후보를 적는다.
- 사용자가 확인하면 구현으로 간다.

### 3 구현

- [brief-implement.md](brief-implement.md) 형식으로 브리프를 만든다 (서브에이전트에 넘기거나, 같은 세션이면 그 내용을 기준으로 작업).
- 설계 문서의 모듈 경계·인터페이스를 그대로 따른다. 이름(필드명·파일명)도 바꾸지 않는다.
- 작업 하나가 끝나면 lint·빌드를 돌리고 결과를 보고한다. 커밋은 사용자가 요청할 때만.

### 4 검증

- [brief-verify.md](brief-verify.md) 형식으로 브리프를 만든다. **구현 과정은 넣지 않는다.**
- 조건마다 통과/실패와 **재현 절차**(명령, 키 입력, 기대 화면)를 적는다. "될 것 같다"는 통과가 아니다. 브라우저 확인이 필요한 조건은 실제로 실행해 본다.
- 실패 항목은 구현 단계로 돌려보내되, 설계 변경이 필요하면 미결 사항으로 올린다.

## 실행 방식

| 방식 | 언제 | 어떻게 |
| --- | --- | --- |
| **최소 모드 (기본)** | 개인 플랜·토큰이 제한적일 때, 작업이 작을 때 | 한 세션에서 1 → 2 → 3 → 4를 순서대로. 단계 사이에 사용자 확인 지점을 지킨다. 검증 단계에서는 브리프에 적힌 것만 보고 처음 보는 코드처럼 읽는다 |
| **병렬 모드 (선택)** | 작업이 여러 파일·여러 독립 작업으로 나뉠 때, 플랜 여유가 있을 때 | 설계는 메인 세션이 한다. 계획 확인 후 작업별 구현 브리프를 서브에이전트에 나눠 주고, 완료된 작업마다 **별도** 서브에이전트에 검증 브리프를 준다. 메인 세션은 결과를 모아 설계 문서의 계획·검증 절에 기록한다 |

두 방식의 산출물(설계 문서, 계획 절, 코드, 검증 절)은 같다. 팀원마다 플랜이 달라도 리뷰와 인수인계는 같은 문서를 본다. 병렬 모드는 사용자가 명시적으로 요청할 때만 쓴다 (서브에이전트는 토큰을 많이 쓴다).

## 다른 규칙과의 관계

- `mail` skill: 파트 간 합의가 필요한 인터페이스는 설계 승인 후 `mail` skill로 요청 문서를 작성한다(전달은 사용자). 설계 문서에 "EMB 파트에 요청할 것" 같은 절을 두고, mail 문서는 그 절을 참조한다.
- Git 컨벤션: 브랜치·커밋·MR 규칙은 그대로. 이 skill은 "언제 코드를 쓰기 시작하는가"만 정한다.
- Jira 컨벤션: 작업 분리 기준(7장)·완료 기준(16장)을 계획·검증 단계가 따른다.
- CLAUDE.md: 커밋·푸시는 요청받았을 때만. 검증 통과가 커밋 허가는 아니다.

## 예외

- 자명한 한 줄 수정, 오탈자, 설정값 변경, 문서만 바꾸는 작업은 설계 단계를 생략한다. 애매하면 사용자에게 "설계 문서가 필요한 규모인지" 한 줄로 묻는다.
- 이미 승인된 설계 문서가 있는 기능의 후속 작업은 설계를 다시 쓰지 않고 계획 절에 작업을 추가한다.
