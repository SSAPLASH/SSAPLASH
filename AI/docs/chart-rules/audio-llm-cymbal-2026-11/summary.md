# 오디오 LLM으로 마디 단위 하이햇·라이드 구분 시험 결과

측정일 2026-11-09 ~ 11-10 · Jira S15P31A307-325 · 문제 3,513마디(실제 곡 48곡: 검증 10곡, 확인용 38곡) · 작은 시험 120마디 · GPU 서버 H200 6번

## 결론

- 실패함. 소리를 직접 듣는 LLM 6개 모두 마디마다 하이햇과 라이드를 가려내지 못함
- 같은 120마디에서 기존 방법보다 나은 모델이 없음. 가장 나은 Qwen3-Omni 원곡도 AUC 0.703으로 지금 채보 0.723보다 낮음
- 모든 모델이 소리와 상관없이 한 글자로 몰아서 답함(대부분 전부 하이햇)
- 서비스 설정은 그대로임

## 1. 왜 해 봤나

- 지금 채보는 몇몇 곡에서 라이드로 친 구간을 하이햇으로 적음. 정답을 보고 마디마다 하이햇↔라이드를 통째로 바꾸면 확인용 8곡 8패드 F1이 +0.0233 오름. 이 상승은 November Rain(0.763 → 0.892)과 Good Times Bad Times(0.717 → 0.752) 두 곡에서 거의 다 나옴
- 같은 바꾸기를 8패드 모델 확률이나 분리 트랙 에너지로 정하면 8패드 F1이 오히려 떨어졌음(−0.008)
- 텍스트 LLM은 소리를 못 들어 이 판단을 할 수 없었음. 오디오 LLM은 공개 벤치마크(MusTBench)에서 시각을 3초 범위로만 맞혀서 타격 하나하나는 못 짚지만, 몇 초 길이 구간에서 어떤 소리가 나는지는 물을 수 있음. 그래서 마디 하나를 들려주고 박을 세는 심벌을 물음

## 2. 방법

- 문제: 정답 채보에서 마디 안 하이햇·라이드 노트가 4개 이상이고 한쪽이 75% 이상인 마디만 고름. 박 위치로 나눈 마디 길이가 0.8 ~ 6초인 마디만 씀. 원곡과 분리 드럼(채보 모델에 넣는 드럼)을 마디 길이로 잘라 16kHz 모노 wav로 저장
- 작은 시험: 검증 10곡·확인용 30곡에서 라이드 60마디, 하이햇 60마디. 곡당 라벨마다 4마디까지, 지금 채보가 틀린 마디를 먼저 넣어 53마디가 지금 채보가 틀린 마디
- 질문: "드러머가 이 마디에서 박을 세며 반복해 치는 심벌이 하이햇이면 H, 라이드면 R, 둘 다 아니면 N으로 한 글자만 답하라"(영어)
- 점수: 서버 모델은 첫 답 토큰 위치의 H·R·N 토큰 확률을 직접 읽음. AUC는 라이드 확률 − 하이햇 확률로 라이드 마디를 가려내는 정도(0.5는 찍기)
- 비교 기준: 같은 마디의 지금 채보 이름, 8패드 모델 하이햇·라이드 확률 평균 차, 분리 트랙 하이햇·라이드 에너지 비율 차
- 통과 기준: AUC 0.80 이상이고 8패드 모델·분리 트랙 기준보다 0.05 이상 높음. 통과하면 3,513마디 전체로 넓히기로 함. 통과한 모델이 없어 전체는 돌리지 않음

- Gemini는 이 경로에서 토큰 확률을 주지 않음(interactions API에 확률 필드가 없고, generateContent의 logprobs는 "Logprobs is not enabled for this model"로 거절). 그래서 글자와 0 ~ 100 확신도를 같이 답하게 하고 확신도로 AUC를 냄. 서버 모델과 점수 내는 방식이 달라 나란히 비교하지 않음
- Gemini는 75번 모두 형식대로 답했고 확신도는 대부분 95. 75번에 25,906토큰(입력 9,831, 생각 15,770, 답 305)을 씀. 이 모델은 생각 끄기(minimal)를 받지 않아 low로 둠

## 4. 확인한 것과 하지 않은 것

- Nemotron-3-Nano-Omni, Audio Flamingo Next, Kimi-Audio는 서버에서 실행 오류로 답을 못 냄. 원인은 flash-attn 설정(sdpa로 바꿈), 생성 머리 없는 클래스로 불림(생성용 클래스로 바꿈), uv가 PyTorch 저장소만 보다 패키지 버전을 못 찾음(모든 저장소를 보게 바꿈). 스크립트는 고쳤고 다시 돌리지 않음
- Qwen3-Omni는 첫 실행에서 audioread 없음, 두 번째에서 생성 결과를 둘로 나눠 받다 실패. 고친 뒤 서버와 같은 transformers 5.22.2와 무작위 가중치 작은 Qwen3-Omni로 로컬에서 끝까지 돌려 확인하고 서버에서 다시 돌림
- 질문 문장을 바꿔 보지 않음. 다만 AUC는 답 글자가 아니라 확률 순서로 매겨서 한쪽으로 몰린 답에도 가려내는 힘이 있으면 드러나는데, 그 값도 기존 방법보다 낮았음
- 타격 시각, 크래시, 탐, 하이햇 열림·닫힘은 다루지 않음

## 5. 다시 해 볼 조건

- 공개 오디오 LLM이 악기 구분 벤치마크에서 하이햇과 라이드를 가려낸다는 결과가 나올 때. 새 모델은 MR !411 이력의 `cymrole_audio_llm.py`에 백엔드 하나를 더하면 같은 120마디로 비교할 수 있음

## 6. 다시 돌리는 법

실험 스크립트 `cymrole_audio_*.py`와 서버 노트북은 S15P31A307-324에서 저장소에서 뺐고 MR !411 이력에 남아 있음. 문제 만들기(`cymrole_audio_cases.py`)는 로컬 채보 결과(`data/results/judge/*/private/chart.npz`), 박 위치, 실제 곡 학습 가중치와 11/09 AI 판정 실험 스크립트(`judge_cymrole.py`·`judge_song.py`·`judge_recheck.py`, 저장소에 없음)가 있어야 돎. 판정·채점·서버 실행은 만들어 둔 문제 폴더만 있으면 돎.
