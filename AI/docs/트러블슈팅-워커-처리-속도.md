# GPU 서버 워커 처리 속도 트러블슈팅

| 항목 | 내용 |
| --- | --- |
| 날짜 | 2026-11-10 |
| 대상 | GPU 서버 6번 GPU에서 도는 운영 워커 `ssaplash-worker run` |
| 결과 | 같은 곡 uptown funk 처리 시간 71.5초 → 30.0초 |

## 요약

사이트에 곡을 올리면 서버 워커가 악기 분리, 드럼 채보, 결과 제출을 함. 이 처리 시간이 곡마다 40초에서 545초까지 들쭉날쭉했음.

원인은 워커 프로세스가 어느 CPU 코어에서 도느냐였음. 이 서버는 CPU 코어가 NUMA 노드 2개로 나뉘어 있음. NUMA 노드는 CPU 코어와 메모리를 묶은 단위이고, 프로세스는 자기 노드의 메모리를 쓸 때 가장 빠름. 측정해 보니 CPU 128~255번 코어에서 돌면 같은 곡이 10배 느렸음. 리눅스는 워커를 띄울 때마다 코어를 바꿔 가며 배정하기 때문에, 그때그때 어느 쪽 코어에 걸리느냐에 따라 시간이 달라졌음.

운영 워커를 `taskset -c 0-127`로 CPU 0~127번 코어에 묶어서 다시 띄웠음. 그 뒤 uptown funk 한 곡이 30.0초에 끝났음.

## 증상

- 사이트에 곡을 올리고 채보 화면이 뜨기까지 1분 30초~1분 40초가 걸렸음. 이 시간에는 브라우저 업로드, 워커가 작업을 가져가기까지의 대기, 화면의 상태 조회 간격이 함께 들어 있음. 워커 밖에서 걸리는 시간은 따로 측정하지 않았음.
- 운영 워커 로그 `~/ssaplash/results/worker.log` 기준으로, 11/06~11/09 작업 8건은 40.3~90.4초가 걸렸고 중앙값은 54.3초였음.
- 같은 곡도 시간이 달랐음. 노트 814개로 나온 같은 곡이 52.7초, 67.3초, 71.6초, 90.4초로 매번 다르게 나왔음.

## 측정 방법

`AI/scripts/worker_speed_check.py`로 측정했음. 이 스크립트는 서버에 BE 역할을 하는 테스트용 서버를 띄우고, 운영 워커 코드를 그대로 실행해 mp3를 처리하게 함. 워커가 하는 일은 사이트 업로드 때와 같은 순서로 진행됨.

1. 원곡을 내려받음
2. BS-Roformer SW로 드럼과 반주를 분리함
3. 분리한 트랙을 flac으로 올리고 분리 결과를 제출함
4. 같은 작업을 채보 단계로 다시 배정받음
5. ADTOF와 드럼 킷 분리로 채보하고, Beat This!로 bpm을 구해 결과를 제출함

측정한 11/10 기준 흐름임. 지금은 1번 뒤에 음악 여부 검사를 하고, 5번 채보는 STRUM 학습 가중치로 하며 채보 단계가 곡당 2~3초임.

로그의 시간 값은 이렇게 읽음.

- 분리 ms, 채보 ms: `separation.py`, `transcription.py`에서 모델 추론 한 줄만 감싸서 측정한 시간임. 파일 주고받기와 BE 통신은 들어가지 않음.
- 처리 시간: 작업을 받은 순간부터 채보 결과를 제출할 때까지 걸린 전체 시간임.

곡은 사용자가 올릴 법한 실제 발매곡 mp3 10곡을 썼음. 320kbps, 2분 22초~5분 30초 길이임.

## 스레드 수 측정

워커 CPU 스레드 수를 바꿔 가며 같은 10곡을 돌렸음. 스레드 수는 `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `NUMEXPR_NUM_THREADS`로 정함. 측정 중 서버 상태가 변하는 영향을 고르게 나누려고, 설정 순서를 한 번 뒤집어 두 바퀴 돌렸음. 그래서 설정마다 20곡씩 나왔음.

| 스레드 수 | 곡당 중앙값 | 분리 모델 | 채보 모델 | 워커 CPU 사용률 | GPU 사용률 |
| --- | --- | --- | --- | --- | --- |
| 제한 없음 | 78.4초 | 26.7초 | 41.5초 | 4364% | 6.5% |
| 16 | 25.0초 | 9.9초 | 10.0초 | 354% | 20.0% |
| 4 | 26.4초 | 11.2초 | 10.4초 | 131% | 20.5% |

CPU 사용률은 코어 하나를 다 쓰면 100%로 계산한 값임. 스레드 제한 없음 첫 바퀴 10곡을 기준으로, 나머지 50곡의 노트가 전부 같게 나왔음. 이 결과를 보고 운영 `~/ssaplash/worker.env`에 스레드 수 16을 넣었음.

## 운영 적용 뒤에도 느림

스레드 16을 넣고 워커를 다시 띄웠는데도 운영 작업은 빨라지지 않았음.

| 작업 | 곡 | 처리 시간 | 분리 모델 | 채보 모델 |
| --- | --- | --- | --- | --- |
| 26 | Thunder | 60.7초 | 22.2초 | 27.8초 |
| 27 | 확인 안 함 | 108.2초 | 41.4초 | 45.2초 |
| 28 | 확인 안 함 | 545.3초 | 195.9초 | 184.2초 |
| 29 | T.B.H, 2분 56초 wav | 68.3초 | 23.0초 | 31.5초 |
| 30 | uptown funk | 101.6초 | 32.9초 | 45.1초 |

작업 28이 도는 동안 2초마다 기록해 보니, 워커 CPU는 98~102%로 코어 1개 분량에 머물렀고 GPU 사용률은 0%였음.

## 확인해서 제외한 것

| 확인한 것 | 결과 |
| --- | --- |
| 워커가 쓸 수 있는 코어 | `Cpus_allowed_list` 0-255, 전부 쓸 수 있음 |
| CPU 사용량 상한 | cgroup `nr_throttled` 0, 상한에 걸린 적 없음 |
| 우선순위 | nice 0, 기본값 |
| 메모리 | 4TB 중 146GB 사용, 워커 swap 0 |
| 서버 CPU 한 코어 속도 | 숫자 1천만 개 제곱 합 0.75초, 정상 |
| 워커가 받은 환경 변수 | 스레드 4개 값 16, 줄 끝 문자 정상 |
| 코드 | 운영과 측정 모두 서버의 같은 v2.2 체크아웃 |

같은 uptown funk를 같은 시간대에 비교해도 차이가 났음. 테스트용 BE로는 31.0초, 사이트로는 71.5초였음.

## 코드 위치별 비교

py-spy로 두 워커를 기록해 비교했음. py-spy는 실행 중인 파이썬 프로그램이 지금 어느 함수를 실행하는지 1초에 50번 찍어 두는 도구임. 사이트로 올린 uptown funk 한 곡과, 테스트용 BE로 돌린 같은 곡을 각각 기록했음. 기록 스크립트는 `AI/scripts/profile_worker.sh`임.

| 함수 | 하는 일 | 사이트 작업 | 테스트용 BE 작업 |
| --- | --- | --- | --- |
| `Linear.forward` | 분리 모델의 GPU 계산 | 2.4초 | 3.1초 |
| msst `bigshifts_wrapper`의 `np.mean` | 분리 결과 배열을 평균 내 최종 트랙 배열을 만듦 | 23.4초 | 2.0초 |
| msst `bigshifts_wrapper`의 dict 생성 | 분리된 트랙마다 배열을 이어 붙여 새로 만듦 | 6.2초 | 0.3초 |
| `limit_peaks` | 반주 트랙의 피크를 리미터로 낮춤 | 5.2초 | 0.4초 |
| `nan_to_num` | 분리 결과의 NaN·무한대 값을 0으로 바꿈 | 3.3초 | 0.7초 |

GPU 계산은 두 작업이 비슷했음. 늘어난 건 수백 MB짜리 numpy 배열을 CPU로 읽고 쓰는 계산이었고, 약 10배 느렸음. 파일 내려받기와 올리기는 두 작업 모두 1초 안팎이었음.

## NUMA 노드 비교

`lscpu` 기준으로 서버의 NUMA 노드는 2개임. CPU 0~127번은 노드 0, 128~255번은 노드 1임. `nvidia-smi topo -m`을 보면 GPU 6번은 노드 1 쪽, CPU 128~255번에 붙어 있음. 이때 운영 워커의 메모리는 노드 0에 1,817MB, 노드 1에 414MB가 올라가 있었음.

테스트용 BE로 uptown funk와 highway to hell 두 곡을 돌리면서, 워커를 한 번은 노드 1 코어에, 한 번은 노드 0 코어에 `taskset`으로 묶었음.

| 묶은 코어 | 곡당 중앙값 | 분리 모델 | 분리 뒤 파일 처리 | 채보 모델 |
| --- | --- | --- | --- | --- |
| CPU 128~255번, 노드 1 | 265.2초 | 86.0초 | 111.5초 | 60.7초 |
| CPU 0~127번, 노드 0 | 26.8초 | 9.2초 | 3.7초 | 12.9초 |

분리 뒤 파일 처리는 분리 단계에서 모델 추론을 뺀 나머지 시간임. 원곡 내려받기와 읽기, flac 쓰기, 올리기, 분리 결과 제출이 들어감. GPU와 같은 쪽인 노드 1 코어에서 돌 때 오히려 10배 느렸음. 노드 1 코어가 왜 느린지는 측정하지 않아서 모름.

## 조치

운영 워커를 CPU 0~127번 코어에 묶어 다시 띄웠음. 리눅스는 기본 설정에서 메모리를 처음 쓰는 코어와 같은 노드에 올림. 다만 조치 뒤 워커 메모리가 실제로 어느 노드에 올라갔는지는 측정하지 않았음.

| 작업 | 곡 | 처리 시간 | 분리 모델 | 채보 모델 |
| --- | --- | --- | --- | --- |
| 31, 조치 전 | uptown funk | 71.5초 | 25.3초 | 30.4초 |
| 32, 조치 후 | uptown funk | 30.0초 | 8.9초 | 13.6초 |

조치 뒤 운영 작업은 아직 1건만 측정했음. 여러 곡으로 다시 확인해야 함.

## 운영 워커 띄우는 법

GPU 서버 JupyterHub 터미널에서 실행함. 명령은 각각 한 번씩만 실행함.

처리 중인 곡이 없는지 확인함. 마지막 줄이 `끝: DONE`이나 `워커 시작`이면 됨.

```bash
tail -1 ~/ssaplash/results/worker.log
```

워커를 멈춤. `kill -TERM`을 두 번 보내면 처리 중인 곡을 버리고 바로 꺼지므로 한 번만 보냄.

```bash
P=$(cat ~/ssaplash/worker.pid); kill -TERM $P; while kill -0 $P 2>/dev/null; do sleep 2; done; echo "멈춤"
```

CPU 0~127번에 묶어 띄움. `setsid`로 터미널과 떨어진 새 세션에서 띄우므로 터미널을 닫아도 계속 돎. `worker.pid`에는 실제 파이썬 워커 pid가 적힘.

```bash
cd ~/ssaplash/S15P31A307/AI && set -a && source ~/ssaplash/worker.env && set +a && setsid nohup taskset -c 0-127 uv run --no-sync ssaplash-worker run >> ~/ssaplash/results/worker.log 2>&1 < /dev/null & sleep 3; pgrep -f "\.venv/bin/ssaplash-worker run" | tee ~/ssaplash/worker.pid
```

숫자가 하나만 찍혀야 함. 두 개가 찍히면 워커가 두 개 뜬 것이니, 먼저 뜬 쪽을 `kill -TERM`으로 멈춤.

묶였는지 확인함. `0-127`이 나오면 됨.

```bash
grep Cpus_allowed_list /proc/$(cat ~/ssaplash/worker.pid)/status
```

`~/ssaplash/worker.env`에는 기존 값과 함께 아래 4줄이 들어 있어야 함.

```
OMP_NUM_THREADS=16
MKL_NUM_THREADS=16
OPENBLAS_NUM_THREADS=16
NUMEXPR_NUM_THREADS=16
```

## 다시 확인하는 법

노드 1 코어가 느린 이유를 모르기 때문에, 서버 상황이 바뀌면 결과가 뒤집힐 수 있음. 운영 처리 시간이 다시 늘어나면 아래 명령으로 두 노드를 다시 비교함. 테스트용 BE로 두 곡씩 돌리며 4~5분 걸리고, 운영 워커는 그대로 둬도 됨.

```bash
cd ~/ssaplash/S15P31A307/AI && set -a && source ~/ssaplash/worker.env && set +a && for n in 1 0; do c=$([ $n = 1 ] && echo 128-255 || echo 0-127); CUDA_VISIBLE_DEVICES=6 MPLBACKEND=Agg taskset -c $c .venv/bin/python ~/ssaplash/notebooks/worker_speed_check.py --song ~/ssaplash/upload/speed_songs/uptown.mp3 --song ~/ssaplash/upload/speed_songs/highway.mp3 --gpu-index 6 --skip-variant --threads 16 --out ~/ssaplash/results/numa-node$n > ~/ssaplash/results/numa-node$n.log 2>&1; echo "노드 $n"; grep -A4 "설정별 중앙값" ~/ssaplash/results/numa-node$n/summary.md | tail -1; done
```

표의 세 번째 칸이 곡당 처리 시간임. 더 빠른 노드의 코어 번호로 `taskset -c`를 바꿔 워커를 다시 띄움. 같은 폴더가 이미 있으면 `--out` 폴더 이름을 바꿔서 실행함.

## 남은 일

- 끝난 일: 드럼 킷 분리 모델의 조각 겹침을 4에서 2로 줄이는 설정은 같은 MR에서 서비스에 반영했음. 테스트용 BE 측정에서 곡당 약 12.5초가 더 줄었고 노트 일치 F1은 0.979~1.000이었음. 서비스 기본이 STRUM으로 바뀐 뒤로 이 설정은 되돌리기용 모델 original·songsterr_avg에만 쓰임.
- 워커가 꺼져 있으면 BE가 대기 중인 작업을 30분 뒤에야 실패로 바꿈. 빨리 실패로 돌려주는 방법은 BE와 따로 정해야 함.
- 사이트에서 느끼는 대기 시간 중 업로드와 상태 조회 간격처럼 워커 밖에서 걸리는 시간은 아직 측정하지 않았음.
